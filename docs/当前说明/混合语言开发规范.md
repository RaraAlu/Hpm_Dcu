# DCU 混合语言开发规范

更新日期：2026-11-17。电机、IMU 公共模型和产品 PDO/CoE 适配使用 C++17；SSC 栈、C 应用入口、RTOS 编排和硬件适配保留 C。固件/BSP/依赖/生成物目录已分离；布局及遗留事项见[目录规划与实施状态](../设计资料/单片机工程目录重构规划.md)。

## 1. 语言归属

| 范围 | 语言 | 当前落点 |
| --- | --- | --- |
| 电机控制、状态、租约、查询和调度 | C++17 | `firmware/app/motor/`；会话、参数事务、总线调度分开维护 |
| 产品 PDO/CoE 与字典适配 | C++17，保留 C 回调链接 | `firmware/comm/ethercat/motor_pdo.cpp`、`motor_coe.cpp`、`motor_dictionary.cpp` |
| ENCOS 电机协议编解码与参数转换 | C++17 | [encos_motor.cpp](../../firmware/protocols/encos/encos_motor.cpp) |
| 公共电机模型、ENCOS 驱动及产品绑定 | C++17 | `firmware/devices/motor/`、`firmware/app/motor/motor_driver_binding.cpp`；已接入周期命令与反馈 |
| IMU 设备模型、有效性及驱动契约 | C++17 | `firmware/devices/imu/`；没有具体芯片驱动或采样接入，旧 `0x6300` 仍无有效样本 |
| 后续项目自有设备、总线访问及业务抽象 | C++17 | 按实际变化点引入，不提前创建空基类和逐函数转发层 |
| `main`、初始化编排、SSC 应用回调 | C | `firmware/app/main.c`、`firmware/comm/ethercat/ethercat_callbacks.c` |
| 周期交接、RTOS 任务/通知/断言 | C | `firmware/app/cycle/`、`firmware/app/runtime/`；不在快 IRQ 调用内核 |
| MCAN/GPIO/中断、ESC/PHY/EEPROM、GPTMR 适配 | C | `firmware/comm/` 的硬件实现与 `firmware/bsp/dcu_hpm5e31/` |
| HPM SDK、SSC 栈核心和生成对象存储 | C，启动文件仍为汇编 | 不更改第三方语言；`encos_storage.c` 单独包含原生成存储 |
| C/C++ 共享类型和跨语言函数声明 | 双语言兼容 `.h` | 固定宽度数据、原有 packed 布局、静态断言和 C 链接约定 |

`ethercat_canfd_gateway.c` 虽然叫“网关”，实际直接操作 MCAN、GPIO 和 IRQ，因此保留 C。将来拆出的高层抽象采用 C++，不把底层寄存器实现也整体改成 C++。

这是固件的语言归属，不要求把主机构建保护脚本或协议生成工具改写成 C。改成 `.cpp` 也不代表已经完成面向对象设计：电机核心已移除 SSC 头和 FreeRTOS 头，轴控制器不再直接访问全局字典，Raw CAN 核心只接收帧批次与发送策略；但应用适配、参数事务仍使用生成 DTO 与旧字典存储，轴内部也仍使用生成类型。职责拆分不重写启动/停止状态机，也不因一个模块新增一个任务。

## 2. 构建规则

[根 CMake](../../CMakeLists.txt)明确设置 `CMAKE_CXX_STANDARD=17`、`CMAKE_CXX_STANDARD_REQUIRED=ON`、`CMAKE_CXX_EXTENSIONS=OFF`。C++ 源码使用交叉 `g++`，原 `.c` 仍使用交叉 `gcc`；最终 ELF 由 `g++` 链接，产物路径和镜像检查入口不变。

只对 C++ 编译添加 `-fno-exceptions` 和 `-fno-rtti`，不把这些选项施加到 C 文件，也不通过将所有源码强制设为 C++ 来实现混合构建。新增实际模块时由上级 CMake 加入该目录，在模块的局部 CMake 显式注册，例如未来的 IMU 目录中：

```cmake
sdk_inc(.)
sdk_src(imu_driver.cpp)
```

上例不是已存在的具体芯片驱动。当前设备清单已注册 `imu/imu_device.cpp` 公共模型并有宿主测试；新增具体驱动仍必须先确认真实型号、协议、接线与运行需求，不添加空文件占位。

**从旧 C 版本或旧目录布局首次切换，或以后删除/改名静态库源码时，要先清理对应配置的构建产物。** 当前 SDK 的归档命令使用 `ar crD`，增量归档可能保留旧对象。仅 `cmake --fresh` 清理缓存不够，可能在 `--whole-archive` 链接时重复定义。移动前先保留旧 ELF 并执行旧配置的 `clean`；新布局就绪后重新配置和构建：

```bash
cmake --build --preset hpm-debug --target clean
cmake --fresh --preset hpm-debug
cmake --build --preset hpm-debug
cmake --build --preset hpm-debug --target check-image
cmake --build --preset hpm-release --target clean
cmake --fresh --preset hpm-release
cmake --build --preset hpm-release
cmake --build --preset hpm-release --target check-image
```

首次配置、尚无构建目录时跳过 `clean`。若旧布局已经消失导致旧缓存无法执行 `clean`，不要为迁就缓存复制回旧源码；保留所需旧产物后，将对应旧构建目录移出并重新配置。日常不涉及源码删除/改名时继续使用 `python3 scripts/dcu.py build --preset hpm-debug`，不要求每次清理。

## 3. 接口与实时约束

- 自有固件的宏及类型声明放在 `.h/.hpp`。公共契约放模块公共头，内部 `struct/enum/class` 和类型别名放 `detail/` 私有头；工程配置放 `cfg/`。`.c/.cpp` 保留函数实现与模块私有状态实例，不以公开 `extern` 状态数组替代封装。
- 私有头可独立、重复包含；普通类型头不分配可变实例。SSC 既有生成存储是特例：只由 `ethercat_callbacks.c` 包含专用 owner 头，保持 `_DIGITAL_IO_` 的定义/清除作用域，不将实例选择宏放进公共配置。
- C 调用 C++ 时，公共 `.h` 在 `__cplusplus` 条件下以 `extern "C"` 包围函数声明。现用 `motor_control_*`、`MC_*`、`mc_object` 以及 ENCOS 配置/参数辅助函数保持 C 链接；SSC 回调名称不变。已退役的 `encos_encode/encos_feedback` 不保留兼容入口，运动编解码改用 [encos_motor.hpp](../../firmware/protocols/encos/encos_motor.hpp) 的 C++ 契约。
- C++ 调用 C 时，优先使用已有兼容头；未提供 C 链接保护的 SSC 头在 C++ 使用处统一包入 `extern "C"`，不为此修改第三方栈。
- C 接口不暴露类、引用、模板、STL 容器或依赖 C++ 生命周期的对象。纯 C++ 内部类型可用 `.hpp`，不与线上 PDO/SDO 数据布局混用。
- 共享布局断言通过 [dcu_compiler.h](../../firmware/cfg/dcu_compiler.h) 的 `DCU_STATIC_ASSERT` 在 C 下使用 `_Static_assert`，在 C++ 下使用 `static_assert`。不删除或关闭布局检查。
- `encos_storage.inc` 保持原字节，由 [encos_storage.c](../../firmware/comm/ethercat/encos_storage.c) 按 C 编译；不让生成的 C 指定初始化依赖 C++ 扩展。原文件头仍记录旧包含者，实际构建关系以 C 包装文件为准。
- 不在控制周期、ISR 或长时间关中断区内引入堆分配、阻塞调用或隐含锁。关闭异常不等于禁止 `new`，是否使用动态内存必须另行评审。
- 设备访问不依赖全局对象动态构造的先后顺序；在板级初始化完成后显式初始化。现有 SDK 有静态构造调用机制，但本轮没有在板上验证 C++ 构造函数。
- 不为使用 C++ 强行把所有函数装进类；先保留现有保护行为，再在协议测试和真实依赖的基础上收敛模块接口。
- 电机有状态操作采用普通成员函数，各轴控制和原始 CAN 转发对象分别持有私有状态，应用对象负责组合与编排。纯辅助函数可放匿名命名空间；不通过删除 `static` 暴露内部全局函数，也不机械移除 C 快路径中合理的私有辅助函数。对象实例仍可具有静态生命周期。
- 轴的反馈、故障和查询值由轴对象持有，不能从对象字典读回作为安全判定输入。`read_feedback()` 只复制快照，不消费新反馈/新功率事件；发布路径复制后才调用 `acknowledge_publication()`。SDO 读取和重复 PDO 映射不得消费下一拍的事件或改写已冻结的输入映像。
- 周期运动的线格式转换只在产品绑定处发生一次，ENCOS 驱动和编解码核心直接使用 `motor::Command/Feedback`，不重新构造 `mc_axis_rx_t/mc_axis_tx_t`。类型化输入不意味着可以删除电流宽度、模式字段约束或反馈有效性检查。
- Raw CAN 不读取轴数组、对象字典或 PDO 映像。PDO 适配解包帧批次，应用提供已生效的保留 ID 和当前准入；Raw 对象只维护队列、序号与限流状态。只处理已接受的新输入，不保留旧暂存 API；旁路与全量 Raw 的不同序号消费语义不能合并。

共享生成头 `encos_interface.h` 仅增加断言兼容和 C 链接声明，字段、位定义、接口版本及默认存储不变。生成链仍不可用，未运行再生成；恢复生成器时须把兼容规则纳入输出，详见[生成文件与来源清单](生成文件与来源清单.md)。

## 4. 开发与验证

VS Code 的 C/C++ 配置使用现有 CMake 提供器和 `compile_commands.json`，已移除该配置中的 ROS2 包含路径、宿主 x86 编译器及个人绝对路径。其他扩展的 ROS2/Python 辅助设置仍可被编辑器回写，不参与固件 CMake 构建。固件编译和调试仍使用原锁定的 HPM 工具链及受保护入口。厂商 GDB 没有 Python 支持，不能据此承诺 STL pretty-printer 可用。

离线测试入口不变：

```bash
python3 scripts/dcu.py test
ctest --preset hpm-debug
```

新增主机端协议测试通过宿主 `cc` 编译 C 存储与调用者，再通过宿主 `c++` 编译、链接并执行 C++ 协议实现。完整测试套件因此需要宿主 C/C++ 编译器，Ubuntu 可由 `build-essential` 提供；这不替代 MCU 交叉工具链，详见[环境准备](环境依赖与外部资源准备.md)。缺少编译器会明确报错，不静默跳过业务测试。

目录迁移时套件为 47 项，配置归档后为 55 项，设备抽象后为 71 项；RTOS 接入及后续修复、职责拆分后为 128 项，命名整理后为 129 项，声明归属后为 133 项；电机对象化后为 144 项，首批业务简化后为 151 项，轴状态与发布快照分离后为 158 项，运动编解码模型统一后为 162 项，Raw CAN 职责隔离后当前为 170 项。完整执行含两个需要可选 Unicorn 的真实内核执行用例；普通入口缺该依赖时为 168 项通过、2 项跳过。当前 Debug/Release 均为 96 个生产编译单元，其中 13 个 C++。

公共设备模型单独在没有 SDK、SSC 和生成头包含路径的宿主编译中验证；ENCOS Adapter 用独立冻结的旧算法作差分，避免新接口与其包装相互比较。18 项设备测试与 9 项协议测试通过 ASan/UBSan 和浮点到整数越界检查，41 项电机/对象及 4 项独立 Raw CAN 用例通过 ASan/UBSan；这些测试均可用 `DCU_HOST_SANITIZE=1` 重跑。Raw CAN 独立测试不链接轴、参数事务或 PDO 实现，只借助 CAN 发送替身和 HPM 类型桩。C/C++ 参数查询链接与共享布局仍单独验证。调度模块独立测试，电机夹具通过公开 C/C++ 接口和 CAN 替身构造状态，生产实现按独立翻译单元链接，不再包含 `.cpp` 或直接修改应用私有状态；仍使用旧字典准备配置，不是完整协议栈或硬件黑盒测试。对象化阶段见[对象化回归记录](../验证记录/2026-11-16-电机应用对象化与接口回归记录.md)，后续简化结果、资源成本与剩余耦合见[固件评审及实施记录](../设计资料/固件目录与代码划分评审.md)，设备接口边界见[设备接入规范](设备驱动扩展与接入规范.md)。

文件名对照、保留的 SSC 固定接入头以及本轮清理重建结果见[命名整理记录](../验证记录/2026-11-16-模块文件命名整理与验证.md)。改文件名不等于改 C 链接符号或线上协议。

声明归属检查包含自有实现文件扫描、私有头唯一包含者、独立/重复包含编译，以及普通类型头的双翻译单元链接；覆盖范围与生成存储特例见[类型与配置整理记录](../验证记录/2026-11-16-类型声明与配置归属整理记录.md)。

以下保留先前语言迁移阶段、尚未移动主目录时的验证结果，不是当前映像的体积表：

- Debug/Release 清理后完整编译、C++ 链接及 EEPROM 保留区检查通过。
- 当时 43 项离线测试通过，其中 8 项为新增协议与语言互操作测试，覆盖 C 调用 C++、C++ 访问 C 存储、共享布局、对象字段边界、五种控制模式固定字节样例、非法命令、反馈、参数查询与浮点输入。
- 同一组 8 项测试也通过了改动前 `c5ede57` 中 C 协议实现的主机编译与执行，作为迁移回归基线；这不等于覆盖了所有输入或证明实物协议已经验收。
- 离线 GDB 能解析新 Debug ELF 的 `main`、电机 C++ 源码行和 `axis_t` 类型，关键 C 接口符号保持原名；Release 保持原优化且无源码行调试信息。没有进行目标连接或 GUI 联调。
- 相对本轮改动前的 C 版本，`size` 的 Debug `text` 从 `295272` 到 `295456` 字节，Release 从 `276944` 到 `277104` 字节；两种配置各自的 `data/bss` 未变。这不是最坏执行时间或运行时堆栈占用测量。
- 本轮未访问 J-Link、未复位或烧录目标，也未验证 IMU、实际电机、EtherCAT 周期及停机效果。先前 C 固件的硬件实测不自动覆盖新的 C++ 映像。
