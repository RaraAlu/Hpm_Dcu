## 3. 当前 DCU 工程的日常入口

继续在 VS Code 中打开 **`Dcu_dev` 根目录**，不要为了使用 HPM 插件而把当前工作区改成里面的 SDK 目录。

| 要做的事 | 使用方法 |
| --- | --- |
| Debug 构建 | `Ctrl+Shift+B`，默认任务为 `DCU: Build Debug` |
| Release 构建 | 命令面板执行 `Tasks: Run Task`，选择 `DCU: Build Release` |
| 工具检查 | 运行任务 `DCU: Doctor (offline)` |
| 离线测试 | 运行任务 `DCU: Offline Tests` |
| CMake 图形入口 | 执行 `CMake: Select Configure Preset`，选择 `hpm-debug` 或 `hpm-release`，再选择对应 Build Preset 并构建 |
| 代码补全与跳转 | 先构建一次，再使用 C/C++ 的跳转、引用和悬停；配置已指向本机交叉编译器和编译数据库 |

工作区显式配置的编译数据库路径为 `build/hpm-debug/compile_commands.json`，同时启用了 CMake Tools 配置提供器。切到 Release 时应通过 C/C++ 诊断核对实际生效配置，不能仅凭这个固定路径判断所有补全信息都来自 Debug。不要改成系统 x86 编译器来消除 RISC-V 头文件报错。

这些入口来自[任务配置](../../.vscode/tasks.json)、[工作区设置](../../.vscode/settings.json)和[实际 Presets](../../cmake/cfg/CMakePresets.json)，不是 HPM 插件新生成的任务。根 `CMakePresets.json` 仅包含实际预设；`.vscode/` 是工具固定入口，不移入 `cfg/`，其余归档规则见[配置文件归档规范](配置文件归档规范.md)。

## 4. HPM SDK Explorer 的使用与限制

### 4.1 它适合做什么

该扩展由 `RCSN` 发布，提供 HPM SDK 示例浏览、板卡选择、工具环境检查和调试配置生成。它本身不包含 SDK、编译器或探针服务端；不能仅因面向 HPM SDK 就把它当作 HPMicro 官方工具包。功能入口可对照[作者说明](https://github.com/RCSN/vscode-hpm-sdk-explorer)。

按 `Ctrl+Shift+P` 输入 `HPM SDK`，本机版本声明的主要命令如下。中文标题会随界面语言变化，命令 ID 可用于核对。

| 命令面板入口 | 命令 ID | 作用或影响 |
| --- | --- | --- |
| 配置 SDK 环境 | `hpmExplorer.environment` | 检测/选择工具；保存环境会修改工作区配置 |
| 打开示例面板 | `hpmExplorer.open` | 查看示例与构建选择 |
| 刷新示例与板卡 | `hpmExplorer.refresh` | 重新扫描当前 SDK |
| 应用当前选择 | `hpmExplorer.apply` | 将选择同步到 CMake 设置，不是纯查看 |
| 配置当前示例 | `hpmExplorer.configure` | 修改配置并运行 CMake |
| 配置并编译当前示例 | `hpmExplorer.build` | 配置并编译所选示例 |
| 可视化调试配置 | `hpmExplorer.debugConfiguration` | 保存时可能新增或更新插件管理的 `launch.json` 条目 |
| 选择调试接口 | `hpmExplorer.selectDebugProbe` | 切换插件调试配置，不代表已连接探针 |
| 恢复插件接管前的 CMake 设置 | `hpmExplorer.restoreSettings` | 根据插件备份恢复所管理的设置项 |

### 4.2 在独立 SDK 副本中体验

1. 用新窗口打开一个独立的、包含示例的 HPM SDK 工作副本；不要与当前 DCU 共用插件的构建目录。
2. 信任确认过的工作区，点击活动栏的 HPM SDK Explorer，或打开其示例面板。
3. 打开 SDK 环境配置，检查 SDK、工具链、CMake、Ninja、OpenOCD、Python 和工具链类型；全部有效后再保存。
4. 选择开发板、示例、`flash_xip` 等运行模式和 Debug/Release。侧栏先暂存选择；点击应用/配置/构建才执行对应操作。
5. 先仅验证配置和编译，不启动新生成的硬件调试项。状态栏切换板卡、示例或构建类型也可能自动同步配置，不能视为只读浏览。

本工程的路径来源可用于核对工具，但**下面不是要求在当前 DCU 工作区执行接管**。在实验副本中，SDK 路径应指向副本自身，不能让插件向原 SDK 写入构建目录。

| 环境项 | 当前工程可核对的来源 |
| --- | --- |
| `HPM_SDK_BASE` | 工程内 `third_party/hpm_sdk/` |
| 板卡与搜索路径 | 根 CMake 选择 `BOARD=dcu_hpm5e31`、`BOARD_SEARCH_PATH=firmware/bsp` |
| `GNURISCV_TOOLCHAIN_PATH` | 工程内 `.tools/hpm-gcc-13.2.0/`，不是其 `bin/` 下某个程序 |
| `HPM_SDK_TOOLCHAIN_VARIANT` | `gcc` |
| `CMAKE` | 本机 `/usr/bin/cmake` |
| `NINJA` | 工程内 `.tools/host/usr/bin/ninja` |
| `PYTHON3` | 本机 `/usr/bin/python3`；SDK 配置脚本使用 PyYAML，IAR/SES 项目生成脚本另使用 Jinja2 |
| `OPENOCD` | 工程内 `scripts/openocd.sh`，包装本地厂商 OpenOCD 并补充动态库路径 |

填写文件选择器时使用对应的实际绝对路径。`openocd.sh` 仅是工具启动包装，**不包含 `dcu.py` 的板级确认、镜像和保留区事务保护**，不能把选中该脚本误当作已经接入安全调试流程。

本地化 SDK 没有完整的 `samples/`、`unit_test/` 目录。插件默认扫描这两类目录，因此列表为空不必然是安装失败。独立实验中可通过 `hpmExplorer.sdkPath` 选择 SDK、`hpmExplorer.sampleRoots` 设置额外示例根目录；扫描只收录直接调用 `find_package(hpm-sdk ...)` 的应用入口。

当前自研 BSP 已移至 SDK 外部。HPM 插件的新建/重新生成工程流程及外部 BSP 自动扫描尚未验收；日常继续使用当前 Presets，不为让插件列表显示板卡而复制回 SDK 或覆盖根 CMake。

### 4.3 为什么暂不接管本工程

以下差异由本机 0.1.0 的 `src/configuration.js`、`src/debug-probes.js` 和本工程配置对照确认：

| 项目 | 当前 DCU | HPM 插件默认生成/接管行为 |
| --- | --- | --- |
| Presets | `cmake.useCMakePresets = always` | 应用选择时写入 `never` |
| 构建目录 | `build/hpm-debug/`、`build/hpm-release/` | 使用 `<所选SDK>/build/`；配置改变时可能清理重建 |
| ELF | `build/hpm-debug/output/dcu.elf` | 按 SDK 构建目录及 `APP_NAME` 推导，不能假定仍是 `dcu.elf` |
| 调试类型 | `cppdbg`，由 `scripts/dcu.py debug-server` 启动受保护的 OpenOCD | 生成 `cortex-debug` 类型，默认流程不等于本项目事务入口 |
| 启动行为 | 校验/必要烧录结束后暂停，不自动继续 | 生成器会为 launch 配置填写 `runToEntryPoint = main` |
| 默认探针 | 本工程 OpenOCD 配置使用 J-Link | 当前板卡 YAML 声明 `openocd-probe: ft2232`，不能直接沿用 |

还要区分 **J-Link 探针**与 **SEGGER J-Link GDB Server**：本工程使用厂商 OpenOCD 的 J-Link 驱动；HPM 插件内置的 J-Link 选项生成 `servertype: jlink`，不是自动复用本工程的 OpenOCD 事务。

因此当前工程保持既有任务和启动项。确需评估接管时，先在副本中验证配置差异、RISC-V 调试互操作、Flash/EEPROM 保护和暂停行为，再单独设计集成，不直接按新生成条目的 F5。

## 5. 调试扩展怎么用

### 5.1 当前优先使用 C/C++ 的 cppdbg

板级核对、隔离电机动力和独立急停准备完成后，才在“运行和调试”选择现有入口：

- `DCU: Reset Debug (verify existing Flash, no programming)`：校验已有 Flash 后复位暂停，不写入固件。
- `DCU: Flash + Reset Debug (backs up retained EEPROM)`：包含备份、写入及校验，再复位暂停。

两者均需要单次 `RESET_TARGET` 确认，且本机板级配置仍须通过检查。即使不烧录也会复位/暂停；板级未确认时应让保护拒绝，不通过修改字段绕过。完整约束见[工程 README](../../README.md)。

当前两个入口均通过 `stopAtConnect=true` 配合 `launchCompleteCommand=None` 在连接后保持暂停，初始位置为 `_start`；`main` 硬件断点改在符号加载和连接完成后设置。手动继续才运行到 `main`，不能仅凭 `launchCompleteCommand=None` 判断不会自动继续。[C/C++ 配置语义](https://code.visualstudio.com/docs/cpp/launch-json-reference#_stopatconnect)

若 GUI 显示“出现异常”但正文只是 `Hit breakpoint 2 at 0x800061f2.`，它对应本镜像 `main` 的正常断点命中，不是凭这条信息就能认定的固件崩溃。原配置手动创建的 `hbreak main` 不在 C/C++ 的原生断点登记表中，而扩展对外部断点默认采用 `throw` 分类；两个入口现已显式设置 `unknownBreakpointHandling: stop`，仍会暂停，但不将这类命中显示成应用异常。真正的信号异常处理未关闭。配置只在新会话启动时生效；不要关闭所有异常断点来绕过提示。后续复验状态见[实测记录第 8 节](../验证记录/2026-11-13-调试与下载实测记录.md#8-断点异常标签后续修正)。

Cortex-Debug 上游定位是 ARM Cortex-M 调试，但本轮已实测其外接 OpenOCD 的 RISC-V 基础调试可用：使用 `servertype: external`、RISC-V GDB/objdump/nm，关闭 SWO/RTT，由原有受保护入口先准备服务端。这不是 HPM 插件默认 J-Link 配置的验收，也没有把实验入口写入日常 `launch.json`。实验的 `attach` 仍会因服务端策略复位目标，不是无扰动附加；服务器生命周期统一前不把它作为默认入口。不要照搬 ARM GCC 或 SWO/ITM 示例。[Cortex-Debug 上游定位](https://github.com/Marus/cortex-debug)

### 5.2 Memory View

1. 先经已有受保护入口建立目标调试会话，并确认暂停状态；本轮未执行这一步。
2. 命令面板运行 `MemoryView: Add new memory view (for debugger)`，ID 为 `mcu-debug.memory-view.addMemoryView`。
3. 输入明确的内存地址或仅求地址的表达式，例如 `&board_command`，在 `MEMORY` 面板查看内容；不要输入会调用函数的表达式。
4. 按只读方式使用，并区分暂停、运行中和未关联会话的缓存显示；多个内存窗口会增加调试通信负担。

Memory View 的说明列出 `cppdbg` 支持，因此不必为看内存强制切换到 Cortex-Debug；本板实际读内存仍需验收。暂停 CPU 会停止软件租约和反馈处理，不能把这个过程当成物理急停或实时性测试。[Memory View 上游说明](https://github.com/mcu-debug/memview)

### 5.3 Peripheral Viewer

需要与 HPM5E31 匹配的 SVD 和可读目标内存的调试会话。本工程本地化 SDK 目前未发现 `.svd` 文件，也没有为现有启动项配置 SVD，不能保证安装后就出现正确寄存器树。

取得并核对 SVD 后，可在实验调试配置中按该扩展要求提供路径；对 `cppdbg` 使用 `svdPath`，不要误用 Cortex-Debug 常见的 `svdFile`。展开外设读取前须核对寄存器访问副作用，不点 `Update Value` 写寄存器。[Peripheral Viewer 上游说明](https://github.com/mcu-debug/peripheral-viewer)

### 5.4 Debug Tracker 与 RTOS Views

Debug Tracker 是视图扩展共享的会话跟踪依赖，通常无需手动操作；排查视图问题时才查看其输出或调试日志级别，不把 `Activate Debug Tracker` 当作连接硬件的命令。

RTOS Views 依赖目标中可识别的 RTOS 数据和调试符号。当前 `firmware/app/main.c` 运行裸机主循环，没有任务列表是正常情况；不应仅为展示线程而引入 RTOS。以上两项都不安装编译器、烧录驱动或 GDB Server。

## 6. 日志、曲线与文件检查

### 6.1 Serial Monitor

打开底部面板的 `Serial Monitor` 标签，选择核实过的串口设备和波特率，再开始监视。当前板级源码的 core0 控制台默认是 UART0、115200 波特率；以实际固件、引脚和 USB 转串口接线为准，不能从 J-Link 已枚举推断已有串口设备。

先核对电平、TX/RX/GND 和 Linux 设备权限，优先仅接收日志，不发送未知命令。一个串口不要同时被 Serial Monitor、Teleplot 和其他终端占用；日志和串口通信本身也会扰动时序。本轮未打开串口。

该扩展的上游仓库已经归档；本机安装并不代表后续仍持续维护，遇到兼容性问题时保留日志再评估替代工具，不为此自动换工具。[Serial Monitor 上游状态](https://github.com/microsoft/vscode-serial-monitor)

### 6.2 Teleplot

命令面板运行 `teleplot: Start teleplot session`，ID 为 `teleplot.start`，再在其界面选择串口。串口数值格式为 `>变量名:数值` 加换行，例如下面两行；普通启动日志不会自动变成电机曲线。

```text
>position:1.234
>velocity:0.125
```

上位机也可按 Teleplot 的 UDP 格式发送数据，默认端口为 47269；串口和 UDP 格式不同，不能直接混用。当前固件没有因为安装扩展就新增遥测，不在 MCAN/ESC 中断里临时增加高频 `printf` 来画图；应另行设计低频、受预算约束的诊断输出。[Teleplot 格式说明](https://github.com/nesnes/teleplot)

### 6.3 Hex Editor 与 XML

在 BIN 文件上选择 `Open With...`，用 Hex Editor 离线查看。例如 [SII BIN](../../protocol/ethercat/HPM_ENCOS_4CAN_28AXIS_IMU.bin) 是文件内容，不是目标 Flash 的实时窗口。先只读查看，不保存随手编辑，也不把 BIN 默认写到 `0x80000000`。

打开 [ENCOS ESI](../../protocol/ethercat/HPM_ENCOS_4CAN_28AXIS_IMU.xml)，用 XML 扩展查看层级或执行 `XML: Revalidate current XML file`。语法检查通过不等于 PDO、对象字典、结构体、SII 与上位机一致，不能直接修改或格式化生成文件后当作协议修复。维护约束见[生成文件清单](生成文件与来源清单.md)。

## 7. 配置变动检查与常见问题

体验插件前后可运行以下只读命令，确认有没有改动现有工程配置：

```bash
git status --short
git diff -- .vscode/settings.json .vscode/launch.json .vscode/tasks.json CMakePresets.json cmake/cfg/CMakePresets.json
python3 scripts/dcu.py test
```

HPM 插件声明的备份位置为 `.vscode/hpm-explorer.settings-backup.json` 和 `.vscode/hpm-explorer.launch-backup.<时间>.<标识>.jsonc`。接管后先比较差异，再评估“恢复插件接管前的 CMake 设置”；恢复 CMake 设置不等于恢复所有调试配置，也不覆盖其他工作。不要用整目录强制回退来清除不明改动。

| 现象 | 优先检查 |
| --- | --- |
| HPM 示例列表为空 | 是否打开了独立 SDK，是否有 `samples/`，自定义扫描路径是否正确 |

## 9. 能否替代自有 Python 与环境配置

### 9.1 当前判断

**扩展可以作为编译、调试和下载的操作入口，但目前不能直接删掉整套自有脚本、工具目录和配置。** 必须区分编辑器前端、底层工具和本工程的烧录约束，安装前端不会自动替代另外两层。这不是要求永久保留现有 Python 封装，而是不能在迁移时遗漏它目前承担的职责。

| 能力或依赖 | 扩展覆盖情况 | 当前可否删除原实现 |
| --- | --- | --- |
| 配置与构建入口 | CMake Tools 能使用现有 Debug/Release Presets，无需先经过 `dcu.py build` | 构建命令的 Python 转发可精简；不能因此删除整个 `dcu.py` |
| 调试界面 | 修正后的 C/C++ 入口和 Cortex-Debug 外接服务的基础调试通过 | HPM 默认生成配置仍未证明能替代本项目的启动策略 |
| 下载与校验入口 | 仍须调用匹配芯片的 OpenOCD 或其他已验证服务端 | 默认配置未接入保留区保护、备份和校验事务，暂不能替代 |
| SDK 的 Python 依赖 | 不由编辑器扩展替代 | 不能删除 Python 运行时及当前 SDK 所需依赖 |
| 项目保护脚本 | 扩展默认流程不提供本项目的 ELF 地址检查和 EEPROM 事务 | `image_guard.py` 和 `dcu.py` 的保护职责须保留或先迁移 |
| `.tools/` 与启动包装 | 仍提供 GCC、GDB、Ninja、厂商 OpenOCD 及运行库 | 替代工具安装、版本和运行库验证前不能删除 |
| Presets、调试与板级配置 | 扩展仍需知道 SDK、目标、探针、运行模式和工具路径 | 可统一配置来源，不能假定全部不再需要 |

Python 有两种不同含义：

- **自编流程封装**：`scripts/dcu.py` 的 configure/build 部分只是调用 CMake，可以由标准命令替代；其目标操作部分还负责板级确认、探针选择、冻结镜像、备份和校验，不能随薄封装一起丢弃。
- **SDK 构建依赖**：[application.cmake](../../third_party/hpm_sdk/cmake/application.cmake) 包含 [python.cmake](../../third_party/hpm_sdk/cmake/python.cmake)，[toolchain.cmake](../../third_party/hpm_sdk/cmake/toolchain.cmake) 调用 Python 获取 GCC 版本；板卡/应用解析脚本使用 PyYAML。即使删去全部自编 Python，当前 SDK 配置仍依赖 Python。Jinja2 用于 SDK 的 IAR/SES 项目生成脚本，当前 Presets 已排除这两类 IDE 生成，不能把它与每次普通构建必需项混为一谈。

关键风险是 EEPROM 仿真保留区 `[0x80080000, 0x80090000)`，共 64 KiB。[镜像检查](../../scripts/image_guard.py) 检查 ELF 物理加载段及包含空洞的整段擦除范围；[目标操作脚本](../../scripts/dcu.py) 在写入前备份保留区，写入后校验固件和保留数据，并保持暂停。普通“下载成功”不能证明这些约束已满足。改用 Tcl、CMake 或其他语言实现可以减少 Python 自编代码，但本质上是迁移保护逻辑，不是扩展已经自动覆盖。

### 9.2 已验证的原生命令入口

2026-11-13 直接执行以下命令，未经过 `dcu.py` 的命令分发：

```bash
cmake --preset hpm-debug
cmake --build --preset hpm-debug
cmake --build --preset hpm-debug --target check-image
cmake --preset hpm-release
cmake --build --preset hpm-release
cmake --build --preset hpm-release --target check-image
ctest --preset hpm-debug
```

两种配置成功；增量构建均返回 `ninja: no work to do`，不是本轮重新完整编译。两个 `check-image` 均通过，CTest 的 `devtools-offline` 套件通过。CMake 的 [devtools.cmake](../../cmake/devtools.cmake) 仍调用 Python 镜像检查和离线测试，因此这证明的是**无需 Python 构建命令封装**，不是整个构建不依赖 Python，也不是扩展 GUI 已验收。

上述离线检查时，本机板级配置的两个确认字段仍为 `false`，没有访问目标。随后用户确认隔离条件、授权硬件操作并要求采用 Windows 已验证的默认参数，才更新本地确认状态并开展第 10 节的上板测试。

### 9.3 精简方向与删除条件

推荐收敛到 **CMake Tools + C/C++ 调试界面 + 必要的板级 OpenOCD 配置 + 小范围保护逻辑**，而不是为了使用 HPM Explorer 再增加一套互相覆盖的环境来源。日常构建可直接使用第 3 节的 CMake Tools 入口；HPM Explorer 暂用于独立 SDK 示例评估。

1. 构建层统一使用现有 Presets。去掉 Python 转发时，同时更新任务、README 和测试，不保留两套不同的构建参数来源。
2. 对调试/下载先明确保留的约束，再接入新的前端：板级参数与探针选择、镜像/符号一致性、擦除范围检查、保留区备份和校验、最终暂停及服务退出。不能只验证一次 F5 能连接。
3. 在电机动力隔离并完成接线核对后，分别验收只校验调试、下载后调试、烧录失败和退出行为。离线检查通过不替代这些实物验收。
4. 责任迁移并通过验证后，再删除不再被调用的自编入口和对应测试；只有替代工具链就绪后才移除 `.tools/` 或安装脚本。不要卸载系统 Python 或删除 SDK 脚本来追求表面上的“无 Python”。

**删除评估阶段未删除任何脚本或工具链；后续上板测试修正了复位和启动暂停配置，未移除保护事务，也未修改固件控制逻辑。**

## 10. 基础调试与下载上板结果

在用户确认电机动力隔离、允许复位/暂停/烧录并采用既有默认板级参数后，已完成以下验证。完整过程、原始数据位置和异常记录见[调试与下载实测记录](../验证记录/2026-11-13-调试与下载实测记录.md)。

| 项目 | 实测结果 |
| --- | --- |
| JTAG 与目标 | TAP `0x1000563d`，单个 RV32 hart；修正复位时序后无前述扫描链/提前 halt 错误 |
| Flash | 驱动探测返回 1 MiB、4 KiB 扇区；当前 Debug ELF 已实际写入 |
| 下载回读 | 独立读取整个 1 MiB，6 个非空 ELF 加载段全部匹配；擦除范围外零字节变化 |
| EEPROM | 前后独立读取 64 KiB，与整片读取切片一致；前后零字节变化，未执行恢复写入 |
| C/C++ 适配器 | 两个现有入口均通过启动暂停、`main` 硬件断点、单步、变量、16 字节内存读取和断开 |
| Cortex-Debug 适配器 | `external` 接入受保护 OpenOCD，完成同类基础调试；默认 HPM/J-Link 配置未测试 |
| 最终状态 | 初次全量回读后停于 `0x80003000`；后续断点分类复验后停于 `main` 内 `0x800061f6`，对应调试服务均已退出 |
| 离线回归 | 当前 71 项测试及 CTest 通过：35 项保护与工具测试、8 项协议及 C/C++ 互操作测试、4 项布局/命名测试、8 项配置归档测试、16 项设备抽象测试；不等于新映像已完成 GUI 或硬件联调 |

这里的“适配器通过”指通过 DAP 协议启动本机扩展实际附带的适配器并连接真实目标板，不是只检查 JSON，也不是已经操作过 VS Code 的 GUI。C/C++ 适配器仍有未识别 RISC-V 架构元数据、假定 x86_64 的提示；GDB 实际识别 RV32，基础功能通过，但复杂展示兼容性仍需逐项确认。

测试还发现并修复了原配置的启动自动继续问题。修复前 CPU 曾意外运行约 30 秒，随后中断并暂停；最终独立回读确认 EEPROM 未变化。故障注入、脱离调试器启动、控制业务、实时性和电机物理停止均未验收。上述结果支持继续精简重复封装，但不等于插件已经替代 SDK Python、厂商工具链或保留区保护。
