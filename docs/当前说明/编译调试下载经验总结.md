# DCU 编译调试下载经验总结

整理日期：2026-11-13，时区 Asia/Shanghai。适用范围：当前 `Dcu_dev` 工程、Ubuntu 24.04 x86_64、HPM5E31、Flash XIP、J-Link JTAG。

当前基础链路已经打通：Debug/Release 编译通过，Debug 固件实板下载及回读通过，基础断点、单步、变量和内存读取通过。日常优先使用现有 CMake Presets 和 C/C++ 调试入口；新安装的 HPM 扩展不是底层工具链与项目保护逻辑的替代品。

本文侧重可复用的操作和排错经验。完整日志、镜像摘要、失败过程及复验记录见[调试与下载实测记录](../验证记录/2026-11-13-调试与下载实测记录.md)，扩展分类见[HPM 开发扩展指南](开发扩展分类与使用指南.md)。

首次搭建、离线安装和跨机器恢复先按[环境依赖与外部资源准备](环境依赖与外部资源准备.md)执行，不将本文的日常构建命令当成完整的系统安装流程。

## 1. 先区分各层职责

| 层级 | 当前实现 | 需要记住的边界 |
| --- | --- | --- |
| 编辑器与操作入口 | VS Code、CMake Tools、C/C++ | 界面能启动，不等于底层工具或目标板已经通过验证 |
| 配置与构建 | CMake Presets、Ninja、厂商 RISC-V GCC | Debug/Release 分开构建，避免混用缓存和产物 |
| 符号与调试协议 | RISC-V GDB、C/C++ 调试适配器 | 必须使用目标板上同一映像的符号；GUI 停止标签不一定等于底层停止原因 |

## 2. 日常编译

### 2.1 工作区和离线检查

在 VS Code 中打开 `Dcu_dev` 根目录，不要打开内层 SDK 目录。以下命令均在工程根目录执行：

```bash
python3 scripts/dcu.py doctor
```

`doctor` 检查本机工具、USB 枚举及权限，不初始化目标，也不复位或烧录；板级警告不能因进程退出码为 0 就忽略。固件构建和镜像检查不代替上板验收。语言边界及首次切换清理步骤见[混合语言开发规范](混合语言开发规范.md)。

缺少工具时使用工程已有的 `python3 scripts/dcu.py bootstrap` 恢复锁定版本。USB 权限不足时才在本机终端运行 `bash scripts/setup-usb.sh`；不要用 sudo 启动整个 VS Code。

### 2.2 选择一种构建入口

常用封装入口：

```bash
python3 scripts/dcu.py build --preset hpm-debug
python3 scripts/dcu.py build --preset hpm-release
```

GUI 中按 `Ctrl+Shift+B` 默认构建 Debug；Release 在命令面板的 `Tasks: Run Task` 中选择 `DCU: Build Release`。

不经过 Python 命令转发，也可以使用原生 CMake：

```bash
cmake --preset hpm-debug
cmake --build --preset hpm-debug
cmake --build --preset hpm-debug --target check-image
```

Release 对应把上述 preset 改为 `hpm-release`。CMake Tools 中可选择相应 Configure Preset 和 Build Preset，再构建，无需另建一套 HPM Explorer 环境。

这几种入口共用 Presets，不应各自维护不同的编译参数。原生 CMake 成功只证明不依赖 `dcu.py build` 的转发，SDK 配置和镜像检查仍使用 Python。

#### OpenIDEA 构建入口

OpenIDEA 0.1.47 的历史配置使用本机 `.openidea/settings.toml`（不随仓库交付）中的 `hpm-debug`、`hpm-release` 两个 CMake profile。“构建项目”默认使用排在首位的 Debug；也可选择 `CMake Build [hpm-debug]` 或 `CMake Build [hpm-release]`。配置和构建参数均通过 `--preset` 引用现有预设，工具链路径、Ninja 和并行度仍由 `cmake/cfg/CMakePresets.json` 管理。

本机实测发现，外部修改该文件后，当前窗口的运行配置列表可能仍保留旧入口；设置页能看到新 profile，也不代表构建列表已经刷新。本次通过“设置 > 构建、执行、部署 > CMake”修改 profile 名称并应用，再恢复原名称并再次应用，使当前窗口重新加载配置。最终点击工具栏锤子执行“构建项目”，日志为 `cmake --build build/hpm-debug --config debug --preset hpm-debug`，退出码为 0。日常构建使用锤子或“构建项目”，不要把仅配置成功当成已经完成编译。

不要使用自动发现的旧 `CMake Build`（`cmake --build build --config Debug`）。它没有加载 HPM 预设，配置会因缺少 `GNURISCV_TOOLCHAIN_PATH` 失败，之后构建才报 `could not find CMAKE_PROJECT_NAME in Cache`。只清缓存或手填该变量不能修复构建入口；正确目录为 `build/hpm-debug/` 或 `build/hpm-release/`。

这里仅配置固件构建。自动发现的 `dcu.elf` 不是可在宿主机直接运行的程序，不能用普通运行或 LLDB 入口替代下文受保护的实板调试流程。

#### OpenIDEA 代码跳转

构建成功不代表语言服务已加载相同的编译参数。根目录 [.clangd](../../.clangd) 将 clangd 的编译数据库指向 `build/hpm-debug/`；该文件是工具要求的根入口。首次配置或清理构建目录后，先执行 `cmake --preset hpm-debug` 生成 `compile_commands.json`。索引固定使用 Debug 参数，不随运行工具栏切换到 Release 而改变。

本机 `.openidea/settings.toml` 的 `languageServers.clangd.args` 保留后台索引，并通过 `--query-driver` 只允许查询项目 `.tools/hpm-gcc-13.2.0/bin/` 下的两个 RISC-V GCC/G++ 驱动，以获取目标平台和 C/C++ 标准库路径；不要改成允许任意可执行文件的通配符。`.vscode` 的 C/C++ 配置不能替代 OpenIDEA 的 clangd 配置。配置依据见 [clangd 编译数据库设置](https://clangd.llvm.org/config#compilationdatabase)和[交叉编译系统头文件说明](https://clangd.llvm.org/guides/system-headers#query-driver)。

本次故障中，缺少数据库时 clangd 使用宿主机回退命令，报 `board.h`、`hpm_ecat_hw.h` 缺失及 `TOBJ1018` 未知，跳转返回原调用位置或空结果；仅补数据库后，C++ 仍缺少 `<array>`。补齐上述两项后，语言服务协议实测 `main.c` 的四个符号和 `motor_application.cpp` 的三个符号均定位到预期定义，两个文件均无错误诊断。这是代表性跳转验证，不是全工程逐符号验收。

### 2.3 判断构建结果

Debug 主要产物为：

```text
build/hpm-debug/output/dcu.elf
build/hpm-debug/output/dcu.bin
build/hpm-debug/output/dcu.map
build/hpm-debug/compile_commands.json
build/hpm-debug/image-check.json
```

Release 使用对应的 `build/hpm-release/`。调试和下载默认使用地址感知的 ELF；BIN、MAP、编译数据库和镜像检查报告分别有不同用途，不能互相替代。

`ninja: no work to do` 表示增量构建无须更新，不是本轮重新完整编译。POST_BUILD 检查只在链接后执行；需要重新确认已有 ELF 时，显式执行 `check-image` 目标。

原 SSC 的已知编译警告仍需单独处理，不能为了获得“零警告”关闭检查或改动硬件配置。协议生成链另有未恢复部分，普通构建目前使用已提交的生成物，见[生成文件说明](生成文件与来源清单.md)。

## 3. GUI 调试和下载

### 3.1 每次上板前的条件

1. 隔离电机动力，保留控制板所需逻辑供电，并准备独立急停措施。
2. 确认 J-Link 的 VTref、GND、JTAG 和 nSRST 接线，核对目标板和 Flash 参数。
3. 结束其他占用该探针或 3333 端口的调试会话，不直接杀掉不明进程。
4. 确认本次允许复位、暂停及所选操作，再输入 `RESET_TARGET`；不要把确认写进全局环境长期生效。

当前板级默认参数曾由用户确认已在 Windows 验证，Linux 又完成了本次探测和读写验证。这不能代替换板后的重新核对，也不证明每次上板时电机动力都已经隔离。

### 3.2 根据目的选择入口

按 `Ctrl+Shift+D` 打开“运行和调试”，使用顶部下拉框中的现有入口：

| 目的 | 选择的启动项 |
| --- | --- |
| 不改固件，只校验并调试已有 Flash | `DCU: Reset Debug (verify existing Flash, no programming)` |
| 修改代码后下载新固件并调试 | `DCU: Flash + Reset Debug (backs up retained EEPROM)` |

两个入口都自动执行 Debug 构建，且都会复位/暂停目标。“不烧录”不是“无扰动附加”。修改源码后若 ELF 与板上固件不一致，应换到下载入口，不要忽略校验失败继续调试。

启动步骤：

1. 打开 [main.c](../../firmware/app/main.c)，定位 `main()`，不要使用旧 `ecat.c` 路径或历史行号。
2. 选择上述启动项，按 `F5`，按提示输入 `RESET_TARGET`。
3. 等待构建和受保护的服务端准备完成；失败时不要选择“仍然调试”。
4. 正常先停在 `start.S` 的 `_start`，这是连接后保持暂停的预期状态。
5. 再按一次 `F5`，命中预设 `main` 硬件断点，观察 `board_init();` 附近的源码位置；具体地址由当前 ELF 决定。
6. 先用单步和只读观察检查启动过程，不连续继续进入控制主循环。

常用 GUI 操作：

| 操作 | 入口 |
| --- | --- |
| 单步跳过函数 | `F10` |
| 单步进入函数 | `F11` |
| 跳出当前函数 | `Shift+F11` |
| 添加源码断点 | 点击行号左侧或 `F9` |
| 查看局部变量和调用栈 | 左侧“变量”“调用堆栈” |
| 添加只读观察 | “监视”中添加 `$pc`、`&board_command` 等表达式 |
| 结束调试 | `Shift+F5` |

首次调试不要在监视表达式里调用目标函数或随意改寄存器。调试期间也不要在另一终端重新构建同一配置的 ELF，否则符号和目标映像可能不再一致。

### 3.3 只下载或只校验

GUI 使用 `Tasks: Run Task`，选择 `DCU: Flash (explicit confirmation)` 或 `DCU: Verify (reset and halt)`。

下面的命令会访问目标，必须先满足第 3.1 节条件，不能作为无硬件检查命令执行：

```bash
python3 scripts/dcu.py flash --preset hpm-debug --confirm-target RESET_TARGET
python3 scripts/dcu.py verify --preset hpm-debug --confirm-target RESET_TARGET
```

日常省略 `--skip-build`，让入口先构建并检查镜像。该选项只适合已明确冻结产物的验证流程。下载/校验结束后目标保持暂停，不会自动继续运行。

排查运行中卡死且必须保留现场时，先隔离动力，再用 `debug-server --inspect-live` 配合对应的 preset 和同一确认参数。此模式不复位、不写 Flash：暂停 CPU、打印 PC 和异常寄存器并核对映像，GDB 附加时也不复位。不能与 `--flash-first` 混用。

## 4. 最重要的调试经验

### 4.1 USB 可用不等于复位可靠

本次 JTAG 初始识别和 Flash 读取成功，但复位仍出现扫描链全零和 Hart unavailable，进程却返回成功。不能只看进程退出码或是否有 USB 设备，必须检查复位日志、目标暂停状态和 PC。

最终修正是保留真实 nSRST 复位路径，补回厂商配置中的 500 ms 复位释放等待，并在项目加载 SoC 配置后清空不适用的提前 halt 回调：

```tcl
adapter srst delay 500
reset_config srst_only
source [find soc/hpm5e00.cfg]
$_TARGET0 configure -event reset-deassert-pre {}
```

这是当前板、探针和 SDK 组合的实测修正，不是所有 HPM 板都应照抄的通用参数。修改放在项目 `debug/cfg/openocd.cfg`，不改厂商 SDK；不要用取消 nSRST 声明来掩盖接线问题。等待时间的含义见 [OpenOCD 复位配置说明](https://openocd.org/doc/html/Reset-Configuration.html)。

### 4.2 服务端暂停不等于前端不会继续

原配置虽然设置了 `launchCompleteCommand=None`，C/C++ 适配器连接后仍自动继续。修正必须同时包含：

```json
{
  "stopAtConnect": true,
  "launchCompleteCommand": "None",
  "hardwareBreakpoints": { "require": true },
  "unknownBreakpointHandling": "stop"
}
```

这些是现有配置的关键字段摘录，不是完整启动配置。`stopAtConnect` 控制连接后是否保持暂停，`launchCompleteCommand` 控制初始化后的启动命令，不能将两者视为同一个开关。[C/C++ 配置说明](https://code.visualstudio.com/docs/cpp/launch-json-reference#_stopatconnect)

首次失败测试曾让 CPU 意外运行约 30 秒；随后已修复，并通过回读确认 EEPROM 未变化。这个经历说明，不能根据配置看起来正确就宣称运行控制已验收。

### 4.3 设置断点必须等符号就绪

`setupCommands` 中过早执行 `hbreak main` 时，符号尚未加载。当前改用 `postRemoteConnectCommands`，在符号加载并连接后设置该断点；GUI 新加的源码断点则由前端管理。

本次 ELF 的 `main` 断点地址为 `0x800061f2`。它是本次产物的地址，不是永久接口；源码、优化级别和链接布局变化后，应重新按符号或源码设置断点，而不是固定这个数值。

### 4.4 “出现异常”可能是断点分类问题

用户实际遇到过 GUI 显示“出现异常”，正文却只是 `Hit breakpoint 2 at 0x800061f2.`。底层 GDB 报告的是正常断点命中，前端却因预设断点来自原始 GDB 命令，默认将它归类为异常。

两个入口已设置 `unknownBreakpointHandling=stop`，把这类外部断点作为普通暂停；不会关闭真实信号异常的处理。修改配置后必须重新启动会话，旧会话不会自动加载新值。[MIEngine 处理逻辑](https://github.com/microsoft/MIEngine/blob/main/src/MIDebugEngine/Engine.Impl/DebuggedProcess.cs)

不能把所有异常都归为此问题：若出现其他信号、不同 PC、错误调用栈或固件陷阱，应另行排查。也不要通过关闭全部异常断点来消除提示。

### 4.5 断言必须覆盖用户实际看到的结果

早期自动测试只检查是否停到了 `main`、能否单步和读变量，漏掉了 GUI 停止分类。加强后的检查至少同时确认：

- 初始停在预期启动位置，连接后没有自行运行。
- 命中正确的函数、源码行和当前 ELF 对应的 PC。
- `stopped.body.reason` 为 `breakpoint`，而不是仅检查地址后忽略 `exception`。
- 单步后重新暂停，变量和内存读取有效，断开后服务端结束且目标保持暂停。

通过 DAP 启动真实适配器并连接实板，比静态检查 JSON 更强；但仍不等于整套 GUI、所有视图和复杂数据展示都已经验收。

## 5. 下载必须保留的保护

当前 Flash 基址为 `0x80000000`，首个非空 ELF 加载地址为 `0x80000400`，入口为 `0x80003000`。这些数值与当前 Flash XIP 布局关联；不要把 BIN 默认从 `0x80000000` 写入，也不要把 `main` 地址误当成烧录起始地址。

EEPROM 仿真保留区为 `[0x80080000, 0x80090000)`，共 64 KiB；[启动编号日志](启动编号日志初始化与烧录保留.md)为 `[0x80090000, 0x80092000)`，共 8 KiB。保护的不是“文件看起来较小”，而是 **ELF 物理加载范围，以及包含段间空洞、按扇区对齐的完整擦除跨度**。

现有下载事务按以下顺序执行：

1. 核对板级参数、唯一探针、权限、端口和本次确认。
2. 构建后冻结待写入的 ELF 副本，计算镜像摘要并检查加载/擦除范围。
3. 初始化并暂停目标，探测 Flash，检查容量与已确认参数一致。
4. 在写入前备份整个 EEPROM 和启动编号日志保留区，校验两份备份与当前 Flash 一致。
5. 使用 ELF 写入并校验固件，再独立校验两个保留区与备份一致。
6. 最终复位暂停；调试模式此时才输出 `DCU_DEBUG_READY`，允许前端连接。

端口开始监听不等于事务结束，不能用它替代 `DCU_DEBUG_READY`。镜像快照可以避免构建并发替换待写入文件，但调试符号仍不应在会话中途被重新生成。

本次额外执行了写入前后整片回读：Debug ELF 的 6 个非空加载段全部匹配，64 KiB EEPROM 和擦除范围外均为 0 字节变化。当时擦除范围为 `[0x80000000, 0x80058000)`；后续镜像必须重新计算，不能把这个结束地址当成固定白名单。

日常下载必备的是保留区备份、固件/保留区校验和审计留档；整片备份、独立完整回读适合首次迁移或重大变更验收，不能声称每次普通下载都会自动执行整片备份。

原始数据在 `artifacts/target/<UTC时间>/`，包括事务脚本、镜像快照、检查报告及相应备份。该目录不随 Git 提交，可能含设备身份和标定信息，应单独妥善保存。不要未经确认自动恢复旧 EEPROM，也不要使用整片擦除绕过镜像范围问题。

## 6. 快速排错

| 现象 | 优先检查与处理 |
| --- | --- |
| 提示新建调试配置或调试当前文件 | 是否打开 `Dcu_dev` 根目录，是否选择现有 `DCU:` 启动项 |
| USB 已识别但打不开探针 | 普通用户读写权限、其他会话占用、选中的探针序列号 |
| 3333 已占用 | 找到并正常结束对应调试会话，不重复启动服务端 |
| 扫描链全零或 Hart unavailable | 接线/电源、复位释放等待、提前 halt 回调；不要只看退出码 |
| 正常停在 `start.S` | 预期的连接后暂停，继续一次才到 `main` |
| `Hit breakpoint ...` 被显示为异常 | 核对 `unknownBreakpointHandling=stop`，结束旧会话后重启 |
| Flash 与 ELF 校验不匹配 | 使用下载后调试入口，不能继续拿不匹配的符号调试 |
| 找不到 `main` 或断点设置失败 | 检查 Debug ELF、符号是否加载、命令执行时机及源码路径 |
| 架构提示假定 x86_64 | 已知 C/C++ 元数据限制；核对实际 RISC-V GDB，不填虚假的 ARM/x86 架构来消除提示 |
| Flash 对齐擦除警告 | 对照镜像检查报告判断是否位于许可范围，不简单忽略全部警告或把所有警告都当失败 |
| 安装插件后构建目录或 Presets 改变 | 检查 HPM Explorer 是否接管工作区配置，对照 Git 差异再恢复 |

## 7. 环境精简与验收边界

### 7.1 可以精简的是重复职责

`dcu.py` 的 configure/build 部分只是转发标准 CMake，可以收敛到 CMake Tools 和 Presets；但不能因此删掉整个脚本，它还承担目标操作保护。将保护迁往 Tcl、CMake 或其他实现属于责任迁移，仍需测试，不是插件已经自动提供了这些能力。

SDK 的 CMake 配置会调用 Python，板卡解析使用 PyYAML；Jinja2 用于 IAR/SES 项目生成脚本，当前 Presets 已排除这两类生成。厂商 GDB 未启用 Python 脚本支持，则是另一件事，不能和 SDK 的 Python 依赖混为一谈。

`.tools/` 中的 GCC、GDB、OpenOCD 和运行库仍是实际执行工具。替代安装、版本、路径与运行库验证完成前，不删除它们。先精简入口和重复配置，保留可复现的工具来源、必要板级参数和保护职责。

HPM SDK Explorer 0.1.0 默认接管方式会改变 Presets/构建目录，J-Link 选项也不等同于本项目的 OpenOCD J-Link 路径。Cortex-Debug 外接受保护服务的基础 RISC-V 调试已通过，不代表 HPM 插件默认生成项或 ARM 专属功能已通过，详细差异见[扩展指南](开发扩展分类与使用指南.md)。

### 7.2 哪些结论可以保留

| 已有证据 | 不能由此推出的结论 |
| --- | --- |
| Debug/Release 完整构建、镜像检查通过 | 两种配置都已完成上板功能验收；本次实板下载主要验证 Debug |
| 实板下载、独立回读、EEPROM 不变 | 应用以后运行绝不会写 EEPROM；启动 SII 逻辑可能合法更新它 |
| 两个 C/C++ 入口及 Cortex-Debug 外接模式的基础调试通过 | 所有扩展默认配置、GUI 组合、SVD/RTOS/SWO 视图和复杂展示都兼容 |
| 断点分类修正后的不烧录复验通过 | 修正后又重复完成了一次下载；本次没有为了分类修正再次烧录 |
| 71 项离线测试和 CTest 通过 | 真实接线、电压、故障注入、冷启动、EtherCAT/CAN、实时性及物理停机都通过 |

CPU 暂停会让软件租约、反馈超时和 PDO 刷新一起停止，不是电机物理急停。探针报告的约 4.8 V VTarget 已向用户核对，但没有独立电气测量，不能当作电平验收结果。

迁移环境、更换探针、升级 SDK 或修改链接布局后，至少重新检查构建、镜像与符号一致性、复位/暂停、真实断点停止原因、下载回读及保留区。对失败路径、脱离调试器冷启动、控制业务和实时性另行验收，不把“基础链路打通”扩大成整机验收完成。
