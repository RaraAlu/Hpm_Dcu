# DCU 环境依赖与外部资源准备

核对日期：2026-11-13。适用范围：Ubuntu 24.04 x86_64 上的当前 `Dcu_dev` 工程，使用本地化 HPM SDK、CMake Presets、厂商 RISC-V 工具链和 J-Link JTAG。

本文是新机器搭建和离线迁移的准备入口。日常操作见[编译调试下载经验总结](编译调试下载经验总结.md)，扩展详细用法见[开发扩展分类与使用指南](开发扩展分类与使用指南.md)。

**先区分两个事实：克隆源码不等于恢复开发环境，安装编辑器扩展也不等于安装了编译器、GDB 或下载保护逻辑。** 本页不会要求删掉系统 Python、项目保护脚本或已验证的底层工具。

## 1. 哪些资源已经随仓库提供

| 资源 | 是否随 Git 提供 | 恢复方式与边界 |
| --- | --- | --- |
| 业务源码、SSC 栈和现有协议生成物 | 是 | 使用当前提交版本；普通构建不运行协议生成脚本 |
| 本地化 HPM SDK 1.12.1 | 是 | 位于 `hpm_sdk_localized_for_hpm5e00evk/`，已含自研板适配，不能用原厂 SDK 直接覆盖 |
| Presets、编辑器配置、OpenOCD 配置与保护脚本 | 是 | 保留现有入口；不用插件默认生成配置直接替换 |
| 工具下载地址与摘要 | 是 | 以[工具锁文件](../../tools/toolchain.lock.json)为准 |
| `.tools/` 安装目录和安装包缓存 | 否 | 另行下载或迁移缓存，再由 `bootstrap` 恢复 |
| 系统软件、Python 包、VS Code 和扩展 | 否 | 在目标主机安装；仅复制仓库不会获得这些依赖 |
| `config/board.example.json` | 是 | 未确认的板级模板，不授权硬件操作 |
| `config/board.local.json` | 否 | 针对实际板卡和接线单独核对，不能照搬另一台机器的确认状态 |
| `build/`、编辑器缓存 | 否 | 在新位置重新构建，避免迁移带绝对路径的旧缓存 |
| `artifacts/target/` 中的 Flash/EEPROM 备份与日志 | 否 | 按设备身份另行妥善保管；不是普通构建必需资源，不放进公共源码包 |

现有生成物与历史副本的维护关系见[生成文件与来源清单](生成文件与来源清单.md)。生成链尚有已知异常，不能把它们当成随时可重建的缓存删除。

## 2. 主机与系统依赖

### 2.1 平台和版本

| 项目 | 当前要求或本机核对值 |
| --- | --- |
| 操作系统与架构 | Ubuntu 24.04、`x86_64`；APT 包的架构名称为 `amd64` |
| CMake | 当前 Presets 要求至少 3.25，本机为 3.28.3 |
| Python | 使用系统 Python 3.12；`bootstrap.py` 明确要求至少 3.12，本机为 3.12.3 |
| PyYAML | 普通 SDK 配置需要，本机为 6.0.1，对应 Ubuntu 包 `python3-yaml` |
| 基础命令 | Bash、Git、coreutils；工具恢复还使用 `curl`、CA 证书和 `dpkg-deb` |

CMake 门槛来自[当前 Presets](../../CMakePresets.json)，Python 和宿主平台限制来自[工具恢复脚本](../../scripts/bootstrap.py)。不要仅按根 CMake 文件较低的最低版本判断当前 Presets 是否可用。本机版本是观测值，不代表所有系统包都已被项目锁定。

当前恢复脚本会拒绝其他系统版本、非 Linux 或非 x86_64 主机；这不等于 HPM 工具完全不支持其他平台，而是本项目没有提供那些平台的已验证恢复流程。

### 2.2 联网新主机安装清单

以下命令在需要搭建的新主机执行，会修改该主机的系统软件；不是每次开发都要执行。普通编译和 `bootstrap` 不使用 sudo。

```bash
sudo apt-get update
sudo apt-get install --no-install-recommends \
  bash coreutils git cmake python3 python3-yaml curl ca-certificates dpkg \
  libc6 libgcc-s1 libstdc++6 zlib1g libexpat1 libmpfr6 libgmp10 \
  libncursesw6 libtinfo6 libusb-1.0-0 libudev1 libcap2 udev
```

这些运行库依据本机对 GCC、编译器内部 `cc1`、GDB、链接器、Ninja 和 OpenOCD 的 `ldd` 结果整理；APT 还需处理它们的传递依赖。大部分库在 Ubuntu 桌面版已存在，精简系统不能只准备编译器压缩包。

`dpkg` 提供 `dpkg-deb`，用于把锁定的 Ninja/HIDAPI 包解压到项目目录，不是把这两个项目包安装进系统。`udev` 用于后续 USB 权限配置；本步骤不连接或复位目标。

安装后核对：

```bash
uname -m
cat /etc/os-release
cmake --version
python3 --version
python3 -c 'import yaml; print(yaml.__version__)'
```

如果激活了虚拟环境或自定义 Python，先核对 `command -v python3`。APT 安装的 `python3-yaml` 对应系统解释器，不保证在任意虚拟环境中可见；必要时退出虚拟环境或使用 `/usr/bin/python3`，不要通过 `sudo pip` 改写系统 Python。

## 3. 必须准备的锁定工具包

以下四项应使用[锁文件](../../tools/toolchain.lock.json)中的准确文件名、下载 URL 和 SHA-256。不要把同名的新版本包放进缓存冒充旧包。

| 用途 | 缓存文件名 | 恢复位置 |
| --- | --- | --- |
| GCC 13.2.0，含配套 GDB 13.2 | `rv32imac_zicsr_zifencei_multilib_b_ext-linux.tar.gz` | `.tools/hpm-gcc-13.2.0/` |
| HPM OpenOCD `hpm_xpi_v0.3.0` | `openocd-linux-hpm-0.3.0.tar.gz` | `.tools/openocd-hpm-0.3.0/` |
| Ninja `1.11.1-2` | `ninja-build_1.11.1-2_amd64.deb` | `.tools/host/` |
| HIDAPI `0.14.0-1build1` | `libhidapi-hidraw0_0.14.0-1build1_amd64.deb` | `.tools/host/` |

GCC 和 OpenOCD 分别来自 [HPMicro GCC 发布页](https://github.com/hpmicro/riscv-gnu-toolchain/releases/tag/2023.10.18)和 [HPMicro OpenOCD 发布页](https://github.com/hpmicro/riscv-openocd/releases/tag/hpm_xpi_v0.3.0)。Ninja/HIDAPI 的固定 Ubuntu 下载地址在锁文件中。GCC 摘要记录自首次官方 HTTPS 下载，不是厂商签名认证；不要扩大其来源保证。

联网时，以下命令缺包则下载；已有缓存则先校验摘要，再安装到 `.tools/`：

```bash
python3 scripts/dcu.py bootstrap
```

`bootstrap` 不安装 CMake、系统 Python、PyYAML 或系统运行库，不修改 shell 配置，也不配置 USB 权限。它可能替换锁文件指定的本机工具安装目录，不应拿它管理自行修改过的工具副本。

当前调试链路是厂商 GDB 加厂商 OpenOCD 的 J-Link 驱动，**不要求额外安装 `gdb-multiarch`、SEGGER J-Link GDB Server、SES 或系统 x86 编译器**。厂商 GDB 未启用 Python 脚本支持，与 SDK 构建仍需要 Python 是两件不同的事。

OpenOCD 需要通过 `scripts/openocd.sh` 包装启动，包装脚本会补充本地 HIDAPI 的库搜索路径。裸运行 OpenOCD 或裸用 `ldd` 时出现 HIDAPI 未找到，不代表包装入口一定失效；其他宿主库仍须安装。

## 4. 编辑器与扩展资源

命令行构建不要求安装 VS Code。需要沿用 GUI 构建和调试时，准备 [VS Code Linux x64 安装包](https://code.visualstudio.com/docs/setup/linux)，以及下面两个核心扩展：

| 扩展 | 用途 | 当前盘点版本 |
| --- | --- | --- |
| `ms-vscode.cmake-tools` | 使用现有 Presets 配置和构建 | 1.25.10 |
| `ms-vscode.cpptools` | 代码索引与现有 `cppdbg` 调试入口 | 1.35.6 |

本机编辑器版本为 1.145.3；它是本次盘点值，不是已经锁定的兼容性范围。新主机复用版本后仍需复核功能，不能仅凭版本号宣称 GUI 验收通过。

联网新主机可以按本次盘点版本安装，不要求在已有环境中重复执行或降级：

```bash
code --install-extension ms-vscode.cmake-tools@1.25.10
code --install-extension ms-vscode.cpptools@1.35.6
code --list-extensions --show-versions
```

VS Code CLI 支持用 `扩展ID@版本` 指定版本，也支持传入 VSIX 路径，见[官方 CLI 说明](https://code.visualstudio.com/docs/configure/command-line#_working-with-extensions)。扩展安装后可能有自动更新策略；迁移验收时应重新记录实际版本，不把安装命令当作持续锁版本机制。

HPM SDK Explorer、Cortex-Debug、内存/外设/RTOS 视图、串口和曲线工具按需准备。版本、依赖和风险以[扩展分类指南](开发扩展分类与使用指南.md)为准，不能因为新装 HPM 扩展就让其接管当前 Presets 或生成另一套下载配置。

## 5. 离线资源清单

### 5.1 断网之前需要带齐什么

| 资源组 | 必须准备的内容 |
| --- | --- |
| 完整项目 | 包含本地化 SDK 的完整源码或 Git 仓库，记录所用提交；保留符号链接和可执行权限 |
| 主机依赖 | 第 2 节系统包及其适用于 Ubuntu 24.04 amd64 的完整依赖闭包，或已经验证具备这些包的系统镜像 |
| 工具缓存 | 第 3 节四个原始安装包，放在目标工程的 `.tools/cache/`，附带同一版本的锁文件 |
| 编辑器 | 如果使用 GUI，准备 Linux x64 的 VS Code 安装包及其系统依赖 |
| 扩展 | 两个核心扩展的指定版本 VSIX；所选可选扩展及它们的依赖也需带齐 |
| 板级资料 | 实际板卡、Flash、探针和接线信息；重新核对本机配置，不直接迁移已确认标志 |
| 设备数据 | 如需迁移历史 EEPROM/Flash 备份，按设备单独受控存放，不混入公共安装包 |

不能只在已有完整环境中执行几次 `apt download`，就认定拿到了干净机器所需的全部依赖；也不能只带四个锁定包便声称系统环境完整。应在相同版本和架构的主机上解析依赖，并在目标基线的干净测试系统中断网复演安装。

资源包应记录来源、版本、架构及 SHA-256。项目锁文件只覆盖四个工具包，不覆盖系统镜像、全部 APT 包、编辑器和 VSIX；这部分要随离线交付物另行保存清单，不能称为项目已有的完整环境锁。

### 5.2 工具缓存的只读预检

在项目根目录执行下面的检查。缺包或摘要错误立即停止，不尝试联网；全部通过后再执行 `bootstrap`。

```bash
python3 - <<'PY'
import hashlib
import json
from pathlib import Path

lock = json.loads(Path("tools/toolchain.lock.json").read_text())
for asset in lock["assets"]:
    package = Path(".tools/cache") / asset["file"]
    if not package.is_file():
        raise SystemExit(f"Missing offline package: {package}")
    with package.open("rb") as stream:
        digest = hashlib.file_digest(stream, "sha256").hexdigest()
    if digest != asset["sha256"]:
        raise SystemExit(f"Checksum mismatch: {package}")
    print(f"PASS {package}")
PY
```

当前 `bootstrap` 没有独立的离线开关；缓存缺失时仍会尝试下载。因此离线迁移要先做上述预检，不能把网络超时当作正常安装步骤。摘要错误的缓存不会被自动覆盖，应重新从可信来源取得对应包，而不是修改锁文件绕过检查。

### 5.3 扩展 VSIX 的准备与安装

联网准备机在扩展视图搜索准确 ID，使用 `Download Specific Version VSIX` 或 `Download VSIX` 获取包；选择与目标匹配的 Linux x64 平台变体，并核对指定版本。官方流程见[扩展下载说明](https://code.visualstudio.com/docs/configure/extensions/extension-marketplace#_can-i-download-an-extension-directly-from-the-marketplace)。

复制扩展清单文本不是下载扩展；仅复制 `~/.vscode/extensions/` 目录也不是本项目验证过的安装恢复方式。扩展包之外可能还有平台组件或扩展依赖，需要在断网前完成安装和实际激活检查。

离线主机可以在扩展视图选择 `Install from VSIX...`，或把下面的占位路径替换为实际已取得的 VSIX 文件，对每个包分别安装：

```bash
code --install-extension "/实际路径/下载得到的扩展.vsix"
code --list-extensions --show-versions
```

不要为了安装失败而关闭扩展签名验证或改装来历不明的包。上述命令来自[官方 VSIX 安装说明](https://code.visualstudio.com/docs/configure/extensions/extension-marketplace#_install-from-a-vsix)，但本次文档补充没有实际下载或安装 VSIX，也没有产出完整离线交付包。

## 6. 新机器恢复顺序

### 6.1 先完成不访问目标板的步骤

1. 恢复完整项目，在 `Dcu_dev` 根目录工作。新路径下重新生成 `build/`，不要复制旧 CMake 缓存当作环境恢复。
2. 按第 2 节安装并核对主机依赖。离线时先准备完整系统包或镜像，不执行需要联网的更新步骤。
3. 准备第 3 节工具包；离线时先运行第 5.2 节预检，再运行 `python3 scripts/dcu.py bootstrap`。
4. 执行以下检查、构建和镜像保护检查；它们不初始化、复位或烧录目标。

```bash
python3 scripts/dcu.py doctor
python3 scripts/dcu.py test
python3 scripts/dcu.py build --preset hpm-debug
python3 scripts/dcu.py build --preset hpm-release
cmake --build --preset hpm-debug --target check-image
cmake --build --preset hpm-release --target check-image
ctest --preset hpm-debug
```

没有接探针或尚未创建本机板级配置时，`doctor` 的相应 WARN 是预期提示，不妨碍普通编译；不能为了清除警告而随手把确认字段改为 `true`。`doctor` 不检查所有系统包或整个 SDK 构建链，因此还必须检查导入 PyYAML、真实构建和镜像检查的结果。

5. 需要 GUI 时再安装第 4 节编辑器和扩展，打开 `Dcu_dev` 根目录，沿用仓库内现有任务和启动项。不要手动设置全局 `HPM_SDK_BASE` 或用插件覆盖本地化 SDK。

构建输出与镜像检查通过只代表该离线阶段成功。`ninja: no work to do` 是增量结果，不代表重新全量编译；既有 SSC 编译告警和生成链问题也不能因此写成已修复。

### 6.2 再准备硬件权限和板级参数

仅编译不需要目标板；调试和下载还需准备实际控制板、逻辑电源、J-Link 和 USB/JTAG 线，核对 VTref、GND、TCK/TMS/TDI/TDO 及 nSRST。保持电机动力隔离，并准备独立急停措施。

新主机尚无本机配置时，可以从模板创建；`-n` 防止覆盖已有配置：

```bash
cp -n config/board.example.json config/board.local.json
```

创建后仍保持模板的未确认状态。实际核对芯片、Flash 容量和扇区、探针、复位接线后才填写对应参数和确认状态；不能因另一块板曾通过就直接复制其 `true` 字段。当前 1 MiB/4 KiB 默认参数适用于已核对的现有配置，不是对任意板卡的保证。

USB 读写权限不足时，在普通用户本机终端执行现有向导：

```bash
bash scripts/setup-usb.sh
```

向导通过 sudo 安装、重载受限的 udev 规则，并要求人工重新插拔探针；不会执行 JTAG 初始化、复位或烧录。不要用 sudo 启动整个 VS Code，也不把 USB 设备设为全员可写。规则和实际 USB ID 的匹配范围见[现有规则](../../config/60-dcu-jlink.rules)。

到此仍未授权任何目标操作。之后按[经验总结的上板步骤](编译调试下载经验总结.md#31-每次上板前的条件)单独确认，保留每次 `RESET_TARGET` 和镜像/EEPROM 保护；本页不把硬件命令混入环境安装步骤。

## 7. 按需资源与非必需项

| 资源 | 何时才需要 |
| --- | --- |
| Jinja2，Ubuntu 包 `python3-jinja2` | SDK 的 IAR/SES 工程生成；当前 Presets 已排除这两类生成，普通构建不因此强制安装 |
| Node.js | 恢复、检查协议 JS 生成链时；普通编译不使用它，现有脚本语法异常不会因安装 Node.js 自动修好 |
| PowerShell 运行时、Beckhoff SSC/ET9300 工具 | 恢复 SII 再生成时；安装 PowerShell 编辑器扩展不等于安装这些运行依赖，流程仍须单独验收 |
| USB 转串口与匹配电平的线缆 | 读取固件控制台日志；J-Link 枚举成功不代表已具备串口 |
| EtherCAT 主站、CAN/CAN-FD 分析设备 | 控制业务、协议和时序联调，不是固件编译及基础 JTAG 调试的必需资源 |
| SVD、内存/外设/RTOS 辅助扩展 | 对应视图功能；当前裸机固件不因安装 RTOS 扩展就有任务列表 |

当前流程不依赖 ROS2、云端编译服务或新的 Python 虚拟环境。工具、主机依赖和所需扩展备齐后，现有本地构建和基础目标访问流程不要求持续联网；完整断网恢复是否成功仍以目标机器复演为准。
