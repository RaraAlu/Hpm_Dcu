# 四轴旧回显限时复现定位

实板限时复现只运行了一次。RK 仍用上一轮同一生产包（SHA-256 `df550cbe878b11ff56c584915d95f25b1bbec180bcbdc2623c325524e33c52a7`），由 build 启动脚本运行 DriverModule。Python 仅发 ROS 命令、读前后计数并监督退出。HPM 在五轴生产固件上增加分段时间记录，未改 CAN 的 100 µs 间隔或 SM3 截止时间。

生产线程约 8.7 秒后退出：提交 4347 拍，N+1 已匹配 4345 拍，调度漏拍 0；N+1 期望 6164，实读 6163。上一次通宵尝试同样返回旧回显，但上次的 HPM 现场是四轴缺失掩码归零、TX_LATE，这次不能当作它的同因复现。

复现后 RK 主站已 Idle/inactive；从站未回 PREOP，ESC 的 AL 状态直接回读为 0x0008，AL 状态码 0，IgH 列表标为 OP/E。结束后的计数 SDO 上传失败，所以没有逐轴 TX 增量可报。没有重发、补测或故障后复位。

普通 JTAG halt 无法访问 CPU hart（DMSTATUS=0x00400ca2），改用 SDK 的调试系统总线读物理内存。处理器本地 DLM 的系统地址别名 0x011e0000 可直接读流水线：槽内线序号 6164、epoch 4408，SM2 就绪 88631520 µs，Sync0 锁存 88631769 µs。本拍 cyclic_epoch=4408，cyclic_missing=0x18（按生成的五轴设备顺序对应 CAN2 ID 3、4），published=0，上一发布 epoch=4407，faults=0。这是最后保留的流水线处理状态，不表示两个电机均未发送或没有回包。

MCAN2 的 TX 队列、TX 完成事件队列、RX FIFO 均空，三者下一放入位置均为 7。对应最近一个槽 6，在发送、发送完成事件和接收的 Message RAM 中 ID 均为 3；最近一组顺序为 1、2、3。故控制器已发出 ID 3 并收到了 ID 3 的 CAN 帧，而流水线还没有将 ID 3 从缺失掩码清除。环形区槽 7 的 ID 4 属于旧记录，不是本轮已完成的证据。硬件头本身不携带 EtherCAT 命令号，关联依据是冻结的队列下标与流水线最后一拍。

新增的阶段记录位于可缓存 AXI SRAM。CPU 无法 halt，此时直接通过系统总线读到的槽序号落后且不一致，不能以旧 cache line 判断 6164 的打包或 ESC 提交时间。现有证据能定位到本次 CAN2 服务在一拍中途未正常推进，不能确定 CPU 停止响应的指令或硬件原因。上一次故障则已排除 SM2 未锁存或反馈一直缺失，详见[原故障现场补读](2026-11-23-CAN2四轴通宵回环首次运行.md)。
