# 设备抽象基础验证记录

日期：2026-11-13。需求：当前只有一种电机，先为后续不同电机和 IMU 准备可替换代码。基线提交为 `a8b7803`，本文记录其后的设备抽象改动与离线验证，实际提交以 Git 历史为准。全过程只做离线操作，没有连接、复位、暂停、烧录或运行目标板。

## 改动边界

- 电机周期命令验证、启动命令编码、周期发送编码和周期反馈解码，已通过 `MotorDevice` 与 `MotorDriver` Interface；唯一生产实现是现有 ENCOS，注册值仍为 `0x8000`。
- 公共模型不依赖 SDK、SSC、生成对象字典或 EtherCAT 类型。产品绑定负责旧线格式转换，配置放在模块内 `cfg/`，未知注册项拒绝而不是回退到 ENCOS。
- IMU 有可测试的非阻塞初始化、样本/能力校验、有效性、错误恢复和单调时间过期模型，以及未接入实现；没有具体芯片驱动、主循环采集或旧 PDO 发布适配。
- 保留原电机状态机、启动握手、CAN 调度、厂商参数事务和停止语义。坏反馈改成完整校验成功后才提交状态；通用 `int32_t` 电流向旧 `int16_t` 转换前增加范围检查，避免窄化回绕。

接口、单位、生命周期和未来接入步骤见[设备驱动扩展与接入规范](../当前说明/设备驱动扩展与接入规范.md)。

## 基线与构建

修改前保存源码、64 个原文件的 SHA-256、Debug/Release ELF 和编译数据库至本机忽略目录 `artifacts/device-abstraction-baseline.6tVmK9/`；最终对比报告为该目录的 `comparison.json`。这些是本机验证材料，不是随仓库交付的外部依赖。

为避免 SDK 静态库归档残留旧成员，保存基线后先清理对应默认构建，再执行 `cmake --fresh --preset ...`；最终增量构建也成功。执行入口：

```bash
python3 scripts/dcu.py test
cmake --build --preset hpm-debug
cmake --build --preset hpm-release
ctest --preset hpm-debug
```

| 检查 | 结果 |
| --- | --- |
| 宿主离线回归 | 原 55 项加新增 16 项，共 71 项通过 |
| CTest | `devtools-offline` 聚合入口通过，执行同一组宿主测试，不重复计算为额外 71 项 |
| 设备测试编译 | C++17、禁用异常和 RTTI；`-Wall -Wextra -Werror -pedantic-errors` 通过 |
| 未定义行为检查 | 两个原生测试程序以 `-fsanitize=undefined -fno-sanitize-recover=all` 重编译，16 个设备用例全部通过，无诊断 |
| Debug / Release | 两套默认固件均编译、链接成功，镜像保护检查通过 |
| 编译数据库 | 原 70 个编译单元全部保留，新增 4 个，共 74 个；其中 6 个为 C++ |
| 离线 GDB | 可定位当前 `main.c`、`motor_control_init` 和 `MotorDevice::encode`；没有连接远程目标 |

新增编译单元为产品驱动绑定、电机公共模型、ENCOS 驱动实现和 IMU 公共模型。入口、板级、CAN、SSC 和生成存储保留 C；未改变语言边界或重写底层中断。构建仍有原 SDK/SSC 警告，不能把成功构建描述为全工程零警告。

## 测试范围

新增测试位于 [设备测试入口](../../tests/host/test_device_abstractions.py) 及其 [原生测试目录](../../tests/host/devices/)：

- 无厂商头的测试驱动替换：不同命令/反馈实现使用同一个公共 Interface；未绑定、不支持模式、非法帧和失败输出均被检查。测试替身不加入生产注册。
- 真实 ENCOS 适配：1000 个有效命令覆盖 5 种控制模式，与原编解码器逐字节比较；256 组周期反馈比较旧状态结构体，包括已有字段和独立功率有效位。
- 配置校验、未知型号拒绝、注册方言在首次 Apply 前可识别、多轴实例隔离、无主动停止能力，以及坏反馈不污染旧状态、电流/故障码窄化溢出拒绝。公共模型可接受部分反馈，产品绑定则拒绝缺少位置/速度/电流的周期快照，防止旧就绪逻辑误判。
- IMU 未接入不能发布有效样本；初始化可重试；空读不刷新时间；样本在最大年龄边界失效；非有限数据、非法字段、非单位四元数、错误时钟域、I/O 错误及时间回退被处理。

差分测试基于复用的原编解码器，另保留原 8 项协议与 C/C++ 互操作测试中的固定报文和布局检查。这只能证明已覆盖样例及契约，不是独立厂商协议认证，也没有覆盖完整 SSC 状态机、参数事务端到端或调度时序。

均未触碰 64 KiB 保留 EEPROM 区。检查仍使用原默认 1 MiB Flash、4 KiB 扇区参数，`hardware_geometry_verified=false`；本轮没有实测器件几何信息或读取目标 Flash。新代码导致映像内容、链接地址和初始数据变化，不宣称整个 ELF/BIN 与基线相同。IMU 尚无运行时调用，链接器可能裁掉未引用代码，不能将当前增量当作未来真实采集接入的完整成本。

通过 Git 差异核查，`firmware/generated/`、`protocol/ethercat/`、BSP、SDK/SSC、调试及下载保护配置、脚本、根构建入口和预设未改；ESI/SII、三档 PDO、对象字典布局及现有 C 调用入口未改。SDK 的 `start.S` 调用 `__libc_init_array`，链接脚本保留初始化表；这是源码层确认，不等于新 C++ 映像已经冷启动验收。

## 尚未验收

1. 没有第二种实物电机或 IMU 型号，不能宣称已经完成多厂商硬件适配。
2. 当前传输仅容纳 8 字节载荷；旧入口仍约束标准标识符、通道格式和最小长度。新驱动还必须核对启动握手、地址、查询与停止规则，不能只新增注册项。
3. 当前停止仍是取消/禁止后续控制发送，不等于失能、零力矩、制动或物理急停。
4. 新映像的冷启动、构造初始化、GUI 调试、EtherCAT/CAN 联调、反馈超时、故障注入、真实停机、最坏耗时及栈使用尚未上板验收。历史授权和旧纯 C 映像结果不自动覆盖本轮。
5. 控制权、租约、厂商事务、调度、长关中断区和 CAN 定时反向依赖仍待后续独立测试与解耦；本轮没有扩大到完整控制架构重写。
