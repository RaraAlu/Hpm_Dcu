## 基线与文件保留

起点是 `c5ede57` 加已有未提交的 C++/文档改动，不把 HEAD 本身称为已包含全部语言迁移。移动前保存工作区源码快照、4702 个现存受控或待纳入文件的 SHA-256、两种 ELF 及 Debug 编译数据库；未用 reset、stash 或新提交覆盖用户改动。

本机证据位于被忽略的 `artifacts/layout-baseline.EmUAeY/`：`source.tar.gz`、`source-manifest.json`、`moves.json`、`source-comparison.json`、`build-comparison.json` 和旧 ELF。源码包不含 `.tools/`、构建目录、硬件证据目录或大型编辑器数据库；这份本机快照不是需要提交的第三方依赖。

迁移后核对结果：

- 4668 个迁移的源文件/资料均能找到目标，未丢失；其中 4661 个保留原字节。
- 7 个被移动文件有必要的内容调整：入口测试头条件包含、三个 Python 测试的根目录/包含路径、SII 脚本路径，以及两份原评估板 RST 的图片引用。
- 电机 CPP/H、板级 C/H、SSC 栈核心、SDK 核心、生成头/存储、ESI、SII 和 EEPROM 数组均与本轮迁移前字节一致。先前 C/C++ 兼容补丁保留，不再次运行生成器。
- 另有一个既存 SDK Python 缓存随目录迁移，属于忽略的生成物，不计入源文件摘要；没有为它放宽忽略规则。

新局部 CMake、根 CMake、脚本测试发现和当前文档的更新单独审阅，不把这些修改伪装成纯移动。

## 生效目录与源码集合

CMake 配置实际报告：

```text
Board (custom board): dcu_hpm5e31 from .../firmware/bsp
hpm_sdk: 1.12.1 (.../third_party/hpm_sdk)
GNU ld linker script: .../third_party/hpm_sdk/soc/HPM5E00/HPM5E31/toolchains/gcc/flash_xip.ld
```

`board`、`clock`、`pinmux` 只从 `firmware/bsp/dcu_hpm5e31/` 编译；SDK 内旧评估板目录已移出。板卡 YAML 仅改文件名，硬件字段未改；`BOARD_NAME` 的旧日志文字保留，不能拿它判定外部 BSP 未生效。

两种默认配置各有 70 个编译单元，与迁移前数据库经过路径映射后的集合完全一致，无增加或缺失。只有下列两个源使用 `g++`、`-std=c++17`、`-fno-exceptions`、`-fno-rtti`：

```text
firmware/app/motor/motor_control.cpp
firmware/protocols/encos/encos_motor.cpp
```

其他 C 与启动汇编保持各自语言。默认数据库不含 `legacy/`、原旧数字量示例或 CAN LED 诊断源码。SSC 产品头和生成头已移出栈核心目录，没有旧副本通过引号包含遮蔽。

## 离线验收

| 项目 | 结果与范围 |
| --- | --- |
| Debug、Release | 清理旧对象后从新 CMake 缓存完整配置、编译和链接通过；原 SSC 告警保留 |
| CLI 测试 | 47 项通过：35 项保护/工具、8 项协议/互操作、4 项布局/中文命名 |
| CTest | `ctest --preset hpm-debug` 通过一个聚合入口，实际执行上述 47 项，不把一个入口计为一项业务测试 |
| 保留区检查 | Debug 擦除跨度 `[0x80000000, 0x80058000)`；Release 为 `[0x80000000, 0x80053000)`；均不触及 EEPROM `[0x80080000, 0x80090000)` |
| 离线 GDB | 新 Debug ELF 能解析 `firmware/app/main.c`、电机 CPP 源码行；未连接远程目标 |
| OpenOCD 配置 | 使用新 SDK 搜索路径解析后仅执行 `shutdown`，通过；没有执行 `init` 或打开探针 |
| CAN LED 可选项 | 独立 `build/hpm-can-led-check/` 中配置 ON，编译/链接与镜像检查通过；宏 `CONFIG_CAN_LED_TEST=1` 确实进入入口编译。默认 Debug/Release 仍为 FALSE，未运行诊断 |
| 异常生成链 | 三个归档 JS 的 `node --check` 和归档 JSON 解析仍失败；与既存原字节异常一致，未尝试猜修 |

CAN LED 清单现在同时定义固件宏，修正原先只有 CMake 选源、入口宏却默认 0 的不同步问题；这是显式启用诊断时的行为修正，不是默认控制逻辑变更。测试是阻塞式诊断，不能因编译通过就带电运行。

主要验收入口：

```bash
python3 scripts/dcu.py test
cmake --fresh --preset hpm-debug
cmake --build --preset hpm-debug
cmake --build --preset hpm-debug --target check-image
cmake --fresh --preset hpm-release
cmake --build --preset hpm-release
cmake --build --preset hpm-release --target check-image
ctest --preset hpm-debug
```

本轮在移动前已经对两个旧构建执行 `clean`。以后复演路径迁移时也要先保存 ELF 并清理旧对象，不能只靠 `--fresh` 处理 SDK 静态归档残留。

## 二进制差异

下表来自交叉 `size`，基线是**目录迁移前的 C++ 映像**，不是先前纯 C 版本。

| 配置 | 时点 | text 字节 | data 字节 | bss 字节 |
| --- | --- | ---: | ---: | ---: |
| Debug | 迁移前 | 295456 | 49808 | 111432 |
| Debug | 迁移后 | 295424 | 49808 | 111424 |
| Release | 迁移前 | 277104 | 49808 | 111424 |
| Release | 迁移后 | 277104 | 49808 | 111432 |

两种配置各自 1073 个 data/bss 符号的名称、类别和大小集合前后完全一致，没有新增或改变状态对象。局部 CMake 注册顺序调整后，对象链接顺序、地址和段填充变化；据此可解释 bss 总量的 8 字节差异。Debug text 的小幅差异发生在重排后的链接结果中，不能把整个加载映像都称为字节等同，也不能只归因于调试信息。

固件入口和 Flash 保留边界不变，协议编解码固定样例与全部布局断言通过；这些证据仍不是执行时间、堆栈峰值、并发行为或物理停机验收。
