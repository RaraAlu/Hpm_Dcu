## 3. 发现的问题与修正

### 3.1 nSRST 复位时序

首次连接可识别目标并读取备份，但 `reset init`、`reset halt` 出现 `JTAG scan chain interrogation failed: all zeroes` 和 `Hart 0 is unavailable`。OpenOCD 最终退出码仍为 0，因此不能仅按进程成功判断复位通过。

最小反馈环为：加载实际项目配置，执行 `init`、`reset init`、读取 PC、`reset halt`、再次读取 PC、`shutdown`；同时检查日志无 Error/Warn，两个 PC 均为 `0x80003000`。

| 对比条件 | 结果 |
| --- | --- |
| 原配置，复位释放等待为 0 | 扫描链错误和 Hart unavailable，失败 |
| 仅增加 500 ms 等待 | 扫描链错误消失，但 Hart unavailable 仍在，失败 |
| 在上一条件下清空 `reset-deassert-pre` 回调 | 无前述错误，两次 PC 正确，通过 |
| 将修正写入项目配置，再运行两个独立会话 | 4 次复位均无前述错误、PC 正确，通过 |

厂商 J-Link 配置本来就包含 `adapter srst delay 500`。项目现已补回这一设置，并在加载 SoC 配置后清空 SDK 的 `reset-deassert-pre` 回调。该回调在硬件 nSRST 尚未释放时调用 `arp_halt`，与本次板级复位路径不匹配。修正只在项目配置覆盖，不修改 SDK 文件，也不取消 `srst_only`。复位释放等待的含义见 [OpenOCD 官方说明](https://openocd.org/doc/html/Reset-Configuration.html)。

### 3.2 C/C++ 自动继续与断点时机

实际适配器测试证明，原有 `launchCompleteCommand=None` 不能单独保证连接后暂停。原配置未设置 `stopAtConnect`，适配器自动发送继续命令；原 `setupCommands` 中的 `hbreak main` 又早于符号加载，未成功保留预期断点。

首次失败测试中，CPU 曾运行约 30 秒，之后通过调试器中断并断开，服务端执行 halt。没有把这次失败记为通过，也没有隐去应用曾运行的事实。最终独立回读证明 EEPROM 未变化，不需要也没有执行恢复写入。

两个现有启动项均已修正：

- 增加 `stopAtConnect=true`，仍保留 `launchCompleteCommand=None`。
- 把 `hbreak main` 从 `setupCommands` 移到 `postRemoteConnectCommands`，待符号与连接就绪后再设置。
- 保留镜像校验、备份、单次确认、硬件断点和断开 halt 策略。

`stopAtConnect` 与默认继续行为的区别由 [C/C++ 官方配置说明](https://code.visualstudio.com/docs/cpp/launch-json-reference#_stopatconnect)核对，并由本次实际 DAP 日志验证。

新增复位配置回归测试、加强启动暂停配置测试，均先在旧配置上观察到失败，再应用修正。它们防止配置回退，不代替真实硬件时序验收。

## 8. 断点异常标签后续修正

用户 GUI 反馈：显示“出现异常”，正文为 `Hit breakpoint 2 at 0x800061f2.`。留存的两个 C/C++ 通过会话中均可复现同一现象：底层 GDB 报告 `reason="breakpoint-hit"`、`func="main"`，但 DAP 发出的 `stopped.body.reason` 却是 `exception`。这不是关于固件崩溃的证据，而是实际遗漏的 GUI 分类问题。

根因是 `postRemoteConnectCommands` 中的 `hbreak main` 属于原始 GDB 命令创建的外部断点，未在前端断点管理器登记。本机 C/C++ 1.35.6 的配置声明确认 `unknownBreakpointHandling` 默认是 `throw`，可选 `stop`；[MIEngine 的对应分支](https://github.com/microsoft/MIEngine/blob/main/src/MIDebugEngine/Engine.Impl/DebuggedProcess.cs)对前者报告异常，对后者报告普通断点停止。它不改变后续信号异常分支。

修正保持原有 `main` 预设断点及暂停策略，只对两个现有启动项增加：

```json
"unknownBreakpointHandling": "stop"
```

没有修改异常过滤器、继续执行策略或固件，也不需要重新烧录。已经打开的调试会话不会动态使用这项新配置。

新增配置回归测试先在旧配置上失败，修正后 35 项离线测试及 CTest 通过。专用 DAP 测试客户端现已加强为：命中 `main` 时必须断言 `stopped.body.reason == "breakpoint"`，不能只检查源码行和 PC。对旧协议记录执行该断言会如预期失败，避免把原有日志错误地当作停止分类已通过的证据。

用户结束当前 GUI 会话、确认继续隔离电机动力并允许不烧录复验后，已运行加强后的 DAP 测试客户端。结果：同样命中 `ecat.c:31`、`0x800061f2`，本次 `stopped.body.reason` 为 `breakpoint`，不再是 `exception`；单步、变量和内存读取也通过。

本次仅重测“校验已有 Flash 后调试”入口，事务脚本包含 `verify_image`，不含 Flash 写入、EEPROM 恢复或 `resume`。另一个下载后调试入口同步了相同选项，但本次没有重复烧录验证。复验前没有中断或连接用户正在使用的会话。
