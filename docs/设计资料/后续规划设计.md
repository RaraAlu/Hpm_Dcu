# HPM DCU 表情头 CAN 透传后续规划设计

> 本文保留早期 48 B 双槽提案，不是生产 ABI。生产 rev 11 使用固定 can0 的 12 B 单槽，实际字段、排程及容量以[生产周期布局](../当前说明/按启动配置生成周期布局.md#表情头与双手旁带)为准。

**当前 DCU 已经预留透传 PDO，接表情头复用现有布局。** 上电默认的 `MotorWithRaw`（档 1）每个方向已经有 48 B 透传旁带，各含两个原始 CAN 帧槽。旁带通过槽内的 `Channel` 指定物理 CAN 口。`can0` 在当前生产和台架启动配置中均未启用，建议将它设为表情头专线，使用 **1 Mbit/s、标准 11 位 ID 的经典 CAN**。

| 使用场景 | 能否直接走现有通路 | 最小改动 |
| --- | --- | --- |
| **只接表情头，先验证透传** | 可以复用档 3 `SingleFd` 的 88 B PDO。`can0` 须先在启动 Profile 中启用 | 在 Profile 新增 `can0` classic 通道，经 PREOP 协商档 3 和 `can0` 的透传配额。RK 使用现有 88 B 通路并确认支持 `can0` 的经典 CAN 帧。这个档位只运行透传 |
| **同一块 DCU 同时跑电机和表情头** | 可以复用档 1 的 48 B PDO。当前启动校验会拒绝在含电机的 Profile 中声明 Raw 配额，现有生产镜像仅写一个 SDO 无法启用该旁带通道 | 为 `can0` 加启动配置和旁带配额，生成器和固件各改一处角色/配额校验，允许专用 Raw 通道与其他总线的电机并存。重新生成契约，RK 在原电机周期里接入该旁带 |

RK3588 的 `DriverModule` 收发原始 CAN 帧，算法层负责组包、解码和头部状态。HPM 根据 `Channel` 转发，负责通用帧校验、限流和故障统计。首版沿用 **500 Hz DC、现有 SM3 发布截止和电机 N+1 契约**，以当前头板固件运行 **25 Hz 完整姿态**为目标。本文基于 `Hpm_Dcu` 提交 `4cfea81` 和表情头仓库提交 `f278e3f`，吸收了两份附带的修订建议。RK 混合档适配、联调时序和故障行为待验证。 [表情头通讯协议](表情头通讯协议.md)

启用顺序为 PREOP 核对布局 → 进 OP 并按既有规则建立板级无使能基线 → 允许板级发送并打开 `ChannelEnableMask` bit0。`can0` 按 Raw 角色配置，头部命令走帧槽，轴位图只表示运动轴。HPM 复用 MCAN classic 初始化、ISR、Raw RX 队列、`process_raw` 和现有发送终态；档 1 检测到已选通道的 `role >= 2` 时，TxPDO 旁带发布原始帧。电机诊断从逐轴生产数据和完成计数获取，不占用旁带。

生成器和 `initialize_profile()` 应执行等价校验。验证专用 Raw 与其他总线电机并存、同一总线角色冲突、未配置通道授权或发送，以及原 Profile、档 2/3 和在线通道选择的回归。首轮在 RK 发送入口检查表情头的帧类型与各 ID 的 DLC，头板接收校验的现有缺口见第 7 节。HPM 继续使用通用 Raw 帧检查。

### 档 1 旁带字段供 DriverModule 对接

主站写从站的 RxPDO 为 `0x1640 → 0x7300`，从站发主站的 TxPDO 为 `0x1A41 → 0x6400`。以下均为**相对旁带块起点**的字节偏移。PDO 的整数用小端，`Data` 内字节顺序由表情头协议定义。

| 偏移 | 字段 | RK 处理 |
| --- | --- | --- |
| 0–3 | `BatchSeq`，U32 | 下行用递增批次序号，首个有效批次用非零值。上行按发布序号消费一次，随会话重建去重状态。两向序号各自独立 |
| 4–5 | `ValidMask`、`SlotCount` | bit0/bit1 对应两个槽，计数填置位数。首版空批填 `0/0`，单帧下行填 `1/1`。上行按有效掩码读取两个槽 |
| 6–15 | `Flags`、`DropCount`、`Reserved` | 下行三个字段均填 0。当前档 1 上行的 `DropCount` 取板级 `RxDropCount`，排查时同时看 can0 通道计数及 `0x2101:04` 的透传累计丢弃差值 |
| 16–31、32–47 | 槽 0、槽 1，各 16 B | 槽内 `+0` CanId(U32)，`+4` Channel(U8)，`+5` FrameFlags(U8)，`+6` DLC(U8)，`+7` 保留，`+8` Data[8]。表情头下行 `Channel=0`、`FrameFlags=0`，保留字节和 DLC 后尾部填 0 |

混合档的 `raw_submit<false, true>` 会检查当前 CAN 发送是否已退休。同一 `can0` 在一拍填满两槽时，后一个槽可能被拒收并计为丢弃。首版采用 **下行 1 帧/拍、上行最多 2 帧/拍**。原始帧路径先接受 `BatchSeq` 再尝试提交 CAN，若后续因忙或预算不足拒绝，同一序号重复写入会被去重。验收覆盖空批、重复、跳号、U32 回绕和会话重建。板级 `CycleSeq` 和命令租约仍按 EtherCAT 周期维护。上行帧按实际到达进入后续发布窗口。

## 3. RK DriverModule 给算法层的接口

通过现有 RK 进程中的 `DriverModule` 接入 IgH，由同一个周期拥有者写入旁带。优先复用 RK 已有的 ROS 2 原始 CAN 消息或内部队列。当前工程记录了独立 `SingleFdTransport` 和透传话题通路，实际混合档接口和字段需在 RK 仓库确认。以下为建议的数据契约。

| 方向 | 算法侧数据 | DriverModule 行为 |
| --- | --- | --- |
| 算法 → 驱动 | 原始 CAN 帧提供 `channel`、`can_id`、`frame_flags`、`dlc`、`data`。普通表情提交完整五帧快照及生成单调时间、会话和过期时刻 | 首版最多保留一个执行中组和一个最新待发组，只替换尚未开始的组。组启动前检查剩余有效时间能否排完五帧，组中途过期或故障则丢弃未发部分并报告已知结果。已发目标由头板处理。周期侧使用有界交换，维护应答由非周期路径处理 |
| 驱动 → 算法 | `on_can_rx(frame, rx_monotonic_time, session)` 或等价话题 | 每个新 TxPDO 批次按有效槽发布。时间戳取 RK 首次消费该帧的单调时间，用于反馈年龄和超时。过期或跨会话数据不进入当前状态缓存 |
| 驱动 → 算法 | 链路状态、丢弃/拒绝、会话标识 | 分别记录 RK 入队、PDO 交付、MCAN 提交、CAN TX 完成/取消和设备应用结果。WKC 用于判断过程数据交换。`0x2101:07` 是全板发送完成累计值，`0x2101:08` 是透传取消累计值，配合通道计数和抓包使用。只有累计值时，逐帧执行结果标记为未知。普通姿态没有应用层逐帧 ACK |

算法按 **25 Hz** 提交完整五帧姿态，驱动在 500 Hz EtherCAT 周期内分拍下发。首轮按 `0、6、12、18、24 ms` 写入一组，下一组间隔 40 ms。其余拍继续维护板级周期和命令租约，闲时透传区用空批。头板按帧处理，五帧可能在不同时刻生效。普通只读查询放入组间空档，首轮每个间隙最多一笔，舵机查询逐路等双回包。涉及标定、写参数和 Flash 的操作使用独占维护时段，暂停完整姿态组。当前回包协议缺少事务号，超时后同字段的迟到回包可能仍有歧义，结果标记为未知并按需读回。增量微调、保存和恢复等命令须显式处理结果，自动重发会带来重复执行风险。

## 4. 算法层如何控制头和读取反馈

### 控制目标

算法以当前头固件的通道表维护一份完整姿态目标。做 Blendshape 时，在算法层完成权重组合、零位或基准姿态、通道映射、限位和变化率限制，再按 `0x601 → 0x602 → 0x603 → 0x604 → 0x605` 输出一组完整目标。每帧是标准数据帧，DLC 固定为 8；只调一路时，同一帧的其他字节仍要填入应维持的已知目标。上位机集中式 Blendshape 说明可用于算法数据流，具体舵机字段采用当前 CAN 协议中的范围和类型。

| CAN ID | 编码与实际用途 |
| --- | --- |
| `0x601`、`0x602` | 每字节一个电机目标。原始值 `0…72`，每格 `10°`，对应寻零有效时的相对位置。全局编号 6、8、14、16 在当前固件为预留槽 |
| `0x603` | Byte0–5 为六路电机目标，Byte6–7 为板4两路舵机的标定零位偏移，`0…54°` 每格 `1°` |
| `0x604` | 四个大端 `int16`，按角度乘 100 编码。Byte0–5 依次为板4舵机5、6、7 的 roll、yaw、pitch 通道，协议范围为 ±20°、±35°、±35°。Byte6–7 为板4 `servo[2]` 和 `servo[3]` 共用目标，范围 0–45° |
| `0x605` | 四个大端 `int16`，板2舵机顺序 `servo[1], servo[0], servo[3], servo[2]`，各为 ±45°，按角度乘 100 编码 |

`0x604/0x605` 普通控制目前进入舵机任务前会截断为整度。当前 `0x604` 直接驱动对应舵机并沿用各路标定设置。实际姿态和行程按标定值约束。历史 Stewart 实现说明可用于追溯旧方案，当前字段语义见根目录 CAN 协议第 3.2 节。

### 反馈与主动查询

| CAN ID | 算法侧处理 |
| --- | --- |
| `0x700…0x703` | 心跳 DLC 4，格式 `[板号, 递增计数, A5, 5A]`，每板 4 s。按板记录 last-seen，可先以约 9 s 为离线初值并用抓包调整。心跳表示通信在线，寻零就绪需另行确认，现有心跳及周期反馈缺少寻零状态位 |
| `0x781/785/791`、`0x782/786/792`、`0x789/78D/794`、`0x78A/78E/795` | 四板各三种电机组合反馈。每个电机是大端 `int16` 位置（度）与 `int16` 速度（rpm），`0x792/0x795` DLC 4，其余 DLC 8。按 `(CAN ID, A/B 槽)` 查固定物理映射。例如 `0x791` A 对应 `0x603 Byte2` 的 t6，B 对应 Byte0 的 t5。板1/3 每个 ID 约 120 ms，板2/4 约 200 ms。状态带时间戳、有效性和年龄，超时标为陈旧 |
| `0x7A3/0x7A7/0x798/0x79F` | DLC 8，每帧两路大端 IEEE-754 `float32`，单位度。表示舵机软件逻辑输出相对标定零位的偏移，可能短暂读到新目标值。板4舵机5–7 可逐路发 `0x610` 查询，从 `0x628 Byte4–5` 读绝对逻辑输出角度 |
| `0x620 → 0x621` | PID 和系统信息。用定向板号发送，按返回的地址、环路、参数编号和状态码匹配，建议同一时刻只挂一个此类查询。设备响应等待独立于 EtherCAT 周期 |
| `0x60F → 0x625/0x627`、`0x610 → 0x626/0x628` | 分别是板2和板4舵机标定/缓动接口。请求 DLC 5、响应 DLC 8。走独立维护入口，标定期间暂停对应通道普通目标更新，查询按单路节流 |

首个只读往返可用板4电机槽数查询。算法发送 `channel=0, can_id=0x620, flags=0, dlc=8, data=05 40 00 03 00 00 00 00`，成功时收到 `0x621`、DLC 8、`00 40 00 03 00 00 00 05`。抓包应能同时对照 SM2 上的请求、CAN 上的请求与响应、SM3 返回和算法解码结果。

### 带动力前确认失联、寻零和维护行为

算法分别跟踪 EtherCAT 会话、各头板心跳、各路反馈和查询超时。4 s 心跳与约 9 s 离线阈值用于在线监控。DCU 租约到期只停止后续转发，已接收的目标和正在执行的缓动由头板继续处理。带动力联调前，先在隔离台架验证头板本地保护或整机已有的独立停机链路，明确各轴在断线、寻零失败、标定中断时的安全输出与允许响应时间。若安全动作尚未确认，先完成只读与动力隔离透传验收。

如需补头板命令看门狗，可将 **200 ms** 作为联调试测值，由机构允许的停止时间和实测命令间隙共同定值。固定周期控制任务应按本板所需的各个控制 ID 单独检查有效目标年龄，积压帧按入队时间判定，心跳、查询、无关帧和错误帧不能续期。联调覆盖主站仍在线但目标停发、持续收到一个 ID 且缺少其他必需 ID、重连和重新寻零。恢复使用新会话与授权、有效寻零状态和经标定的初始目标。旧线协议缺少授权/序号字段，若现有独立控制权机制不足，由头板与 RK 共同评估授权接口。

## 5. 需要在台架定值的参数

500 Hz EtherCAT 每 2 ms 交换一次 PDO，按下行一槽、上行双槽计算，理论服务上限分别为 **500 帧/s**、**1000 帧/s**。25 Hz 五帧姿态需要 **125 帧/s**，常态反馈和心跳合计约 **101 帧/s**，还有余量用于逐笔查询。持续下发的瓶颈在头板。四板接收任务都在每处理一帧后等待约 5 ms，每板处理量约 **200 帧/s**。每组的五帧都会进入每块板的接收队列，50 Hz 整组会达到 **250 帧/s/板**，按当前源码会持续积压。若需要 50 Hz 完整姿态，先调整并验证头板接收任务的吞吐。

| 参数或时序 | 首轮设定 | 怎样测和调整 |
| --- | --- | --- |
| 姿态频率、组内间隔、过期时间 | 25 Hz，组内每隔三拍写一帧（6 ms），首帧到末帧的 PDO 写入跨度 24 ms。可试用生成后 40 ms 作为待发组过期阈值 | 同时记录 SM2 写入、CAN 实际上总线和头板处理时刻。看一组是否在下一组前处理完、控制效果是否可接受。用头板 FIFO 和 RX 队列丢弃计数检查积压，再调整组内节拍和待发组时限。过期后等待新组，用正常排程恢复 |
| 透传限流与 HPM 的 RX 服务 | `can0` 一帧/2 ms，上行复用两槽，先沿用现有 FIFO、队列和闭锁门限 | 区分配额/发送端未退休拒绝、HPM 或头板 RX 丢弃、主站晚消费。突发查询先节流，连续电机周期下若发现 Raw RX 服务间隔过长，再改工作任务并做电机回归。验收目标为所需负载下无持续积压、丢弃计数无增量 |
| 只读查询响应超时 | 一次只挂一笔同类请求，普通查询和涉及 Flash 的操作分别计时 | 记录同类请求完整往返的分布和最大值，按最坏工况加余量。舵机查询计到第二帧回齐，另测迟到回包与重连的处理。算法查询时限独立于 EtherCAT 命令租约 |
| 反馈陈旧与心跳离线 | 各组合反馈 ID 按 120/200 ms 刷新，陈旧阈值可从约 360/600 ms 起步，心跳 4 s，离线阈值可从约 9 s 起步 | RK 接收时间用于计算主站侧反馈年龄，头板采样时刻另测。记录最坏间隔和断线观测时间，再按需要调整。断链后立即使旧会话缓存失效。执行器失联动作按第 4 节独立验收 |
| 现有 EtherCAT/电机时序 | 以现有 2 ms DC 周期、SM3 发布相位、板级租约及电机 N+1 为对照 | 同时测头部回传和电机本拍新反馈。出现回归先定位工作任务、发布或采样延迟，并把 Raw 开销压回既有余量。真实硬件漏边沿和软件登记迟到分别取证，按原规则验证保护 |

## 6. 实施顺序与验收

| 阶段 | 交付与通过条件 |
| --- | --- |
| 1. 保存基线、确认物理总线 | 记录当前电机镜像、Profile、主站配置和 N+1 基线，保留回退版本。核对 Kunhong 板 `can0` 端子、四板固件和终端。用 CAN 分析仪确认经典 1 Mbit/s、四个心跳和 16 种组合反馈，用原 USB-CAN 完成一次只读查询作为对照 |
| 2. 单独验证透传 | 为台架镜像新增 `can0` classic 通道，沿用档 3 `SingleFd` 的 88/88 B 通路。PREOP 经现有档位协商为 `can0` 写 `0x2101:05=0x00000001`，电机总线发送权保持默认。RK 按档 3 建立空批基线、确认就绪及 DC 锁定，再运行只读查询和持续接收。核对 `0x2101:07` 发送完成增量、取消/丢弃计数、CAN 抓包和算法解码。由电机档切入前结束电机控制 |
| 3. 接入混合档 | 实施第 2 节的启动校验与 RK 旁带适配，Ubuntu 上用 `hpm-release` 和生产 Profile 构建，确认本次构建实际使用的 YAML 与导出契约。动力隔离时在 PREOP 核对映射后进 OP，验证 can0 持续收帧、只读往返、BatchSeq 重复/回绕、无效帧头和过期组。记录队列高水位、总线错误及丢弃计数 |
| 4. 同机周期验证 | 按仓库台架流程，用生产 `DriverModule` 做单拍全零 MIT，第 N+1 帧逐轴核对本拍新反馈和 CAN TX 完成计数，同时保持头部被动反馈与只读查询。确认第 4 节安全前提后，从经标定的低幅度 10 Hz 姿态逐步到 25 Hz，按第 5 节记录五帧跨度、回传尾延迟、丢弃和电机周期余量。可从 60 s 短测起步，通过后按实际使用时长扩展。WKC、CAN 发送完成和外设回包分别记录 |
| 5. 异常与恢复 | 测试表情头断线、can0 bus-off 或发送未完成、主站退 OP、重新连接及突发 RX。检查超时判定、旧帧清退、故障报告和停机行为，并核对电机侧的既有保护与周期要求。正式运行以通过此阶段的 Profile、主站配置和记录为依据 |

## 7. STM32 优化路线

当前头板普通接收仍有逐帧约 5 ms 等待，合法控制帧的字节格式继续参照现有协议。25 Hz 接入先验证现有吞吐和第 4 节的必要保护。以下工作按实测和升级需求推进。

| 顺序 | 适合在 STM32/RK 落地的改进 | 验收要点 |
| --- | --- | --- |
| 1. 输入校验 | 四板接收路径固定拷贝 8 字节，补齐帧类型和长度校验。普通控制及 PID 请求 DLC 8，板2/4舵机维护 DLC 5。驱动发出前按协议检查，头板用当前 HAL 的 DLC 表示确定有效长度 | 错误帧不更新目标或刷新保护计时，合法旧帧和维护回包兼容 USB-CAN 与 EtherCAT-CAN |
| 2. 按板过滤 | 先验证映射与被过滤帧的副作用，再缩小普通 ID。板1 `0x601/603`，板2 `0x601/603/605`，板3 `0x602/603`，板4 `0x602/603/604`。保留四板 `0x620` 及底板各自维护 ID | 25 Hz 普通控制在顶板约 50 帧/s、底板约 75 帧/s。现有 `StdFiltersNbr=2`，若底板全用双 ID 精确过滤，每板 5 个 ID 需 3 个过滤项。核对分配、索引和 HAL 返回值 |
| 3. 按需提升吞吐 | 若测得逐帧等待限制目标速率，沿用现有阻塞队列，评估唤醒后有限批处理。利用现有舵机维护队列和 PID 参数任务，验证 Flash/QSPI 操作对控制周期的影响 | 用实际优先级、队列水位和最坏执行时间证明控制任务准时。若要评估 50 Hz，重新制定组内间隔，40 ms 一组的原 6 ms 间隔无法排进 20 ms 一组 |
| 4. 可选反馈与同步扩展 | 分别评估舵机内部小数精度、区分命令值与逻辑输出、寻零/授权状态反馈，以及完整姿态的分组提交 | 精度与输出语义先做旧协议回归。新增报文由 RK 与四板共同定义版本及帧归属，测量同组跨板应用偏差。HPM 仍通过原始 CAN 传送 |
