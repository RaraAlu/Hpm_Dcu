# DCU 固件目录与代码划分评审

核对日期：2026-11-17。范围为 `firmware/` 的目录、文件职责、命名、构建注册、C/C++ Interface 和 FreeRTOS 执行归属。以下评审以首批实施前的源码为基线；用户确认后的实际改动与验证见末尾“首批落实与验证”，其余建议不代表已经实施。

**总体判断：现有目录骨架值得保留，语言分工基本合理；主要欠账是应用对 EtherCAT 字典和线格式的依赖、CAN 硬件接口混入产品协议，以及部分状态和时钟的归属不清。继续大规模改名的收益低于收敛这些 Interface。**

复审修正：“目录骨架值得保留”不等于 `app/motor` 的业务划分已经合理。电机应用目前仍有状态分散、事务生命周期外泄和重复模型转换，详见下文“motor 业务专项复审”。仅把函数拆成类和文件，没有充分减少维护者需要同时理解的内容。

## 优先问题

优先级表示维护和后续扩展的处理顺序，不表示已经发现相应板上故障。

### 应用仍以 EtherCAT 字典作为共享状态

优先级：高。

事实：[motor_application.cpp](../../firmware/app/motor/motor_application.cpp)、[axis_controller.cpp](../../firmware/app/motor/axis_controller.cpp)、[raw_can_gateway.cpp](../../firmware/app/motor/raw_can_gateway.cpp) 和 [encos_parameter_transactions.cpp](../../firmware/app/motor/encos_parameter_transactions.cpp) 都依赖 `motor_dictionary.hpp`。其中应用和原始转发还直接使用 `motor_pdo_codec.hpp`；反过来，`motor_pdo.cpp`、`motor_coe.cpp` 又调用 `motor_application.hpp`。

[motor_dictionary.hpp](../../firmware/comm/ethercat/motor_dictionary.hpp) 的 `object<T>()` 返回底层可写指针。应用中仍直接出现 `0x2001`、`0x6000` 等对象索引，轴控制的反馈和诊断也直接写入字典。对象化已经隐藏了会话、轴和队列的一部分状态，但没有让字典退出业务状态存储。

风险：修改 PDO、SDO 或字典字段会波及应用控制；新增非 EtherCAT 命令来源时，仍需满足旧字典约定。当前单一业务任务限制了并发访问范围，但不消除这种维护耦合；未来直接增加任务会扩大共享状态问题。

建议：让 EtherCAT 适配负责线格式、对象索引和访问权限，应用接收类型化配置与命令，输出反馈快照。先处理配置应用、命令接收、反馈发布三条实际通路，不一次重写所有字典访问，也不只把通用的 `object<T>()` 换一个目录。通信回调调用应用是正常适配关系，问题在于应用反向依赖通信布局和可写存储。

### CAN 公共头混合硬件和产品协议

优先级：高。

事实：[ethercat_canfd_gateway.h](../../firmware/comm/canfd/ethercat_canfd_gateway.h) 同时包含 `hpm_stat_t`、CAN 收发和轴标签操作、LED/时间入口，以及 packed 的 `canfd_slot_pdo_t`、`canfd_bus_pdo_t`、`ethercat_canfd_process_image_t`。[motor_pdo_layout.hpp](../../firmware/comm/ethercat/motor_pdo_layout.hpp) 为得到这些线格式而包含整个 CAN 硬件头，间接带入 `hpm_common.h`。

判断：这不是独立、通用的 CAN 驱动，`gateway` 也不足以描述当前实现。实际 EtherCAT 透传策略在 `app/motor/raw_can_gateway.cpp`，此处主要是 HPM MCAN 收发、中断队列、发送归属跟踪和指示灯。

建议：先将 PDO 类型与布局断言放入 `comm/ethercat/` 的专用线格式头，例如 `raw_can_pdo.h`；CAN 收发公开头只保留帧、收发、状态及必要的取消契约。轴标签确有当前用途，可保留为产品专用语义，或在存在第二个消费者时改成中立发送标签，不提前设计通用总线框架。职责分开后再考虑 `can_transport.h`、`hpm_mcan_transport.c` 等名称。

### 毫秒时钟绑定在指示灯回调中

优先级：中，但拆除或关闭指示灯前必须处理。

事实：[main.c](../../firmware/app/main.c) 通过 `board_timer_create(1, ethercat_canfd_gateway_led_tick)` 启动回调；[ethercat_canfd_gateway.c](../../firmware/comm/canfd/ethercat_canfd_gateway.c) 在这个回调中递增 `s_now_ms`。应用用 `ethercat_canfd_now_ms()` 检查命令租约、反馈与参数事务超时。

风险：维护者可能把 `led_tick` 当成可关闭的显示功能，实际停掉它也会停掉业务毫秒时间。`now_ms` 是回调计数，`now_us` 则转调 BSP 的自由运行硬件计数器，两者来源和启动时点不同。

建议：将单调时钟的维护职责与灯效分离，由 BSP/运行适配提供明确定义的时间 Interface，灯效只消费时间或节拍。不能简单用当前 32 位微秒计数器除以 1000 替换毫秒时钟，那会改变回绕周期和已有无符号差值契约。变更时补充回绕、长时间运行及延迟中断测试。

### 公共诊断状态不符合私有实例约束

优先级：中。

事实：[ethercat_cycle.h](../../firmware/app/cycle/ethercat_cycle.h) 第 23 行导出 `extern volatile dcu_cycle_diagnostics_t g_dcu_cycle_diagnostics`，实例在 `ethercat_cycle.c` 第 17 行具有外部链接；任务模块直接写入栈水位和致命错误字段。

判断：这是自有代码，不是 SSC 生成存储特例，与项目“公共头只暴露调用契约、可变状态实例保持模块私有”的规则不一致。`volatile` 没有规定谁能写哪些字段，也没有提供完整诊断快照的读取约定。

建议：周期统计与运行致命错误各自明确唯一写入者，通过只读快照和窄更新函数协作。若必须保留调试器全局符号，应明确记录例外，而不能声称所有可变状态都已私有。现有 [test_header_ownership.py](../../tests/host/test_header_ownership.py) 主要检查实现声明和列出的私有头，不会拒绝这个公共 `extern`；应补公共状态导出检查及第三方例外清单。

### 构建目录尚不能约束模块依赖

优先级：中。

事实：局部 CMake 使用显式 `sdk_src()` 清单，这是优点。但 SDK 的 [cmake-ext.cmake](../../third_party/hpm_sdk/cmake/cmake-ext.cmake) 将这些源加入同一个 SDK 库，`sdk_inc()` 把路径加入同一个 Interface 目标。`motor`、`cycle`、`canfd`、`ethercat`、具体 ENCOS 驱动及生成头均在共享包含路径中。

风险：目录层次不会阻止应用引用具体硬件头，`detail/` 也没有编译器级访问隔离。当前结构测试对部分直接 `#include` 有约束，不等于验证了完整或传递依赖。

建议：近期增加按目录限制依赖的宿主编译/结构检查；先让公共设备模型、协议核心、调度和流水线保持可独立编译。出现真实独立构建需求后，再评估独立 CMake target 和 `PRIVATE/PUBLIC` 范围，不为目录整齐立即替换 SDK 构建体系。

### 生成物的名称和可再生成性需要分开看

优先级：中；修改线上布局、轴数或设备类型之前应提升为前置工作。

事实：`generated/encos/encos_interface.h` 不仅描述 ENCOS 电机，还包括板级命令、通道、原始 CAN、IMU 和对象字典元数据；`encos_storage.inc` 是整套产品对象存储。文件头标注的 `tools/generate_encos.js` 当前不存在，普通 CMake 使用已提交产物，不执行该生成器。来源约束见[生成文件与来源清单](../当前说明/生成文件与来源清单.md)。

判断：名称带有历史厂商色彩，但不能仅改成 `motor` 就宣称已经通用化。更重要的是类型、存储、SSC 字典、ESI、SII 的一致来源尚未恢复。

建议：当前保留生成物原名和唯一副本。恢复可重复生成及隔离目录差分后，再考虑按产品协议归档，例如 `generated/dcu_protocol/`。`pinmux.*`、`clock.*` 虽位于 BSP，却有 HPM 工具生成标记；这是按维护责任就地保存，不必强制搬到顶层 `generated/`，但应记录生成与手工补丁的维护规则。

### 低成本修正应优先于整目录改名

优先级：低。

- [ethercat_callbacks.c](../../firmware/comm/ethercat/ethercat_callbacks.c) 的映射注释仍写“四路 × 128 字节，禁止运行时改变过程映像大小”，实际支持三档完整产品 PDO；空 `APPL_Application()` 的注释还写“1 ms CAN 调度”，实际工作节拍配置为 50 us。这些注释会直接误导职责判断。
- [board.h](../../firmware/bsp/dcu_hpm5e31/board.h) 的 `BOARD_NAME` 仍为 `hpm5e00evk`，根 CMake 实际选择的是 `dcu_hpm5e31`。这是标识与日志歧义，不是当前构建选错板卡的证据。
- `cfg/device_config.h` 名称较泛，内容实际是四通道、每通道七轴的产品容量。以后去厂商化时可改为 `product_topology.h`；先检查生成布局和硬件数组约束，不把这些宏误当作可以任意调整的参数。
- `cfg/dcu_compiler.h` 是双语言编译兼容工具，不是运行配置。职责上更接近公共基础头；目前只有少量内容，不值得单独引入一套 `platform/common/utils` 层级。
- `ethercat_can_task.h` 当前只有 C 消费者，没有 `extern "C"` 保护不等于现有链接故障；若以后供 C++ 调用，应先补跨语言契约及链接测试。

## C 和 C++ 的划分

[根 CMake](../../CMakeLists.txt) 已声明 C/C++/ASM，C++17，仅给 C++ 添加 `-fno-exceptions`、`-fno-rtti`，最终使用 C++ 链接。这是有效的混合工程，不是只改扩展名。

| 责任 | 当前语言 | 评价 |
| --- | --- | --- |
| 入口、SSC 回调、ISR/硬件适配、RTOS 启动 | C | 与现有 SDK/SSC 保持一致，合理 |
| PDO 流水线与周期编排 | C | 原子交接及可独立测试比使用哪种语言更重要，无需强制类化 |
| 电机应用、轴对象、调度、设备模型、PDO/CoE 产品适配 | C++17 | 私有状态和静态组合已有实际用途，合理 |
| ENCOS 编解码 | C++ 实现，C Interface | 合法且已有跨语言测试，不需要强制改 `.h` 为 `.hpp` |
| 生成对象存储 | C | 保留生成初始化语法和唯一实例，合理 |

不建议新增 `c/`、`cpp/` 两棵源码树，也不建议统一 `src/` 与 `inc/` 后把所有同名头集中在一起。当前按责任就近存放接口和实现，更利于定位修改。

宏和类型声明归 `.h/.hpp`，实例留在 `.c/.cpp` 的原则应继续执行。纯辅助函数不必变成类；静态生命周期不等于公共可变全局。C++ 虚函数也不等于动态内存：当前生产驱动由静态实例绑定，应分别评估调用代价和分配策略。

## FreeRTOS 执行归属

当前是一个 `ecat-can` 业务任务，另有内核 Idle 任务；不是每个目录一个任务。关键调用如下：

```text
main.c
  -> 板级与通信初始化 -> motor_control_init -> 时基/周期/SSC 初始化
  -> dcu_rtos_start -> 静态 ecat-can 任务

ESC PDI IRQ -> SSC PDI_Isr -> APPL_OutputMapping -> PDO 暂存
Sync0 IRQ   -> pdo_pipeline_sync -> 锁存当前周期并记录待处理事件
MCAN IRQ    -> 接收队列、发送完成统计
SSC 1 ms IRQ -> 记录待处理 tick
工作 50 us IRQ -> 截止监视/TX 禁止与取消 -> FreeRTOS 任务通知

ecat-can 任务 -> dcu_cycle_step
  -> SSC 延后 Sync 处理 -> 取得锁存 PDO -> 应用命令
  -> 反馈发布窗口检查 -> 电机/CAN/事务处理 -> 再检查发布窗口
  -> SSC tick 与 MainLoop -> 故障检查
```

不要把“业务由一个任务串行处理”扩大为“SSC 全部不在中断运行”：PDI 仍执行 `PDI_Isr()`；`Sync0_Isr()`、`Sync1_Isr()` 则延后到任务。快 IRQ 与可调用内核 IRQ 的阈值契约已集中在 `cycle_config.h`，以后拆模块也必须保持它。

### 当前时间资源

| 用途 | 资源 | 配置/实现位置 |
| --- | --- | --- |
| FreeRTOS tick | MCHTMR/MTIME，配置为 1 kHz | `cfg/FreeRTOSConfig.h`、SDK HPM FreeRTOS port |
| 微秒自由计数 | GPTMR1 通道 0，计数时钟配置为 1 MHz | BSP `cycle_timer_map.h`、`cycle_timers.c` |
| 业务通知及截止监视 | GPTMR2 通道 0，配置周期 50 us | BSP `cycle_timers.c` 与 `ethercat_can_task.c` |
| SSC 计时 | GPTMR0 通道 0，1 ms | `cfg/ecat_config.h`、`hpm_ecat_hw.c` 的当前非 RTOS tick 分支 |
| CAN 毫秒计数、活动灯和心跳 | GPTMR3 通道 1，1 ms | `board.h`、`board.c`、`ethercat_canfd_gateway.c` |

这是资源配置清单，不是实测精度或延迟结论。`board.h` 还保留其他 RTOS 示例定时器宏，不能单看这些宏就认定当前 FreeRTOS tick 使用 GPTMR1。

单任务方案减少了会话和字典的任务间同步成本，当前可以保留。但前提是周期内工作量有界：未来 IMU、日志、存储或复杂 CoE 操作不能随意塞入这个任务。是否新增任务应由阻塞行为、采样速率、截止要求和测量结果决定，而非文件数量。当前 EEPROM 刷写入口限制在非 OP/非 SAFEOP 状态，也不能因重新划分目录而丢掉该限制。

尚需板上评估的变量包括 CAN 实际负载和帧长、ISR 最坏耗时、通知合并后的工作延迟、Flash XIP/擦写影响、栈水位以及停止发送后电机的实际响应。`BusScheduler::frame_cost()` 的注释明确是工程估计；50 us 定时配置不保证任务每次都能按时运行。取消 CAN 发送也不等于已验证物理急停。

## motor 业务专项复审

本节针对“motor 业务太复杂”重新核对调用链、状态和宿主测试。范围包括 `app/motor/`、设备驱动、ENCOS 编解码与 EtherCAT 适配；不以文件数、类数量或行数直接判定设计质量。复审基线中 `app/motor/` 为 17 个文件、2039 行，包含空行和注释，其中 6 个 `.cpp` 共 1602 行。

### 判断与必要边界

**确实存在可削减的实现复杂度，但不能把现有保护和产品能力都当成冗余。** 这里的 motor 不只是“目标值转 CAN”：还包含配置生效、控制权、启动握手、查询反馈、租约、总线调度、参数写入及读回核验，以及两种原始 CAN 通路。C/C++ 共存和 FreeRTOS 本身不是这些业务分支的主要来源。

启动握手、Stop 优先、命令/反馈超时、总线故障、写参数后的读回核验都有具体行为和测试。候选配置与已 Apply 的运行配置也必须区分，不能为了“唯一状态”把合法的配置快照删掉。停止排队/发送不等于已经验证电机物理停止。

以下优先级针对维护风险，**不是已复现的运行故障等级**。

### 高：轴对象没有拥有完整的轴运行状态

事实：[axis_controller.hpp](../../firmware/app/motor/axis_controller.hpp) 的 `State` 拥有阶段标志和时间戳，但位置、电流、故障、查询结果存放在全局字典；[axis_controller.cpp](../../firmware/app/motor/axis_controller.cpp) 的 `query_ready()`、`accept()`、`consume_feedback()` 都直接读写这些对象。`publish()` 主要更新全局反馈并清除“新数据”标志，返回的 `AxisPublication` 却只有 `online/fault` 两个布尔值。应用的 `prepare_publication()` 同样先修改字典，再返回部分元数据。

后果：判断一根轴能否启动、反馈是否有效，不能只看轴对象；还必须了解字典中的状态和发布调用顺序。当前单任务串行访问不等于数据竞争，但这种隐式依赖使功能修改和测试都跨越通信层。现有轴对象测试也通过 `axis_feedback()` 检查结果，并不是不依赖字典的轴测试。

建议：先在现有 `AxisController` 内收拢权威反馈、故障和启动状态，通信层只负责配置/命令转换及状态映射。不要另建一套长期同步的完整字典镜像；明确哪些是运行状态、哪些是待提交配置、哪些是发布缓存。“新数据”标志的消费时点需要单独契约，不能把有副作用的发布函数简单改成可随意重复调用的 getter。

### 高：一次参数事务的生命周期分散在多个模块

事实：轴的 `start_query()` 创建内部查询；`MotorApplication::process()` 读取事务状态、判断超时、取消 CAN、选择发送窗口、发送并调用 `mark_sent()`；`AxisController::consume_feedback()` 再调用参数模块解析响应；参数模块处理 ACK、读回及完成结果。启动运动时，轴还直接执行“取消硬件服务 + 中止内部事务”。[事务模块](../../firmware/app/motor/encos_parameter_transactions.cpp) 已有明确的 `Phase/Purpose`，问题不是完全没有状态机，而是调用方仍需要掌握其生命周期细节。

后果：修改超时、抢占或会话退出策略时，必须同时核对应用、轴、事务和传输取消路径。`cache_query()` 与轴接收路径还重复写入 `QueriedPosition/QueriedVelocity`，同一个状态有多个业务写入点。

建议：继续使用现有事务模块，集中请求、响应、超时和取消的状态转移；轴只提出查询需求、接收查询结果。实际发送和预算仍由调度/编排负责，通过明确的提交成功或取消事件推进事务。不要为了收拢状态再引入通用服务框架、消息总线或新任务，也不要把查询策略、CAN 调度和参数协议全部合成一个大类。

### 中：通用模型与旧线格式之间有往返转换

当前控制链可以直接从源码复核：

```text
AxisController 中的 mc_axis_rx_t
  -> motor_driver_binding.cpp: motor::Command
  -> MotorDevice: 能力检查与驱动调用
  -> EncosMotorDriver: 再构造 mc_axis_rx_t
  -> encos_encode(): CAN 帧
```

反馈则经过 `encos_feedback()` 生成 `mc_axis_tx_t`，转换为 `motor::Feedback`，再由 binding 写回 `mc_axis_tx_t`。依据见 [motor_driver_binding.cpp](../../firmware/app/motor/motor_driver_binding.cpp) 的 `motor_command_from_wire()/decode_motor_feedback()` 与 [encos_driver.cpp](../../firmware/devices/motor/drivers/encos/encos_driver.cpp) 的 `encode()/decode()`。

判断：通用模型有测试替身和驱动隔离的实际用途，但当前接法属于兼容包装尚未收敛，不是完整的协议独立。建议将线格式转换固定在 EtherCAT 入口/出口，内部优先统一使用已有的命令/反馈模型，不再设计第三套中间 DTO。迁移必须保留宽度检查、失败不覆盖输出、线上字节和需要保留的 C ABI；不能把全部适配代码当作可直接删除的复制代码。没有测量依据，不把问题归咎于虚函数性能。

### 中：启动状态表达和命名增加了阅读负担

事实：轴有 `configured/active/armed/query_armed/control_sent`，另有反馈有效性和新数据标志。尤其 `armed` 在收到 ARM 为 0、STOP 为 0 的允许命令时才置真，实际表示重新握手的准备条件，不是通常理解的“电机已使能”。`query_ready()` 和状态字合成是长条件表达式，`accept()` 同时处理停机、复位、握手、校验和首次启动。

建议：先列事件与状态转移表，再考虑用一个枚举表达互斥的运行阶段，例如停止、可重新 ARM、只查询、待首发、等待首反馈、运行；这是设计候选，不是现有协议的新承诺。位置/速度/电流/功率的新鲜度是正交状态，不能强行塞进同一个枚举。保留现有 `AxisController`，不把每个状态拆成类，不新增层层转发的管理器；优先修正 `armed` 这类误导性内部名称。

### 中：原始 CAN 通路只是搬出了主文件，仍然依赖电机内部协作

事实：[raw_can_gateway.cpp](../../firmware/app/motor/raw_can_gateway.cpp) 的 `process()/send()` 接收整个轴数组和调度器数组，同时读事务全局状态、对象字典与 PDO 格式，并直接发送 CAN。它只需用轴的 `matches()` 排除已保留 CAN ID，却在 Interface 上依赖完整 `AxisController`。发送成本还重复了 `BusScheduler::frame_cost()` 的公式。

建议：保留有界队列、去重、速率限制和 ID 保护；将 PDO 解包归通信适配，用只读路由保留信息和明确的发送准入替代整组轴对象依赖。原始 CAN 应是与电机控制共享总线资源的通路，而不是了解电机内部状态的子系统。先收窄 Interface，再决定是否移动到相邻目录；只改路径不能降低复杂度。

### 具体取舍与顺序

| 对象 | 处理意见 |
| --- | --- |
| `motor_application.*` | 保留为单任务编排入口；移出线格式解析和事务内部状态转移，避免继续加职责 |
| `axis_controller.*` | 保留；收拢轴状态、显式表达启动阶段，不继续拆小类 |
| `encos_parameter_transactions.*` | 保留现有模块并集中生命周期；暂不抽象成所有厂商通用参数服务 |
| `can_bus_scheduler.*` | 保留；已有清楚的预算、轮询、截止窗口职责和独立测试，不并入大主循环 |
| `raw_can_gateway.*` | 保留功能，减少对轴/字典的知识；不另起 RTOS 任务 |
| `motor_driver_binding.*` | 保留驱动选择/静态绑定责任；在模型统一后撤掉不再需要的往返转换 |
| `.h/.hpp`、`cfg/`、`detail/` | C ABI 和声明归属有实际约束，不为减少文件数破坏项目规则 |

低风险起点是删除无用途的持久状态和重复计算：轴的 `basic/range` 只在 `configure()` 中赋值并用于驱动配置，可改为配置时局部值；应用的 `rx_total` 每次 `publish()` 清零后累加丢包数，也可成为局部变量；原始 CAN 的帧成本计算复用现有函数。这些有确定的局部证据，但它们只是清理，不能替代前述状态和事务边界调整。

随后逐项收拢反馈状态和事务生命周期，再处理模型转换及启动状态表达。每一步保留行为回归，不能把协议重构、状态机重写和任务拆分一起做。验收应看修改一个业务规则是否只触及其所属模块、轴测试是否脱离 SSC/字典，而不只看主文件缩短了多少行。

产品层仍有一个未确认变量：SDO 运动命令、混合原始 CAN、全透传模式是否都必须长期保留。若都保留，只能消减实现复杂度，不能承诺把业务压缩为“收命令、发 CAN、回反馈”三个函数；若允许裁剪功能，必须同步核对主站、PDO/ESI/字典兼容性和现场调试能力。本轮按保留全部现有功能审查，没有擅自删除能力。

## 建议的整理顺序

1. 修正错误注释和板卡日志名，补充公共可变状态/依赖检查；不改变线上字节、周期和任务数量。
2. 分离 CAN 收发 Interface 与 EtherCAT PDO 类型；分离时间维护与灯效；收回公共诊断实例。每项单独验证，不把改名与时序行为变更混为一次大提交。
3. 从配置应用、命令输入、反馈发布逐条解除应用对字典和 PDO 的依赖，保留既有行为回归。不要用多个新层级包装同一个可写字典指针。
4. 在改变协议布局或产品容量前恢复生成链。扩展第二个真实驱动时，再决定哪些厂商参数/查询操作需要公共 Interface。
5. 最后按已经清楚的职责调整名称和局部目录。只有确认维护收益后才引入独立构建 target 或新增任务。

可能的局部调整是新增 `comm/ethercat/raw_can_pdo.h`、收敛 `comm/canfd/` 的 transport Interface，以及让 `ports/` 明确提供时间契约；不需要推倒现有八个顶层职责目录。`app/runtime`、`comm`、`devices`、`protocols` 等现名没有足够理由仅为个人偏好替换。

每次改动都应保留 C ABI、packed 字段/偏移、三档 PDO 映射、初始化次序和 IRQ/任务访问约束。宏/类型归属变更后运行项目规定的 `python3 -m unittest discover -s tests/host -p test_header_ownership.py -v`，并验证受影响模块和 Debug/Release 固件。删除或改名参与 SDK 静态库的源码时，按[混合语言规范](../当前说明/混合语言开发规范.md)清理旧归档，避免增量归档残留旧对象。

实施日期：2026-11-17。此批保留全部现有功能、PDO/SDO 布局、C ABI、启动规则、发送优先级和超时阈值，不改任务、中断或生成物，不做状态机与协议模型的整体重写。

### 已完成的调整

- `AxisController` 不再持久保存仅在配置时使用的 `basic/range`；配置函数借用待提交对象，驱动仍保留已生效的路由和协议参数。新增用例确认修改候选配置不会悄悄改变已绑定驱动。
- 将内部 `armed` 更名为 `arm_edge_ready`，明确它记录“允许的 ARM=0/STOP=0 已出现”，不是电机已使能。补充 Stop 后重新 ARM、无许可清零和有效清零的回归，没有改变握手流程。
- 将 `MotorApplication::publish()` 的接收丢包累加值改为局部变量；原始 CAN 请求帧和响应帧的成本统一通过 `BusScheduler::frame_cost()` 计算，保留原估计公式。
- 参数模块新增 `available()`、`check_timeout()`，`Status` 不再暴露 `started/hold_until`。应用和原始 CAN 通路不再自行计算参数超时或设备等待期；排队、实际提交、写 ACK 转读回后的计时重置规则不变。
- `cancel()/abort_internal()/reset_session()` 统一承担对应请求的按标签 CAN 取消与事务收尾；轴启动不再手写“检查内部事务 + 取消 CAN + 中止事务”的组合。取消先请求硬件取消再释放事务，不等待硬件完成。会话退出仍保留应用的全总线取消，未完成事务的按标签取消可重复执行，不能据此宣称机器指令时序完全不变。
- 参数解析只通过 `Observation` 返回位置/速度查询值，不再重复写轴的 `QueriedPosition/QueriedVelocity`；这两个字段由轴接收路径更新。参数原始缓存、查询有效位、事务结果和其他诊断写入仍由原模块负责，尚未完成全量字典解耦。

未新增类、RTOS 任务或生产源码文件，也未移除现有防护。事务模块使用现有 CAN 取消 Interface，仍不是一个完全不依赖传输和对象字典的模块。
