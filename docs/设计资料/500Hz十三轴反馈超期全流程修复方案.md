# 500 Hz 十三轴反馈超期全流程修复方案

本文是 2026-11-29 静态审查的结论与改动清单，对象为 `hpm-release` 生产可达路径，拓扑为三路 CAN FD 3+5+5、500 Hz、帧间隔 100 µs、严格截止 `Sync0 + 1600 µs`。审查依据为 [MCU 固件审查规则](../当前说明/MCU固件审查规则.md) 和 [周期锁存与反馈发布契约](../当前说明/周期锁存与反馈发布契约.md)。本文只是方案：未编译、未上板，所有时间目标都要按 [AGENTS.md](../../AGENTS.md) 的单拍规则实测。

## 1. 结论

**只让任务"及时取帧"也通不过。** 按现有测量，任务即使零等待，预算也是负的：

| 阶段（相对 Sync0） | 现状 | 来源 |
| --- | ---: | --- |
| Sync0 → 首帧提交 | 385–403 µs | [十三轴单拍验收](../验证记录/2026-11-29-十三轴单拍反馈验收.md) |
| 5 轴收发（含 4 段 100 µs 间隔） | 约 830 µs，最晚 RX EOF +1221 | 同上 |
| 单帧出队 → 写入 PDO 输入缓冲 | 约 376 µs 墙钟 | 修正版单拍 |
| SM3 写 492 B | 220–277 µs | [500 Hz 设计](500_hz_can_fd_3_5_5_sm2_sm3.md) |

1221 + 376 + 250 ≈ 1850 > 1600。入队后等待 527 µs 只是 CPU 被中断和慢代码占满的表象。需要同时压缩三段：**起跑延迟、单帧处理、SM3 尾段**。

修复后的粗估目标（待实测）：

| 阶段 | 目标 |
| --- | ---: |
| Sync0 → 各路首帧 TXBAR | ≤ 60 µs |
| 最晚 RX EOF | 约 +890 µs（总线时间不变） |
| 最后一帧出队 → 写入 | ≤ 30 µs |
| SM3 尾段（板头、通道、最后一个字） | ≤ 30 µs |
| SM3 发布完成 | 约 +950 µs，余量约 650 µs |

**源码不能定论的项：** 修正版诊断拍里，MCAN 占 563 µs，约 26 次中断平均每次约 20 µs。源码中的工作量解释不了这么多。现有统计用 `dcu_time_now_us()` 取墙钟时间，包含更高优先级中断的抢占，也不含进出中断开销。另外 GPTMR1 的功能时钟被设成 1 MHz（[cycle_timers.c:38](../../firmware/bsp/dcu_hpm5e31/cycle_timers.c)），读它是否慢也要测。所以第 0 步先测量。

## 3. 全流程改动

按数据流顺序列出。每步单独提交、单独单拍验收；单拍失败不自动重试、不转长测。

### 步骤 0：测量基线（只加诊断，不改行为）

- 新增一个诊断构建选项（例如 `CONFIG_IRQ_CYCLE_PROFILE`，生产默认 OFF）。在每个中断包装入口和出口读 `mcycle`，按中断源累计**次数、总周期数和最大周期数**，写到 `.noncacheable.bss` 数组，覆盖 Sync0、PDI、ECAT 1 ms 定时器、GPTMR2（周期与间隔两个通道分开）、MCAN0–3 和 MTIMER。
- 在 PREOP、不发 CAN 的条件下跑一次基础操作基准：各 1000 次的 `dcu_time_now_us()`、`dcu_time_now_ms()`、MCAN `IR`/`ATB`/`TS_SEL` 读、报文 RAM 字读、ESC 字写；一次 `bjcx::decode_status_reply`；一次 `stage_device`。同时记录 `minstret`，用 IPC 区分取指停顿和外设停顿。
- 一拍内额外读出现有的 `prepare_max_us` 和 `esc_write_max_us`，拆开 SM3 的组装时间和写入时间。
- 判读：如果某项外设读取每次超过 0.5 µs，就把它列为步骤 3 的首要对象；如果 IPC 很低且热点在 Flash 地址，步骤 2 优先。

### 步骤 1：Sync0 前预装首帧，Sync0 后立即起跑（F4，约省 330 µs）

**数据通路**

1. PDI 提交 SM2 ready 槽后（约 Sync0 − 375 µs），任务在 `dcu_cycle_service_ethercat_al()` 的预览阶段：
   - 对**全部**严格反馈轴生成预览帧。取消 `preview_control()` 对 `supports_legacy_queries()` 的一刀切，改为驱动声明 `supports_preview()`。BJCX 全零 MIT 可以直接预编码，滚动计数 `counter_` 由驱动保证与受理时一致。
   - 每路按 slot 顺序调用 `mcan_write_txbuf`，预写专用 TX buffer。只写报文 RAM，不发 `TXBAR`，不改 `s_chain`。
   - 记录预装的 SM2 序号、每路帧数和帧内容摘要。
2. Sync0 快中断仍然只锁存（MCU-01）。另加一个处在 `DCU_IRQ_KERNEL_PRIORITY` 内的级联唤醒源，候选有 GPTMR 单次 1 µs 重装、PLIC 软件挂起位，或者复用 `DCU_CAN_WAKE_CHANNEL` 的独立实例。
3. 级联 ISR 或被它唤醒的任务做发射前复核：
   - 锁存槽序号与预装序号一致，命令字段逐轴与预览匹配；
   - `command_permitted()`、租约、`dcu_tx_inhibited()`、总线非 bus-off、`dcu_can_tx_serial_ready()`；
   - 全部满足才写 `s_chain`/`s_tx` 并对各路 slot 0 发 `TXBAR`；任一不满足，就整路回退到现有的"Sync0 后编码再提交"路径。
4. 后续 slot 仍由 TX EOF 加帧间隔节拍发射，现有 `launch_paced` 逻辑不变。

**约束**

- MCU-04：预装不是授权。预写报文 RAM 后若未发射，不能留下待发请求；退 OP、租约过期、拓扑切换时，要清除预装标记。
- 预装帧只能在序号和字段全部匹配时复用；首次启动改发位置保持时，按实际生效的启动命令选帧（沿用 ENCOS 现有规则）。
- 主站命令晚到或缺拍时，不做预装，按原路径处理。

**验收：** `CONFIG_CAN_BATCH_SAMPLE` 对照构建，Sync0 → 各路 `submit_us` 最大值 ≤ 60 µs，没有 50 µs 量化跳阶。

### 步骤 2：热路径整体进 ILM（F3）

- 不再逐个函数加 `DCU_FAST_CODE`，改为按目标文件放置：
  - 固件：`hpm_mcan_transport.c`、`cycle_timers.c`、`ethercat_cycle.c`、`pdo_pipeline.c`、`ethercat_can_task.c`、`main.c`（通知），以及 `gateway_application.cpp`、`gateway_publication.cpp`、`can_transactions.cpp`、`can_bus_scheduler.cpp`、`motor_instance.cpp`、`bjcx_*.cpp`、`encos_*.cpp`、`motor_pdo.cpp`、`motor_adapter.cpp`、`motor_dictionary.cpp`、`hpm_ecat_hw.c` 的 `.text*`；
  - 库：libgcc 的 `*div*`/`*mul*`/软浮点函数，newlib 的 `memcpy`/`memset`，FreeRTOS `tasks.c` 中的 `vTaskNotifyGiveFromISR`/`ulTaskNotifyTake`。
- 实现方式：通过 SoC CMake 的 `USE_CUSTOM_LINKER`，提供基于 SDK `flash_xip.ld` 的项目链接脚本，在 `.fast` 输出段里按 `*file.obj(.text .text.*)` 和 `*libgcc.a:*(.text*)` 收集。
- MCU-08：ILM 共 128 KB，先在 Ubuntu 构建的 map 里统计上面这些段的大小，并保留至少 16 KB 余量；超出时按调用频度裁掉 SSC 和维护路径。

**验收：** 步骤 0 的基准复测，单帧 `stage_device` 及解码周期数下降；单拍中"出队 → 写入"≤ 30 µs。

### 步骤 3：MCAN ISR 减肥（F5、F6、F7）

- `receive_isr`：
  - 只保存原始 header 两个字、payload、TSU tick（`TS_SEL`）和 ATB 快照，再加一个 `enqueued_us`；
  - `observed_ms` 和 EOF 换算到 µs，都由任务出队时完成；
  - LED 改为 ISR 只置位标志，由 1 ms tick 点灯和熄灭；
  - `dcu_can_channel_config()` 改成文件内联的 `s_active_mask` 判断；`dcu_cycle_event_enabled()` 改为读一个原子缓存标志。
- `collect_tx_eofs`：同样只存原始 tick，换算放到 `dcu_can_take_tx_event`。
- `CONFIG_CAN_BATCH_SAMPLE` 生产默认改为 OFF，只在诊断预设打开。打开时也改用 `mcycle` 计时。
- GPTMR2 周期通道：任务进入 `WAIT_CAN_FEEDBACK` 后，周期 tick 只做看门狗检查，不再发通知；或者把看门狗改成在截止时刻触发的单次比较。帧间隔通道不受影响。
- 如果步骤 0 证明 GPTMR1 读取慢，`dcu_time_now_us()` 改用 MCHTMR（24 MHz）右移换算；ISR 内统一只读一次时间。

**验收：** 步骤 0 的逐中断统计，MCAN 每次中断平均周期数下降到 5 µs 等价以内；一拍内 GPTMR2 次数下降。

### 步骤 4：解码去软浮点（F1、F2）

- 首选：周期路径改成整数运算。
  - BJCX：从 IEEE754 单精度位直接拆出指数和尾数，用 64 位整数乘以定点比例（`π·1e6/180`、`π·1e6/30` 的 Q 格式），再用整数舍入；NaN/Inf 和越界判定逐位处理。
  - ENCOS：线性映射 `r0 + v·(r1−r0)/(2^n−1)`，在配置阶段预算整数斜率和截距（Q32），周期内只做乘加和移位。
  - 为新旧实现写逐值对照表：覆盖全量 16/12 位输入，以及 BJCX 的边界浮点值；误差 ≤ 1 个最低单位。
- 备选：开启 FPU，`RV_ARCH=rv32imafdc_zicsr_zifencei_zba_zbb_zbc_zbs`、`RV_ABI=ilp32d`。前提有三个：
  - 用 `-print-multi-lib` 确认锁定工具链带这一组合；
  - 所有静态库按同一 ABI 重编；
  - 接受 FreeRTOS 每次中断多保存约 33 个 FPU 寄存器，并在步骤 0 的统计里复核中断成本。

### 步骤 5：SM3 分段写入（F9）

- 在 3-buffer SM3 里，最后一个字节的写入完成缓冲交接，此前的写入不会被主站看到。改为：
  1. 本拍 `set_cyclic_feedback_window` 之后，把不依赖本拍反馈的区域（非严格轴、透传槽、保留字段）先写入 ESC；
  2. 每个严格轴 `stage_device` 成功后，立即把该轴 TxPDO 段写入 ESC 对应偏移（偏移来自当前布局，不手写）；
  3. 全部轴匹配后，只写板头、通道状态和最后一个字。
- 约束：
  - 每一拍必须覆盖全部字节，因为三缓冲轮换，未写字节是两拍前的内容；
  - 缺轴时不写最后一个字，主站继续读上一个完整缓冲，与严格模式"不提交新 SM3"一致；
  - 写入顺序和偏移都从当前生成的布局取，保持 Profile 驱动。
- 发布函数保留截止判断，最后一个字的写入改为内核掩码，不再关全局中断（F12）。

**验收：** 单拍中，最后匹配到 SM3 完成 ≤ 30 µs；PREOP 逐字节读回 SM3 映像，与组装缓冲一致。

### 步骤 6：取帧扫描不跨总线阻塞（F8）

- `service_cyclic_feedback`：某一路队头 TX 未终态或 `dcu_can_receive` 拒绝时，把这一路加入本轮 `blocked` 掩码，然后 `continue`，下一次 `dcu_can_oldest_rx_head` 只在 `live & ~blocked` 里挑。只有所有 live 总线都无帧或都被阻塞时才返回。
- 无帧分支仍对每路收割 TX 事件，预算改为 `bus_device_count_[c]`。

### 步骤 7：BJCX 状态轮询歧义清理（F10）

- `CanTransactions::abort_slot` 处理轮询超时时，调用驱动的 `status_poll_expired()`，清除 `waiting_for_status_`。
- `ambiguous_status_` 改为"本次轮询窗口内歧义"：等到下一次有效状态回包，并且没有在途请求时清除，不再永久置位。
- 进入严格周期 MIT 前，若轴上有内部轮询在途，按现有设计第 6.3 条撤销未发射的轮询，或者本拍不要求这一轴，避免整拍陪绑。

### 步骤 8：帧间隔进入 Profile（F11）

- 在生产 YAML 的 `channels[]` 加 `tx_gap_us`，或在 `devices[]` 加 `min_command_gap_us`，由生成器写进 `dcu_can_profile_generated.h` 的运行时表，替换 `DCU_CAN_TX_EOF_GAP_US`。
- 默认值保持 100 µs，不在本方案里放宽；是否能缩短，要先用电机手册和实测证明。

## 4. 提交与验收顺序

| 批次 | 内容 | 台架验收 |
| --- | --- | --- |
| 0 | 步骤 0 诊断构建 | PREOP 基准加一拍逐中断统计，不要求 N+1 通过 |
| A | 步骤 1 + 步骤 6 | Sync0 → 首帧 ≤ 60 µs；记录 N+1 结果 |
| B | 步骤 2 + 步骤 3 | 单帧"出队 → 写入"≤ 30 µs；MCAN 单次中断成本下降 |
| C | 步骤 4 + 步骤 5 | 13/13 轴 N+1 新反馈，每轴 TX 完成计数 +1，SM3 在 +1600 前完成 |
| D | 步骤 7 + 步骤 8 | 状态轮询超时注入后，轴能恢复就绪；改 Profile 间隔不重编 HPM |

每批都要：

- 在 Ubuntu 上执行 `python3 scripts/dcu.py build --preset hpm-release`；
- 确认动力隔离后，用受保护入口烧录，保留 SII 和启动编号日志；
- PREOP 核对 Profile 与双向映射；
- 先发一拍全零 MIT，第 N+1 帧逐轴核对本拍新反馈与 TX 完成计数。`WKC=3`、仅发出 CAN 帧或收到旧反馈都不算通过；
- 批次 C 通过之后，才按项目计划进入 60 秒和长测。
