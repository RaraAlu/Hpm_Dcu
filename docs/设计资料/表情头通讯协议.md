# Robot Head USTC V2.0 表情头通讯协议

适用于算法层通过 **RK3588 → EtherCAT → HPM DCU → `can0` → 四块头板**控制和读取表情头，也适用于原 USB-CAN 直连。本文合并 `CAN通信协议.md` 和 `CAN_ID使用说明.md`，按表情头仓库 `f278e3f` 的四个常规 STM32 工程核对。板3以 `test_stm32g474_top_mcu` 为准。DCU 部分依据 `Hpm_Dcu` `4cfea81` 的现有旁带和计划接入方式，时序结论来自源码和容量核算，实机联调待完成。

**500 Hz EtherCAT 足以承载 25 Hz 完整姿态、全部周期反馈及节流后的按需查询。** 双向数据持续交换，每个反馈 ID 仍按头板自身周期更新。四板接收任务每处理一帧便延时约 5 ms，**当前固件的完整五帧姿态以 50 Hz 连续下发会超出处理能力**。本协议的 25 Hz 节拍修订了前一份规划中关于 50 Hz 试跑的建议。

## 1. 总线、板号和报文周期

- 四块板共用一条经典 CAN，名义位率 **1 Mbit/s**，使用 **11 位标准数据帧**。协议载荷中的多字节量为**大端序**，Byte0 是首字节。与 EtherCAT 单槽对接时，`CanId` 按小端编码，CAN `Data` 原字节复制。
- 四板均接受 `0x601`～`0x605` 和 `0x620`。板2另收 `0x60F`，板4另收 `0x610`。扩展帧、远程帧和其他标准 ID 被过滤，周期反馈和心跳不会进入这些控制队列。控制接收路径固定拷贝 8 字节，算法及传输适配器应在发出前校验各 ID 的 DLC。
- 板号与工程对应关系为 1 `in_top_mcu1`、2 `in_bottem_mcu2`、3 `out_top_mcu3`、4 `out_bottem_mcu4`。`motor[i]`、`servo[i]` 均为板内零起始，标定请求的舵机号从 1 开始。全局通道编号见下文映射。

| 方向 | CAN ID | DLC | 名义周期或触发方式 |
| --- | --- | ---: | --- |
| 主站 → 四板 | `0x601`、`0x602`、`0x603`、`0x604`、`0x605` | 8 | 算法首版每 40 ms 发送一组，每个 ID 25 Hz。同组按 ID 递增顺序发送 |
| 主站 → 板2/4 | `0x60F` / `0x610` | 5 | 按需维护、查询。逐路请求，等该路两帧回齐或超时后再发下一笔 |

## 2. 普通目标下发

算法维护一份完整姿态。每组依次编码 `0x601 → 0x602 → 0x603 → 0x604 → 0x605`，每帧 DLC 8。每组使用同一份目标快照，帧内其他在用通道填应维持的目标，预留字节固定填 0。先应用实机标定限位、变化率限制，再编 CAN 字节。头板按帧解析后由控制任务分别更新目标，现有协议没有五帧提交标记、逐帧确认或目标序号。

## 3. 周期回传与解码

各板的发送任务每约 **40 ms** 尝试发一帧组合反馈，并轮询本板的组。板1与板3各三组，板2与板4各五组。相位为任务启动后的设定值，各板上电、任务调度与 CAN 仲裁会改变实际时间。发送任务构造每帧时读取当时的本地值，算法应按字段保留独立的接收时间和有效性。

| 板 | 反馈起始延迟 | 组轮询顺序 | 每种 ID 周期 |
| --- | ---: | --- | ---: |
| 1 | 0 ms | `0x781 → 0x785 → 0x791` | 约 120 ms |
| 2 | 10 ms | `0x782 → 0x786 → 0x792 → 0x7A3 → 0x7A7` | 约 200 ms |
| 3 | 20 ms | `0x789 → 0x78D → 0x794` | 约 120 ms |
| 4 | 30 ms | `0x78A → 0x78E → 0x795 → 0x798 → 0x79F` | 约 200 ms |

### 3.1 电机位置和速度

槽 A 为 Byte0–3，槽 B 为 Byte4–7。每组先读大端有符号 `int16` 位置（度），再读大端有符号 `int16` 速度（rpm）。DLC 4 时只有槽 A。源码将角度与速度向零截断并饱和到 `int16`，位置无小数倍率。位置为有效寻零后的相对角度，寻零尚未成功时回传原始累计角度。反馈中没有寻零状态位。`motor[i]` 固定对应本板 `encoder[i+1]`，按 `(ID, A/B)` 解码后查第 2.1 节绑定目标通道。

| CAN ID | 板 | DLC | A 的本地下标 | B 的本地下标 | 周期 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `0x781` | 1 | 8 | 0 | 1 | 120 ms |
| `0x785` | 1 | 8 | 2 | 3 | 120 ms |
| `0x791` | 1 | 8 | 4 | 5 | 120 ms |
| `0x782` | 2 | 8 | 0 | 1 | 200 ms |
| `0x786` | 2 | 8 | 2 | 3 | 200 ms |
| `0x792` | 2 | 4 | 4 | — | 200 ms |
| `0x789` | 3 | 8 | 0 | 1 | 120 ms |
| `0x78D` | 3 | 8 | 2 | 3 | 120 ms |
| `0x794` | 3 | 8 | 4 | 5 | 120 ms |
| `0x78A` | 4 | 8 | 0 | 1 | 200 ms |
| `0x78E` | 4 | 8 | 2 | 3 | 200 ms |

离线解码向量 `0x781`、DLC 8、`00 5A FF F6 FF D3 00 14` 表示 A=`90°/−10 rpm`，B=`−45°/20 rpm`。

### 3.2 舵机软件输出

每帧 DLC 8，Byte0–3 为 A，Byte4–7 为 B，各为大端 IEEE-754 `float32`，先组装位模式再按位解释。值表示方向反转前、相对各自标定零位的**软件逻辑偏移**。舵机没有角度传感器，且接收任务与缓动任务共用 `target_angle`，5 ms 输出更新前可能短暂读到新命令值。板4舵机5–7可逐路发 `0x610` 的 `0x0C` 查询，从 `0x628` 得到绝对逻辑输出。

| CAN ID | 板 | A | B | 周期 |
| --- | ---: | --- | --- | ---: |
| `0x7A3` | 2 | `servo[0]`，全局 35 | `servo[1]`，全局 33 | 200 ms |
| `0x7A7` | 2 | `servo[2]`，全局 39 | `servo[3]`，全局 37 | 200 ms |
| `0x798` | 4 | `servo[0]`，全局 24 | `servo[1]`，全局 23 | 200 ms |
| `0x79F` | 4 | `servo[2]`，共用全局 31 | `servo[3]`，共用全局 31 | 200 ms |

发送函数按组合首下标 `0、2` 从定义数组选 ID，接口按表中四个实际报文接收。

### 3.3 心跳

DLC 4，`[board_id, counter, 0xA5, 0x5A]`，每板约 4000 ms。计数按 U8 回绕，启动后可用首个有效样本建立该板状态。首次心跳按 40 ms 循环检查，因此存在粒度和启动相位偏差。

| --- | ---: | ---: | ---: |
| `0x700` | 1 | 500 ms | 4000 ms |
| `0x701` | 2 | 1500 ms | 4000 ms |
| `0x702` | 3 | 2500 ms | 4000 ms |
| `0x703` | 4 | 3500 ms | 4000 ms |

## 4. PID 与系统信息

请求 `0x620`、响应 `0x621` 均 DLC 8，按需触发。一次只保留一笔未完成的同类请求，用响应的 Byte1–3 与请求匹配。响应缺少事务序号和操作码，超时后的迟到帧可能与下一笔同字段请求冲突。维护操作安排在完整姿态组之间，保存或恢复前暂停姿态流，写入后逐项读回。

| 字节 | 请求 `0x620` | 响应 `0x621` |
| --- | --- | --- |
| 0 | 操作码 | `0` 成功，`1` 参数错误，`2` QSPI 错误。源码还定义 `3` 忙、`4` CRC 错误，当前处理路径只返回 `0…2`。队列满或发送失败可导致无响应 |
| 1 | 高四位板号 `1…4` 或广播 `0`，低四位本地电机下标 | 回显复合地址 |
| 2 | `0` 速度环，`1` 位置环 | 回显环路 |
| 3 | 参数编号，操作 `5` 时选信息项 | 回显编号 |
| 4–7 | 大端有符号 `int32` 参数值 | `0/5` 成功时返回读取值，`1…4` 成功时回显值 |

| 操作 | 行为 |
| ---: | --- |
| 0 | 定向读取一个电机的一个参数。板1/3电机下标 `0…5`，板2/4为 `0…4` |
| 1 | 写运行时 RAM。低四位 `0xF` 可对本板所有电机应用 |
| 2 | 写 RAM 并把本板全部电机、两个环路现值存入 QSPI。低四位 `0xF` 可批量修改 |
| 3 | 保存本板所有电机、两个环路现值，忽略低四位、环路和参数编号 |
| 4 | 恢复本板编译默认值并保存，作用域同操作 3 |
| 5 | 只读系统信息。定向板号，低四位和 Byte2 可填 0，Byte3 选信息项，Byte4–7 填 0 |

广播写入可执行，四块板均无 `0x621` 响应。广播操作 `0/5` 忽略。要求持久化结果时用定向操作，QSPI 报错后 RAM 仍可能已改变。下发的保存、恢复命令应由维护接口显式触发。

| 参数编号 | 参数 | 原始整数换算 |
| --- | --- | --- |
| 0、1、2 | Kp、Ki、Kd | 参数 × 100000 |
| 3、4 | 输出上限、下限 | 参数 × 100 |
| 5、6 | 积分上限、下限 | 参数 × 100 |
| 7 | 积分分离阈值 | 参数 × 100 |
| 8、9 | 积分分离、抗积分饱和使能 | 0 / 1 |

四板编译默认速度环 `Kp/Ki/Kd=6.0/0.1/30.0`，输出 ±1000，积分 ±600，积分分离阈值 100。位置环 `2.2/0.014/0`，输出 ±300，积分 ±30，积分分离阈值 60。两环默认开启积分分离和抗积分饱和，有效 QSPI 记录优先。操作 `5` 的信息项 `0…4` 依次是固件版本 `0x00020000`、硬件版本 `0x00010000`、板号、电机槽位数、存储格式版本 `1`，返回原始整数。

**首个只读联调向量**可查询板4电机槽数。下发 `0x620` DLC 8 `05 40 00 03 00 00 00 00`，成功响应 `0x621` DLC 8 `00 40 00 03 00 00 00 05`。

| 4 | `0x610` | `0x626` | `0x628` |

请求为 `[cmd, servo_id, value_hi, value_lo, flag]`。`servo_id=1…7` 对应 `servo[0…6]` / PWM1…7。角度 value 为 BE `int16(度 × 100)`。`0x0D` 的 value 为 BE `uint16`。未使用字段填 0。

| `cmd` | 功能与发包条件 |
| --- | --- |
| `0x01`、`0x02` | 进入、退出标定模式，忽略其余字段，无自动回包 |
| `0x03` | 选择舵机 1–7，无自动回包 |
| `0x04` | 设置绝对逻辑角度，无自动回包 |
| `0x05` | 相对上一目标角度增量微调，无自动回包。超时后的自动重发会重复叠加 |
| `0x06`、`0x07`、`0x08` | 保存当前缓动输出为零位、最小限位、最大限位。等待输出到位再发，需处在标定模式 |
| `0x09`、`0x0A` | 保存或恢复默认并保存本板全部 7 路，ID 可为 0，执行后反馈当前选中路，需处在标定模式 |
| `0x0B` | 设置方向，`flag=0` 正向，非零反向，需处在标定模式 |
| `0x0C` | 查询单路，ID 0 查询全部。单路依次尝试发两帧，全部尝试发 14 帧 |
| `0x0D` | 设置单路缓动系数，0 为直达，上限 30000，单位 0.1 ms/deg，需处在标定模式 |

`0x06…0x0B` 和 `0x0D` 执行后立即保存并反馈。`0x04/0x05` 在普通模式也可用。普通位姿帧在标定模式仍可覆盖目标，标定期间应暂停相关帧。默认零位/最小/最大为 `90°/0°/180°`，有效 Flash 标定优先。默认缓动系数 `100`，即 10 ms/deg，插值更新每 5 ms，单次最长约 3000 ms。板2默认全正向，板4默认舵机4反向。

| 字节 | 零位/限位 `0x625/0x626` | 方向/缓动/输出 `0x627/0x628` |
| --- | --- | --- |
| 0 | `servo_id` | `servo_id` |
| 1 | 标定模式，`0/1` | 反向标志，`0/1` |
| 2–3 | BE `int16` 绝对逻辑零位 × 100 | BE `uint16` 缓动系数，0.1 ms/deg |
| 4–5 | BE `int16` 绝对逻辑最小限位 × 100 | BE `int16` 当前**绝对**逻辑输出角度 × 100 |
| 6–7 | BE `int16` 绝对逻辑最大限位 × 100 | Byte6 最近一次 Flash HAL 状态（0 成功），Byte7 失败阶段 |

失败阶段 `0` 无失败，`1` 保存取锁，`2` 擦除，`3` 写入，`4` 回读，`5` 校验，`6` 加载取锁，`7` 加载读取，`8` 记录无效。逻辑角度在方向反转之前。按需读取示例 `0x610` DLC 5 `0C 05 00 00 00`，等待板4的 `0x626` 和 `0x628`，两帧 Byte0 都为 `05`。全部查询在板内连发，各次发送允许失败且应用层无补发，线上优先逐路查询。把周期输出、标定回包和 CAN 发送完成分别记录。

## 6. 500 Hz EtherCAT 容量与节拍

500 Hz 是 EtherCAT 主站交换过程数据的频率，周期 **2 ms**。生产档 1 的头手专线在 `can0`，上下行各一个槽；[生产十拍排程](../当前说明/按启动配置生成周期布局.md#表情头与双手旁带)与下文针对头板处理能力的 25 Hz 联调建议是两件事。

| 环节 | 名义容量或需求 | 对接口的含义 |
| --- | --- | --- |
| RK → HPM → CAN | 2 ms 一帧，PDO 侧上限 500 帧/s。混合档以现有串行发送门控和 `can0` 配额 1 帧/2 ms 估算 | 25 Hz × 5 = 125 帧/s，占下行发布机会约 25%。维护请求共享这些机会 |
| CAN → HPM → RK | 每拍一槽，PDO 侧上限 500 帧/s | 常态是四板各 25 帧/s 组合反馈，加四板心跳合计 1 帧/s，共约 101 帧/s。按需应答额外占用槽，突发帧可顺延 |
| 专用经典 CAN 物理总线 | 25 Hz 姿态加常态回传共约 226 帧/s。用每帧 135 bit 作无错保守估算，约 30.5 kbit/s | 约占 1 Mbit/s 的 3.1%，不含错误重传和按需流量。仲裁与调度仍影响瞬时延迟 |
| 四块 STM32 各自的 RX 接收任务 | 深度 10 的软件队列，每取一帧解析后 `osDelay(5)`，且 RTOS tick 为 1 ms。持续处理量约 200 帧/s/板，实际还受任务和维护命令影响 | 五个控制 ID 及共享 `0x620` 都消耗每块板的接收机会，即使该帧在本板没有执行通道。25 Hz 普通控制每板约 125 帧/s，50 Hz 为 250 帧/s，会持续积压直至丢帧。40 Hz 是按 5 ms 算出的无余量理论点 |
| 头板电机和底板舵机的应用任务 | 普通电机位置控制任务约 5 ms，板2/4舵机目标及缓动更新约 5 ms | 命令需先通过接收队列，5 ms 控制周期无法把整组控制变成同一次同步更新 |

**建议的 25 Hz 下发时刻**为每 40 ms 提交一份完整姿态，由 DriverModule 在第 `N、N+3、N+6、N+9、N+12` 拍分别写入五帧，即 `0、6、12、18、24 ms`。这样用 6 ms 的 PDO 下发间隔给头板约 5 ms 的帧处理留出余量。下一组在 `N+20` 开始，其余拍写空批并按既有周期维护板级会话。若在连续五拍写，共需五个机会，第一到第五个写入时刻相隔至少 8 ms，头板空队列时从处理第一帧到处理第五帧仍需约 20 ms。两种排程均需用 CAN 抓包和头板计数验证，报文实际到达可受控制器发送与仲裁影响。

主动查询优先排在完整姿态组间隙，维护事务逐笔查询和匹配。若用 `0x0C` 一次查 7 路，理论会产生 14 帧；即使全部收到，单槽也至少需要 14 个 EtherCAT 发布机会，周期流量还会占槽。头板 TX FIFO、HPM RX FIFO 和软件队列、主站调度均是突发约束。更高的完整姿态频率需要先验证或调整头板接收任务，增加 EtherCAT 频率不会改变该任务的 5 ms 处理节拍。

## 7. USB-CAN 迁移到 EtherCAT-CAN

两种方式共用第 1～5 节的 CAN ID、DLC、字节序和量纲，算法可复用编码器与解码器。以接入层替换旧上位机对 `can.Bus` 的访问，上层保留完整姿态、反馈缓存及维护事务状态。

| 项目 | 原 USB-CAN | 新 EtherCAT-CAN |
| --- | --- | --- |
| 发包路径 | 上位机用 PCAN/gs_usb 后端调用 `bus.send()`，旧 GUI 的“全部发送”循环提交 5 帧，普通控制由操作触发 | 算法提交完整目标给 `DriverModule`，该模块在 2 ms 周期按计划写 PDO，HPM 在 `can0` 上发出 CAN 帧 |
| 接收路径 | `bus.recv(timeout=0.1)` 在后台线程等待来帧，GUI 约每 80 ms 扫描显示队列。等待超时与 UI 刷新是主机参数 | HPM 收入队列，SM3 每拍最多取一帧。RK 按板头新 `PublishSeq` 和槽的 `Valid` 消费，每帧打 RK 单调接收时间 |
| 节拍与回包 | 五次 API 调用间隔由软件、适配器及 CAN 仲裁决定。已有标定界面约每 100 ms 查询当前路 | 五帧由 DriverModule 按 PDO 节拍发送。CAN 回包、反馈异步出现，可在后续窗口到达，组内、组间与维护调度由驱动管理 |
| 发送与故障观测 | 可观察 USB 后端错误和外部 CAN 抓包 | 分别观察 OP/WKC、PDO 序号、丢弃、`can0` 状态、CAN 发送终态及设备回包。PDO 被接收、CAN 上总线和头板消费是不同事件 |

### 7.1 RK 与算法接口约定

- **控制入口**接收整组姿态及其生成时间和过期时刻。运输帧字段为 `channel=0, can_id, flags=0, dlc, data`。驱动用有界队列，只替换尚未开始的旧组。同一组发送途中保持顺序，维护查询排在组间。取消、过期和拒绝需反馈给算法。
- **状态输出**将每条上行原始 CAN 帧连同会话 ID 和 RK 单调接收时间发给算法。算法按 CAN ID/DLC 校验后更新电机、舵机或心跳缓存，并跟踪维护请求。RK 接收时间描述主站看到帧的时刻，头板报文缺少传感器采样时间和逐帧序号。
- **PDO 绑定**用与 HPM 镜像同次构建生成的契约，PREOP 核对 Profile、映射与偏移后进入 OP。生产档 1 下行 `0x1640 → 0x7300`、上行 `0x1A41 → 0x6400`，每方向 12 B：`+0 CanId`（LE U16）、`+2 Dlc`、`+3 Valid`、`+4 Data[8]`。有效帧写 `Valid=1`，无帧写 0。上下行分别复用板头的 `CycleSeq` 和 `PublishSeq`，没有单独的批号。
- **掉线和恢复**时停止提交新目标、清除旧会话待发帧和缓存有效性。DCU 停止转发后，已送达头板的目标仍由头板处理。实际失联输出、寻零边界和整机停机策略在联调确认，恢复时用新会话、新反馈及已确认的初始目标重新启动。

### 7.2 联调通过条件

1. 先抓取 USB-CAN 或分析仪基线，核对 16 种组合反馈、4 个心跳 ID、DLC、轮询周期，并完成 `0x620` 只读查询。确认同一条 CAN 上的控制发送权归属。
2. 切到 DCU，按同一只读向量逐字节比对 SM2、物理 CAN 和 SM3，记录新批次、实际 CAN TX/回包、查询往返时间，以及现有电机业务的 WKC 和周期反馈。
3. 用经标定的低幅度姿态做 25 Hz 连续联调，检查每组五帧顺序、组内间隔、全部反馈 ID 的消息数和年龄。在头板读 `fdcan1_rx_fifo0_lost_count`、`fdcan1_rx_queue_drop_count`，在 DCU 读透传/通道丢弃与总线状态，核对运行期间丢弃增量为零。头板 RX 计数属于调试观测量，算法可见性需台架读取确认。
4. 对单路标定只读查询检查两条反馈齐全。验证断链、退 OP 和重连后，过期目标不会再次上总线。联调记录应区分 CAN 波形到达、头板接收任务处理、执行器更新，以及 RK 首次读到反馈的各段时间。
