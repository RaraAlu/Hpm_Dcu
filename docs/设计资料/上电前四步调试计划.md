# 上电前四步调试计划

日期：2026-11-17。状态：首轮实板初始化路径已通过，重复性复验和物理总线验收待实施。实际镜像、数据变化和证据见[首轮实板调试记录](../验证记录/2026-11-17-上电前四步首轮实板调试记录.md)。

目标是在电机动力隔离、外部总线无业务报文的条件下，依次确认 SDK 启动、板级初始化、EtherCAT 硬件初始化和四路 CAN 初始化。停止点是 `main()` 内 `dcu_mcan_init()` 返回后的状态检查处，不继续执行 `motor_control_init()`、SSC 初始化或 RTOS 启动。

这是一轮初始化调试，不是 MCU 任务循环或 EtherCAT/CAN 数据回环验收。当前版本不能直接继承此前 C 基线的实板结论。

## 实施边界

- 最初准备阶段只编写计划、构建 Debug 镜像并执行离线检查；其后经用户单独确认，已完成首轮目标操作。本计划不构成后续硬件操作的自动授权。
- 保留现有固件、板级配置和 VS Code 调试配置，不增加测试宏、自动运行脚本或绕过保护的入口。
- 以后实施时使用现有受保护入口；每次目标操作单独确认。`verify` 和两个 F5 入口都会复位、执行探测算法并暂停目标，不属于无扰动读取。
- 第三步可能初始化、迁移或更新 Flash 中的 SII 数据。即使不重新烧录应用，运行初始化也可能写入保留区，必须先确认有效备份及允许此类写入。
- 前四步不发送 CAN 测试帧，不请求 EtherCAT OP，不进行电机使能、参数 Apply/Save 或故障注入。

## 四步检查表

表中源码行号对应本次准备快照。实施前以实际 ELF 的行表及反汇编重新确认位置，不能在源码或镜像变化后照搬地址。

| 步骤 | 执行范围与停止点 | 观察项 | 通过标准 | 失败时保留的证据 |
| --- | --- | --- | --- | --- |
| 1. SDK 启动 | 复位暂停后，确认预设的 `main` 硬件断点有效，再手动运行到 `main`；不得先放行板级初始化 | PC/SP、源码对应关系、异常/复位情况；抽查已知 BSS 状态，例如 CAN 的 `s_initialized` 初值 | 到达当前镜像的 `main`，栈地址落在链接布局允许范围，抽查初值正确；不出现异常循环 | GDB/OpenOCD 日志、PC/SP、可用的调用栈；异常时再安排 `_start`、`reset_handler`、`system_init` 逐段定位 |
| 2. 板级初始化 | 从 `main` 运行到 `ecat_hardware_init` 入口，尚不执行其函数体 | `board_init`、LED 引脚、`dcu_timebase_init`、1 ms 板级定时器、ESC 引脚初始化；时间基准使用 MCHTMR 24 MHz 和 GPTMR1 1 MHz | 没有走时间基准失败返回；能到达下一入口；相关配置与源码一致。不同检查点的计数快照可辅助确认计数器推进 | 失败位置和返回值、相关时钟/定时器配置、串口日志（具备串口采集条件时） |
| 3. EtherCAT 硬件初始化 | 运行到 `main.c:52`，即 `ecat_hardware_init` 返回后的状态检查处 | `stat`；EEPROM 模块 `g_initialized`；SII 校验结果；PHY 配置结果；`pEsc`、ESC 中断和 1 ms 定时器配置 | `stat == status_success`，EEPROM 初始化完成，SII 无未解释校验错误，PHY/ESC 配置完成；未接网线时不以链路未建立判失败 | 原始返回值、EEPROM/PHY 日志、备份路径及摘要、相关状态快照。返回成功不抵消 EEPROM checksum 警告 |
| 4. 四路 CAN 初始化 | 运行到 `main.c:61`，即 `dcu_mcan_init` 返回后的状态检查处；本轮到此停止 | `stat`、CAN 模块 `s_initialized`；四路 Message RAM/FIFO、时序和中断配置；空闲时的队列/丢帧计数；收发器使能实现及外部约束 | `stat == status_success` 且 `s_initialized == true`；四路控制器配置完成，不存在 RAM 重叠或未解释错误。源码配置为仲裁段 1 Mbit/s、数据段 5 Mbit/s，RX FIFO0 16 项、TX FIFO 8 项，数据槽 8 字节 | 失败总线索引、`status`、对应配置和错误状态；不强制改返回值，不跳过失败继续业务初始化 |

四步检查均通过后，仍停在 `main.c:61`。只读取和保存已批准的状态，不继续到 `main.c:66` 的 `motor_control_init()`。

首轮核实 `board_can_transceiver_phy_set()` 为空实现。是否由硬件常使能尚未确认，收发器物理状态必须单列待验，不能以该接口调用完成作为使能证据。

步骤 1 的结果只能证明已检查的启动路径到达应用入口，不能据此宣称 SDK 每个初始化分支、全部 C++ 对象状态或独立冷启动均已验收。步骤 3、4 的结果只证明初始化和静态配置，不证明中断真实触发、PHY/CAN 电气波形或端到端通信正确。

## 断点与观察方法

1. 首次连接后保持暂停，确认 `DCU_DEBUG_READY`、镜像匹配和 `main` 硬件断点已建立，再手动继续。连接后的第一停点不保证已经是 `main`。
2. 按检查表逐段替换硬件断点。同一时刻只保留本阶段必要断点，不假设有足够资源一次设置全部停点；已有验收只覆盖单个硬件断点。
3. 每次继续前核对实际断点地址和状态。Flash XIP 不使用会改写代码的普通软件断点。源码行无法准确定位时，依据当前 ELF 反汇编在调用返回后的指令处设置硬件断点。
4. 优先运行到阶段边界，不在 Flash 擦写、PHY 延时或轮询等待中反复单步。不要用 `return`、改 PC、改 `stat` 或直接写寄存器来绕过失败。
5. Watch 只放变量和已确认可安全读取的状态，不调用目标函数，不批量展开可能有读副作用的外设寄存器，不读取接收 FIFO 来代替正常驱动消费。
6. 本次不依赖 SVD、RTOS 视图或复杂 C++ pretty-printer。暂停前后的计数只能辅助判断状态，不用于计算真实周期、抖动或停机时延；不能假设 CPU 暂停时所有外设也停止。
7. 发生异常复位、镜像不匹配、初始化失败或越过停止边界时，停止后续放行并保留现场。不得通过自动重烧、格式化 EEPROM 或断点屏蔽来消除症状。CPU halt 不能替代动力隔离和独立安全措施。

建议先做一轮完整分段检查；成功后再按相同边界复验两轮，每次复位仍需单独确认。三轮仅用于初步重复性检查，不代表可靠性统计或脱离调试器启动验收。
