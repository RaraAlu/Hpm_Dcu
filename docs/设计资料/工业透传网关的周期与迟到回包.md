# 工业透传网关的周期与迟到回包

**结论：不让 EtherCAT 周期等待某个 CAN 应答。** 下列三款网关都将“主站交付命令”和“主站读到已发布的接收数据”分开。差别在于是否保留未读批次、何时提交 CAN 发送、何时冻结输入。主站要判定特定设备是否在 N+1 回了本拍命令，还要识别该应答并检查读取拍号；网关确认命令批次不等于设备应答。

## Beckhoff EL6751：经典 CAN 原始帧队列

- **带缓冲。** 默认由 SM2 事件启动接口周期。输出 `TxCounter` 变化才消费新批次；发送空闲时启动首帧，否则入本地发送队列，其余帧依次排队。输入回显 `TxCounter` 表示该批已接收处理；另有最近已发送 CAN 帧的事务号。接收方向单独握手：主站确认上一批 `RxCounter` 后才交付下一批已收到的 CAN 帧。[官方 CAN 接口同步时序](https://infosys.beckhoff.com/content/1033/el6751/2519221387.html)
- **快速模式。** CAN RX 直接写三缓冲的 EtherCAT 输入映像，不再用本地 RX 队列，也不等主站逐批确认。主站只读本批计数内的有效槽，不能把其余槽的旧值当新帧。Fast CAN Queue 可选 DC：`SYNC0` 启动接口周期，`SYNC1` 触发首个 CAN 帧的发送；手册的最大 500 ns 抖动针对首帧启动，不是总线往返或收齐回包的上界。[快速队列](https://infosys.beckhoff.com/content/1033/can-interface/4727758347.html)；[SM2 与 DC 时序](https://infosys.beckhoff.com/content/1033/el6751/2519221387.html)
- **边界。** 这里讨论的是经典 CAN 接口队列，不是 CANopen 同步 PDO 或 CAN 总线上的 SYNC 报文。Beckhoff 在常见 LRW 配置下描述的“两任务周期”指 `TxCounter` 确认在任务中可见，不是设备应答固定在 N+2。它也不是 CAN FD 实测。[接口配置](https://infosys.beckhoff.com/content/1033/el6751/2519220363.html)；[EtherCAT Update 小节](https://infosys.beckhoff.com/content/1033/el6751/2519221387.html)

## esd CAN-EtherCAT/2-FD：有无未读批次确认可选

对象和页码对应型号 `C.2932.62`、手册 `C.2932.21` Rev. 1.0，不使用上一代经典 CAN 网关的对象解释 FD。[厂家产品页](https://esd.eu/en/products/can-ethercat-2)

| 观察点 | 能证明什么 |
| --- | --- |
| 主站更新 `0x7002:01`，网关更新 `0x6002:01` | 一批 CAN FD 命令已从输出映像复制到 CAN 发送队列；不是逐帧发完。最近已发送帧的事务号另在 `0x6002:04`，不是对端回传的业务序号。[手册第 47、52 页](https://esd.eu/fileadmin/esd/docs/manuals/en/CAN-EtherCAT-2_Manual_en_10.pdf#page=47) |

| `0x8000:20` 的 bit 9 开启 Fast Mode | 收到数据可逐拍写入过程映像，不等主站回写 RX 计数；主站漏读可能丢失未处理的数据。FD 的映像队列每方向最多 20 帧，还受 SM 容量限制；本地队列每方向最多 32 帧。两种容量都不是延迟保证。[手册第 53–54 页](https://esd.eu/fileadmin/esd/docs/manuals/en/CAN-EtherCAT-2_Manual_en_10.pdf#page=53) |

## 岚动 ECAN-Lite：按输入截止点发布

厂家注明下述 DC 调度语义自测试版 2.14 起适用。SM2 先验证完整 RxPDO 并准备命令，通常在 Sync0 提交已准备好的命令。只用 Sync0 时输入发布不等本批应答，通常返回前一轮；另选 Sync1 锁存输入时，CAN 回包必须在截止前处理并被选入，主站还必须在发布完成后读。迟到应答只能参加后续发布，不能追加进已冻结映像。厂商也区分了获得发送许可后才准备完的命令，不承诺其应答一定赶上原窗口。[应用手册 §4.1.1–4.1.3、技术参考 §12.9](https://lanmotion.com/en/docs/ecan-lite/)

不要照搬事件名称：EL6751 Fast DC 用 Sync1 **启动首帧发送**，这里用 Sync1 **锁存输入**。两者都不是靠让正在经过的 LRW 停下来等 CAN 回包。

有明确请求/应答语义时，可以由协议层管理跨拍事务。例如 [CANopenNode 的 SDO client](https://canopennode.github.io/CANopenNode/group__CO__SDOclient.html) 在发起上传或下载时指定 `SDOtimeoutTime_ms`，后续周期非阻塞推进直到成功或报错；这是 CANopen SDO 的例子，不表示本项目电机运行 SDO。

## 对 Dcu_dev 的含义

按本项目[周期锁存与反馈发布契约](../当前说明/周期锁存与反馈发布契约.md)，应分别记录命令接受、各轴 CAN 发送完成、各轴匹配应答、SM3 发布与 RK 实际读取。第 N 拍请求在 N+2 才读到有效应答，可以记作“晚到”，有助于区别总线丢失和错过发布窗口，但仍是 N+1 验收失败。通用透传可以跨拍交付；这不放宽生产电机的逐轴截止要求，也不是本板的性能证据。

若同轴同类应答不带请求序号，而且前后两笔都可能产生该帧，不能仅凭“下一拍收到”强行配对；没有独立证据排除上一笔迟到应答时，应标记归属不明。
