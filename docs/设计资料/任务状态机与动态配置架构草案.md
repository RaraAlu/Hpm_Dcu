# 任务状态机与动态配置架构草案

日期：2026-11-17。状态：**需求方向已记录，技术方案待逐项核对，尚未实施或验收。**

本文承接[从站预就绪与主站一次确认启动计划](从站预就绪与主站一次确认启动计划.md)，记录后续对 Profile、任务状态机及动态配置的补充要求。用户本次要求是先形成文档、后续核对；本轮不修改固件、主站、生成器或协议交付物，不连接、复位、烧录或运行目标板。

下文将用户提出的方向、当前源码事实、建议设计及待定事项分开。状态名、命令名、字段和模块划分都是设计草案，不是已存在的接口，也不在本轮冻结对象索引、二进制格式、任务数量或时间指标。

后续第一阶段已开始收敛，见[首版最小回环契约与无动作测试准备](首版最小回环契约与无动作测试准备.md)：新增单路回显试验 Profile、字节级契约及只读离线检查，尚未接入固件或实现本文状态机/动态配置。用户确认暂无外部 CAN 测试对端，内部回环与真实物理通信分层验收；不把试验字段视为生产 ABI 定型。

## 用户提出的方向

- 项目以 EtherCAT 与 CAN 设备之间的数据传输、处理和映射为主线；这里的“回环”指数据往返，不默认 MCU 承担运动控制闭环。
- 由 Profile 组织整体结构：明确使用哪些 CAN 通道、每路连接什么设备、多少个节点及其地址；Motor、灵巧手、表情头、IMU 是设备类型，不由 motor 统领网关。
- 重建原来以电机为中心的应用编排，不在旧 `MotorApplication` 外再套一层 Profile；各设备模块只承担自己的数据处理和必要协议交互。
- 通用运行层采用基于任务的状态机，能自主启动，并根据主站准备情况和自身准备情况推进、等待、暂停或恢复通信，保持快速响应。
- Profile 不局限于固件预置：支持通过状态机协调动态下发与修改，不再要求每次启动由主站逐设备、逐字段完成繁杂配置。
- 从站已经准备好且配置匹配时，主站一次应用级确认后，在协议条件满足时自动开始周期交换。
- 当前只形成待核对文档，不立即实施架构重构。

“完全抛去原来的逻辑”的建议落实范围是旧应用编排及重复配置流程，不是无条件删除 BSP、协议栈、已验证底层实现或数据正确性约束。原有运动策略是否保留、由谁承担，需要另行核对；不能通过改名把它们重新变成所有设备的通用前提。

## 当前工程事实

| 当前事实 | 对新架构的约束 |
| --- | --- |
| [设备配置](../../firmware/cfg/device_config.h)按 4 路 CAN、每路 7 个电机槽位编排 | 这是现有实现的资源模型，不是 CAN 天然只能接 7 个设备；动态配置不能增加物理控制器 |
| [应用总控](../../firmware/app/motor/motor_application.cpp)同时承担轴控制、Raw CAN、通道调度、配置、会话和诊断 | 需要按职责重建，不是仅移动目录 |
| [运行任务](../../firmware/app/runtime/ethercat_can_task.c)已有定时器通知驱动的静态 FreeRTOS 工作任务 | 可以作为任务执行基础，但没有完成本文的自举和动态配置状态机 |
| [周期入口](../../firmware/app/cycle/ethercat_cycle.c)已有 Sync0 流水线、同步检查及故障处理，仍调用 `motor_control_*` | 通用数据运行层需要替换业务接入；不能仅凭任务已经存在宣称新架构已实现 |
| [协议生成器](../../tools/protocol/generate.py)生成对象字典、线格式及 ESI/SII；[现有 CoE 入口](../../firmware/comm/ethercat/motor_coe.cpp)不支持 Complete Access | 新的 Profile 传输、状态对象及映射契约需单独实现和验证 |
| 目前生产设备驱动只有 ENCOS，IMU 尚无真实采样接入，见[设备接入规范](../当前说明/设备驱动扩展与接入规范.md) | 配置设备名称不能自动获得灵巧手、表情头或 IMU 的协议实现 |
| [首轮实板记录](../验证记录/2026-11-17-上电前四步首轮实板调试记录.md)停止于业务、SSC 和 RTOS 启动之前 | 新架构没有实板依据，原测试也不是数据回环或实时性验收 |

用户反映旧从站需要多次 SDO 才能配置启动且耗时明显；这是设计动机，不是已经测得的性能归因。后续须分别记录配置传输、主站等待、设备准备和标准 EtherCAT 启动耗时。

## 目标结构

```text
预置 Profile / 主站下发的候选 Profile
                 |
          校验、准备与版本管理
                 |
     通用任务状态机 + 统一通信调度
                 |
EtherCAT <-> 数据映射与路由 <-> 设备模块 <-> CAN
                              电机
                              灵巧手
                              表情头
                              IMU
```

此处“底层状态机”指设备业务之下的通用运行层，不把主站选择、Profile 事务或设备业务塞入 BSP、CAN 中断或 SSC 内核。

| 所属 | 职责 | 不承担的职责 |
| --- | --- | --- |
| Profile | 描述拓扑、协议引用、数据契约、资源需求及就绪/故障策略 | 不保存当前在线状态或默认动作授权，不承载任意可执行脚本 |
| 构建工具与配置工具 | 从共同契约生成固件支持表、预置配置、主站描述及可下发配置数据 | 不假设所有新协议都能仅靠填写型号自动生成 |
| 通用运行层 | 自举、状态推进、主从就绪协调、配置事务、激活、统一路由和诊断 | 不以电机轴数、Arm 或位置保持作为通用概念 |
| 设备模块 | 自身数据编解码、必要握手、反馈有效性和明确的异常行为 | 不直接占有共享 CAN 接收队列，不各建一套 EtherCAT 状态机 |
| 通信与硬件层 | 实际收发、同步、时间基准、中断及有限的紧急输出抑制 | 不决定本次启用哪个业务 Profile |

各模块“只管自己的回环”是职责独立，不等于每个模块独立启动一个无限循环或 RTOS 线程。共享 CAN 的接收分发和发送预算统一管理，避免抢帧与相互挤占截止时间。

## 配置内容与来源

Profile 的核心先保持为一张设备连接表，再引用数据契约，不重新引入大量重复配置对象。

| 信息 | 草案内容 |
| --- | --- |
| 身份与兼容性 | Profile ID、版本、配置格式版本、内容摘要、所需固件能力及布局标识 |
| 通道 | 物理通道号、是否使用、经典 CAN/CAN FD 模式及速率；必须在硬件和已实现能力范围内 |
| 设备 | 稳定逻辑 ID、设备类型、具体协议/型号、CAN 地址或地址集合、必选/可选规则 |
| 数据 | 命令和反馈字段、长度、单位/比例、字节序、有效性规则、固定槽位或支持的布局引用 |
| 调度与异常 | 交换周期、超时、资源预算、设备核验方式、故障影响范围和输出处理策略 |

设备数量从节点列表推导；逻辑槽位不由扫描顺序决定。一套灵巧手或表情头可能有多个 CAN 节点，具体以协议为准。首批实际接线、设备数量和型号未确认，本文不虚构生产拓扑。

建议同时支持两种来源，使用同一套校验与准备规则：

- **预置 Profile**：随固件提供，使 MCU 在主站缺席时能独立准备，不需要运行时读取主站源文件。
- **动态 Profile**：主站下发完整候选版本，MCU 在声明的能力和资源范围内解析、校验、准备，再通过状态机切换。

这修订了此前“修改 Profile 一律重新烧录固件”的建议：支持范围内的配置变化可以动态下发；增加未实现的设备协议、超出资源上限或引入固件不认识的数据布局，仍需要固件和配套契约升级。MCU 不必运行代码生成器或增加文件系统，源配置与线上编码格式可不同，具体格式待核对。

动态下发不等于掉电保存。建议首版先区分 RAM 中的活动配置与固件启动默认配置；若要求动态修改后断电仍能自主快速启动，必须另行设计独立配置存储、完整性校验和掉电恢复，不能默认复用 SII 保留区。持久化是否纳入首版尚未确定。

## 任务与事件模型

建议采用“事件唤醒 + 有界状态推进 + 定时截止检查”，而不是等待设备回复的阻塞式初始化。

| 逻辑任务 | 推进内容 | 执行约束 |
| --- | --- | --- |
| 协议与周期处理 | SSC/邮箱响应、Sync0、PDO 锁存与发布、CAN 收发调度 | 周期截止和协议响应优先；保持 SSC 可变状态的单一访问归属 |
| 启动与运行管理 | 加载 Profile、设备核验、就绪汇总、激活及故障恢复 | 每次只推进有限步骤，等待通过事件或定时器表达 |
| 配置事务处理 | 接收候选数据、校验、建立待用描述、协调重配与提交 | 有长度、队列、CPU 和内存预算；不得阻塞周期处理 |
| 诊断与可选维护 | 读取状态、统计、日志及将来可能的持久化 | 可延后、可限流；不进入通信快路径 |

上述是逻辑职责，不预先冻结为四个 FreeRTOS 线程。优先核对能否在现有任务所有权模型中实现非阻塞推进；需要独立任务时，再明确消息传递、状态所有者、优先级和栈预算，不能让多个任务同时修改 SSC 或活动配置。

事件至少覆盖：硬件初始化结果、CAN 收发/错误、设备核验完成、设备掉线、配置分片到达、校验结束、主站激活请求、EtherCAT 状态变化、Sync0、超时和停止请求。中断只做必要确认、快照/时间戳交接及故障输出抑制，不在中断里解析 Profile 或执行完整设备流程。

快响应约束：

- 管理通道在硬件及协议栈允许后尽早可用，不能等全部设备核验完成才开始回应主站。
- 准备中返回阶段和未就绪原因；配置处理中返回事务状态，不在 SDO 回调内等待 CAN 应答或等待 OP。
- 设备探测、配置校验和诊断各有预算，事件队列满时有明确处理，不静默丢弃关键状态事件。
- 静态上限内预留活动配置、候选配置和必要缓冲区；不得因接收大 Profile 耗尽周期路径的资源。
- 通信快速路径不执行 Flash 擦写、无限重试或动态内存分配。具体延迟上限后续测量并冻结。

## 自举与主从就绪协调

建议将本地生命周期与主站条件分开表达，不用一个“主站在线”位代表全部启动条件。

| 本地状态 | 含义与工作 |
| --- | --- |
| `BOOT` | 完成基础硬件与管理运行环境建立；不是 EtherCAT 的 Bootstrap 状态 |
| `PREPARING` | 按选定 Profile 准备资源、核验预期设备、准备数据区并维护进度 |
| `READY` | 选定集合的本地准备已满足，保持反馈新鲜；可等待主站确认或标准协议条件 |
| `RUNNING` | 对已接受的配置和会话执行周期数据交换 |
| `QUIESCING` | 为重配置或停止撤销业务输出、处理旧请求并等待明确的切换条件 |
| `HOLD` / `FAULT` | 会话中止或条件失效；保留可用诊断，按原因重新准备或等待处理 |

主站相关条件独立记录：链路及 EtherCAT 状态、所选 Profile/设备集合、配置摘要是否一致、本次会话激活是否已接受、实际映射与 DC 是否匹配、是否已收到本次会话的有效新 PDO。

| 自身准备情况 | 主站情况 | 状态机行为 |
| --- | --- | --- |
| 尚未就绪 | 主站缺席 | 自主准备，不等待主站逐设备触发 |
| 尚未就绪 | 主站已经接入 | 持续回应进度，不虚报就绪；准备完成后主站再发起一次激活 |
| 已就绪 | 主站未选择或未确认 | 维持就绪快照与诊断，不发送未经授权的业务命令 |
| 已就绪 | 匹配的激活已接受，协议条件未齐 | 保留本次有效确认并等待；不要求第二次业务确认，也不阻塞主站状态转换 |
| 已就绪 | 激活与协议条件均满足 | 自动推进到周期交换 |
| 任一关键条件失效 | 任意 | 撤销相应运行许可，清理失效会话，报告原因；不沿用旧命令自动恢复动作 |

业务输出许可的候选条件为：选定集合本地就绪、配置匹配、本次激活有效、EtherCAT/映射/DC 条件成立、命令属于当前会话且未过期。诊断读取、必要探测和协议允许的输入发布不必等业务输出许可成立；设备动作是否允许仍与 PDO 交换本身区分。

主站退出或重新连接，不必无条件重启整个 MCU；可以保留仍有效的设备准备结果，但旧会话确认和命令不能跨会话复用。故障影响局部还是整组由 Profile 的冻结规则决定，不能默认为任何设备故障都停止全部设备。

本地状态不替代 EtherCAT 状态机。PREOP 可以进行邮箱通信但不交换过程数据，SAFEOP/OP 具有不同的输出条件；确认已经接受不等于 OP 已成立。标准状态转换仍由协议协调。[EtherCAT 状态机依据](https://infosys.beckhoff.com/content/1033/tc3_io_intro/1446518411.html)

前一份启动计划中的 `ARMED` 只是“应用确认已接受”的候选命名。本文建议将其表达为独立的会话确认状态，避免与电机 Arm 混淆；最终命名待统一。

## 动态下发与修改事务

建议明确分离 **活动配置 Active** 与 **候选配置 Candidate**。运行期间读取活动版本，下载或编辑只影响候选版本；不允许把半份配置直接写入正在使用的路由或 PDO 内存。

```text
接收候选 -> 完整性与语义校验 -> 等待重配窗口（如需要）
                                     |
                                 资源与设备准备
                                     |
                                  待激活 READY
                                     |
                              一次激活与版本提交
                                     |
                         协议条件满足后运行新版本
```

| 阶段 | 必须表达的行为 |
| --- | --- |
| 开始 | 标识事务、目标 Profile、基于哪个活动版本修改、总长度及预期摘要；先检查容量与控制权 |
| 接收 | 有界分片组装，检查偏移、长度、重复片及内容冲突；中断、超时或取消不能污染活动版本 |
| 校验 | 检查完整性、格式版本、协议支持、地址/路由冲突、布局、资源、带宽及策略合法性 |
| 准备 | 建立待用配置描述并核验就绪；需要改变共享硬件时，先报告影响并取得明确的重配请求，再进入静止窗口 |
| 激活 | 主站对已准备的候选版本及就绪快照确认一次；检查会话、基准版本及快照是否过期 |
| 提交 | 在规定的切换点使路由、配置和数据版本一致生效，隔离旧队列与旧 PDO；不让部分设备先按新版本输出 |
| 结果 | 分别报告接收完成、校验通过、准备完成、激活接受、版本生效和运行状态，不用一个“成功”混淆各阶段 |

这里“通过状态机下发与修改”指由状态机管理事务和生效过程，实际数据仍通过明确的通信对象传输。建议优先评估 CoE/SDO 的整块配置事务；对象索引、分段方式、编码和大小上限待核对，不能假定当前接口已支持。修改首版可采用重新提交完整候选快照，差量修改不是必要前提。

大 Profile 允许有多个传输报文；“一次确认”指准备完成后的一次业务激活，不是把整个配置下载压成一个 SDO 帧。正常启动复用已准备版本，无须重复下载配置。CRC 或内容摘要只用于一致性检查，不能代替写入权限或身份认证；控制权、并发请求及安全边界需要在接口设计时落实。

重复请求必须有明确语义：同一会话、事务和相同内容返回已有结果，不反复初始化；相同标识却内容不同、基准版本过期或来自旧会话的请求拒绝。事务超时、取消和失败原因均可查询。

## 哪些修改需要暂停

动态调整不等于所有字段都能在 OP 中无扰切换。建议首版采用保守分级，白名单之外的变化都需要重新准备。

| 变化类别 | 建议处理 |
| --- | --- |
| 已准备 Profile 或设备集合的选择 | 在资源兼容、布局匹配和就绪有效时走一次激活；运行中切换仍须定义旧会话的退出点 |
| 不改变布局、硬件和设备协议的纯策略参数 | 只有经过明确列举与验证的字段才允许周期边界提交；不能默认所有阈值都可热改 |
| 设备数量、地址、通道角色、协议或 CAN 速率变化 | 静止受影响范围，清理待发请求、重配和核验；不能一边按旧拓扑控制，一边切换同一总线 |
| PDO 布局、大小或同步周期变化 | 退出相应周期运行，完成主从协议重配置；不在 OP 中偷偷调整字段偏移 |
| 未实现的协议、超出硬件或编译资源能力 | 拒绝动态配置，明确要求固件或硬件升级 |

建议动态 Profile 优先使用固件和主站共同支持的固定槽位或预定义布局。配置可以动态绑定设备，但不能凭下发任意字段就在运行时生成一份新的 ESI/SII。引入未声明的数据契约，需要配套更新生成链、固件和主站；是否采用通用数据容器留待核对，不在本文默认实现。

候选版本接收和离线校验期间，旧版本可以继续运行的前提是资源隔离和周期预算已经验证。准备工作若改变物理通道，旧版本就不再具有无扰继续运行的条件；不能把“保留旧配置字节”当作已经回滚硬件。变更失败后若无法验证恢复，应进入 `HOLD` / `FAULT`，不得自动恢复动作。

提交前后要处理在途 CAN 应答。仅清空软件队列不足以证明延迟回复属于新配置；优先利用协议序号/身份匹配，不具备关联能力时必须定义隔离等待、重新核验或拒绝无扰切换的规则。

## 快速启动与配置变更的区别

| 路径 | 主站上线后的工作 | 启动结论 |
| --- | --- | --- |
| 匹配的预置或已准备配置 | 读取紧凑就绪摘要，提交一次激活，完成必要标准协议步骤 | 目标快速路径，不逐设备配置 |
| 新下发或修改配置 | 完成配置事务、校验和必要重新准备，再一次激活 | 是动态配置路径，不能计作同条件的快速启动 |
| 主站提前接入 | 读取准备进度，待目标配置就绪后激活 | 不阻塞管理响应，不保证设备准备已经完成 |
| 配置或设备不匹配 | 返回差异与原因，等待明确处理 | 不静默采用另一份配置或伪造就绪 |

激活快路径只做有限校验和状态提交，不扫描设备、不重新初始化外设、不写 Flash、不阻塞等待设备回复。准备耗时可以前置，但不能隐去；动态配置带来的暂停和重新准备时间要单独统计。

## 重构与保留范围

建议重建的是应用组织方式、启动流程、配置入口和通用数据契约，不以兼容旧内部接口为理由继续让新模块依赖 motor。迁移期可以有明确、可撤销的适配，但目标不是永久维护两套活动配置来源。

- 电机、灵巧手、表情头和 IMU 不继承同一个“轴控制”模型，只共享必要的准备状态、数据传递和诊断契约。
- 当前运动启动、限值与停止策略逐项分配给主站、网关或设备；确认职责和验证后再决定删除或保留，不能一刀切取消保护。
- 保留长度/越界检查、有效位、真实数据年龄、同步截止、故障输出约束和会话隔离等正确性要求，不要求保留其旧实现形式。
- BSP、CAN、SSC、时间基准与流水线按实际适用性复用；改变第四步 CAN 配置、任务模型或同步路径时必须重新验证，不能沿用冻结镜像的硬件结论。
- 新旧对象字典、PDO、主站工具和配置文件的兼容范围必须明确；接口破坏性变化不通过仅改版本号或更新测试摘要来宣称兼容。

## 后续核对与验收

以下均未实施；先核对需求和接口，再安排实现及单独授权的硬件验收。

| 场景 | 验收重点 |
| --- | --- |
| 无主站上电 | 按启动 Profile 自主核验和准备，不自动触发执行器动作 |
| 主站早到或晚到 | 始终能在协议允许时读取状态；双方就绪后无需重复业务确认 |
| 正常快速启动 | 不重复下载逐设备配置；记录业务激活次数、SDO 事务数/字节数和首个有效 PDO 时间 |
| 大配置分片、重复、缺片、冲突、超时 | 有界处理，候选与活动版本隔离，失败结果明确 |
| 配置越界、未知协议、超预算 | 拒绝并保持已知状态，不分配无上限资源或隐式降低周期要求 |
| 接受确认后设备变化或主站断开 | 就绪和会话许可失效，旧数据不进入新会话 |
| 运行中动态修改 | 周期与管理响应预算成立；需要暂停的修改明确报告，不伪装成无扰切换 |
| 切换时旧 CAN 回复或旧 PDO 到达 | 不被误当作新设备、新版本或新会话数据 |
| 重配失败及可能的掉电 | 不报告部分成功；若实现持久化，单独验证恢复过程和版本来源 |
| 满资源与通信压力 | 队列溢出、CPU、栈、候选配置峰值 RAM、CAN 带宽和截止行为均可观测 |

时间指标沿用[启动计划](从站预就绪与主站一次确认启动计划.md)的分项口径，新增配置传输/校验/准备/切换耗时及管理响应最大延迟。保持现有同步目标，不以放宽实时要求换取配置功能通过；具体阈值、负载和样本量待核对，不承诺未经实测的毫秒数。PDO 通信启动与 CAN 对端真实往返分开验收。

待核对事项：

1. 首批实际 CAN 拓扑、各设备协议和无动作核验能力；不默认未实现的设备已受支持。
2. Profile 最小字段、版本规则、线上编码、传输长度与事务超时；不将其设计成任意脚本引擎。
3. 固件支持的固定槽位/布局集合及动态调整范围，主站配套描述如何分发和核对。
4. 动态配置是否要求跨掉电保存，以及启动默认来源、恢复方式和 Flash 分区。
5. 哪些变化允许不中断周期处理、哪些必须暂停；共享总线影响范围及在途回复隔离。
6. 逻辑任务如何映射到 RTOS 线程，SSC 与状态所有权、优先级、队列、内存及时间预算。
7. 激活、断链、设备故障后的重连规则，以及运动授权和安全职责如何分配。
8. 旧主站和旧协议是否需要兼容，替换顺序、测试基线及后续实板范围。
