# 首版最小回环契约与无动作测试准备

更新：2026-11-18。状态：**试验契约已建立，层 B 就绪与一次确认核心已完成离线验证，未链接至运行镜像；独立层 C 首轮实板 12 帧通过，物理往返、线上的确认和周期运行仍待实现及联调。**

本文将[任务状态机与动态配置架构草案](任务状态机与动态配置架构草案.md)收敛到一个可逐项验证的最小数据通路。这里的“回环”是数据往返，不是电机控制闭环。字段和数值是本轮提出的试验基线，仍可评审修改，不代表生产 ABI、设备拓扑或性能指标已定型。

**现场条件：用户已确认目前没有 CAN 测试对端。** 最初契约准备阶段只处理主机材料，未访问板卡；后续经重新授权，已用独立测试镜像完成[MCAN0 内部回环首轮实测](../验证记录/2026-11-17-MCAN0内部回环首轮实板测试记录.md)，不需要外部对端，也未改动生产对象字典、ESI/SII 或 `motor`。前四步结论仍只适用于[初始化首轮记录](../验证记录/2026-11-17-上电前四步首轮实板调试记录.md)的另一份冻结镜像。

## 最小范围

| 项目 | 首版选择 | 边界 |
| --- | --- | --- |
| 设备 | 一路 CAN、一个可控回显对端，逻辑 ID `probe0` | 验证通路，不冒充 motor、灵巧手、表情头或 IMU 的真实协议 |
| 通道 | Profile `bus=0`；现有代码映射到 MCAN0、物理 CANFD1 | 这是软件映射，不是现场接线确认；其余通道不承担此试验的业务 |
| CAN | 经典 CAN，1 Mbit/s，标准数据帧，DLC=8；请求 `0x600`，回复 `0x601` | 不接收 RTR、扩展帧或 FD 帧；发送方不设置 FD/BRS；不是修改现有默认 FD 配置 |
| PDO | 从站 RxPDO 32 字节，TxPDO 48 字节，试验周期 1 ms | Rx 指主站到从站，Tx 指从站到主站；不是现有产品 PDO 布局 |
| 交换节奏 | PDO 每周期刷新，CAN 请求间隔至少 10 ms，一个在途请求 | 先验证数据因果关系，不以此证明最大 CAN 吞吐或 1 us 抖动 |
| 配置 | 单个完整预置 Profile、版本和内容摘要，激活必需，不持久化 | YAML 是主机侧源配置，尚未成为 MCU 解析格式；不要求 MCU 增加文件系统 |
| 暂缓 | 多设备、动态下载事务、掉电保存、生产设备协议、性能验收 | 不取消这些需求；在最小通路成立后分别接入 |

Profile [源文件](../../tools/protocol/cfg/最小回环配置.yaml)中的节点数由列表推导，没有“电机轴数”或通用 Arm 字段。首版只有一个必选节点，不据此声称主站选择设备子集已经实现。

按用户偏好，本次新增的 Profile、契约和测试向量统一使用 YAML，不保留并行维护的 JSON 副本；原生产协议生成器的配置不在此次迁移范围。单位放在字段名后缀，值仅写整数：速率用 `nominal_bitrate_kbps: 1000`，周期用 `pdo_period_ms: 1`，等待用 `activation_wait_s: 5`，数字后不跟单位。检查器将其精确转换为内部 bps/us，不使用浮点换算，也不改变线上字段。

速率后缀固定为 `_kbps`，按每单位 1000 bit/s 换算，不是字节率或 1024 进制。时间字段按源文件固定使用 `_ms` 或 `_s`，不接受随意替换后缀。带单位或引号的数值、布尔值、小数、非正数、换算溢出，以及旧键或未知键直接拒绝，不猜测单位。源文件保留必要的时间策略，尚不将超时值隐藏在未定义的默认规则里。

文件支持注释和 `0x600` 这类十六进制 CAN ID。当前采用受限 YAML 数据格式：键必须为字符串，布尔值仅用小写 `true/false`，普通整数仅用无多余前导零的十进制或 `0x` 十六进制。测试中的数值模式改用十六进制，完整字节串按字节分组，用引号或 YAML 块文本保存，不再排成一整行长数字；保留全部字节，不从待测编码器反向生成期望值。拒绝重复键、锚点/别名、合并覆盖、自定义类型、浮点数、空值、隐式日期及多文档，避免配置出现隐含继承或自动类型转换。需要字面字符串 `on` 等时显式加引号。

## 初始化到回环

以下是同一条流程的分段表。“已有证据”与“目标行为”不混用。

| 步骤 | 负责部分 | 进入条件与工作 | 完成/失败出口 | 当前证据 |
| --- | --- | --- | --- | --- |
| 1. SDK 启动 | SDK/启动代码 | 复位、运行时建立，到达 `main` | 进入板级初始化；异常不继续 | 首轮 JTAG 复位路径到达，未验收无调试器冷启动 |
| 2. 板级初始化 | 自研 BSP 与 SDK 驱动 | 时钟、引脚、时间基准、必要板级资源 | 成功后进入 ESC；失败报告 | 首轮分段检查通过，不是全部电气验收 |
| 3. EtherCAT 硬件 | 工程适配与 SDK/ESC | EEPROM/SII、PHY/ESC 初始化 | 保留区按既有保护流程处理；错误不启动业务 | 首轮通过，SII 有更新并保留前后备份 |
| 4. CAN 控制器 | 工程 CAN 适配与 SDK | 控制器、消息 RAM、中断及队列初始化 | 成功后建立管理运行环境 | 四路生产初始化通过，生产收发未验；另有 MCAN0 独立内部回环通过，不全属于未改动的 BSP |
| 5. 加载配置 | 新通用运行层 | 读取完整预置 Profile，校验能力、尺寸和资源；管理通信尽早可用 | `BOOT -> PREPARING`；不合法进入 `FAULT` | 本轮仅有主机侧契约校验 |
| 6. 自检与准备 | 统一调度 + 回显设备模块 | 按已知 ID 探测，核对真实回复，准备路由及 PDO 快照 | 必选节点成立后 `READY`；缺失继续有界重试 | 核心可接收已核验事件，真实 CAN 探测和匹配尚未接入 |
| 7. 保持就绪 | 通用运行层 | 主站缺席也维护反馈新鲜度、状态和就绪代际 | 条件失效撤销就绪；不虚报准备完成 | 注入时间与反馈事件的离线测试通过 |
| 8. 一次应用确认 | 管理通道 + 状态机 | 比较 Profile/摘要、启动标识、就绪代际，接受一笔完整激活 | 返回会话；协议条件未齐仍为 `READY`，不等第二次业务确认 | 原生值判断及重复请求测试通过；线上编解码和 SDO 对象尚未接入 |
| 9. 周期往返 | 周期调度 + 路由 + CAN | 当前确认有效、实际映射/DC/OP 成立、收到当前会话新 PDO | 周期边界转 `RUNNING`；RxPDO -> CAN -> 对端 -> CAN -> TxPDO | 仅有字节级测试向量，没有真实往返证据 |
| 10. 失效或停止 | 状态机 + 输出抑制 | 主站退出、超时、CAN 故障或关键条件变化 | `HOLD`，撤销会话及在途数据；恢复准备后需新确认 | 转换表待实现及故障注入 |
| 11. 修改配置 | 后续配置事务 | Candidate 完整校验、必要暂停、准备、激活和提交 | 失败保留/恢复已定义的安全状态，不能污染 Active | 仍按架构草案，未纳入本轮代码 |

这四步之后的管理与周期入口当前仍走[现有 `main.c`](../../firmware/app/main.c)的 `motor_control_init()`、SSC 和 RTOS 路径。不能把新 YAML 放入工程就宣称它已经驱动固件。

## 数据与内存契约

机器可读来源是[最小网关契约](../../tools/protocol/cfg/最小网关契约.yaml)。所有整数使用小端、定长无符号编码；偏移单位是字节，区间为左闭右开，无隐式填充。`bytes32` 是原始 32 字节，不是线上 64 字符字符串。内存地址由实现分配，本文冻结的是试验载荷偏移，不是 MCU 物理地址。

不要直接把非对齐 PDO 指针强转为 C/C++ 结构体；例如 `session_id` 在偏移 4。后续固件须显式编解码/复制，发布完整快照，不能边改字段边被 SSC 或中断读取。主机检查器不是 MCU 并发或非对齐访问验证。

| 记录 | 总字节数 | 字段：偏移 / 类型 |
| --- | --- | --- |
| CAN 请求/回复 | 8 | `probe_tag` 0/u32；`probe_seq` 4/u32 |
| RxPDO | 32 | `layout_version` 0/u16；`flags` 2/u16；`session_id` 4/u64；`cycle_seq` 12/u32；`probe_tag` 16/u32；`probe_seq` 20/u32；`reserved` 24/u64 |
| TxPDO | 48 | `layout_version` 0/u16；`state` 2/u8；`valid` 3/u8；`session_id` 4/u64；`publish_seq` 12/u32；`accepted_cycle_seq` 16/u32；`echo_tag` 20/u32；`echo_seq` 24/u32；`feedback_age_us` 28/u32；`reason` 32/u32；`can_rx_count` 36/u32；`can_tx_count` 40/u32；`reserved` 44/u32 |
| 状态查询载荷 | 80 | `layout_version` 0/u16；`state` 2/u8；`ready` 3/u8；`profile_id` 4/u32；`profile_revision` 8/u32；`profile_digest` 12/bytes32；`boot_id` 44/u64；`ready_generation` 52/u32；`active_request_id` 56/u32；`session_id` 60/u64；`reason` 68/u32；`feedback_age_us` 72/u32；`client_tag` 76/u32 |
| 激活请求载荷 | 64 | `profile_id` 0/u32；`profile_revision` 4/u32；`profile_digest` 8/bytes32；`boot_id` 40/u64；`ready_generation` 48/u32；`request_id` 52/u32；`client_tag` 56/u32；`reserved` 60/u32 |
| 激活结果载荷 | 16 | `request_id` 0/u32；`result` 4/u16；`state` 6/u8；`reserved` 7/u8；`session_id` 8/u64 |

**尚未分配新 OD 索引、PDO 映射索引或修改 ESI/SII。** 上表 SDO 部分只是应用载荷，不含邮箱/CoE 头。计划使用完整 OCTET_STRING 接收激活，允许协议分段；只有完整接收并校验后才能提交。不依赖现有未支持的 Complete Access，也不能将 64 字节请求描述为一个 expedited SDO；本地 [SSC 定义](../../third_party/beckhoff_ssc/Src/sdoserv.h)的 `MAX_EXPEDITED_DATA` 为 4。“一次确认”是一笔应用事务，查询状态/结果并未消失。

本地 READY 不代替标准 EtherCAT 状态转换：PREOP 可进行邮箱通信，但过程数据尚未交换，SAFEOP 与 OP 的输出条件也不同。[Beckhoff EtherCAT 状态机说明](https://infosys.beckhoff.com/content/1033/tc3_io_intro/1446518411.html)

### 字段语义

- `layout_version=1`，所有 `reserved=0`；未知标志、错误尺寸/版本/会话拒绝，不能截短后继续解释。
- RxPDO `flags` 仅 bit0 表示提交一次回显请求；其他周期可为 0，用于当前会话保活。首个业务请求的 `probe_tag` 必须等于激活中的非零 `client_tag`。
- 每个有效新 PDO 的 `cycle_seq` 严格递增。每个实际接受的 CAN 请求的 `probe_seq` 在当前 tag 内严格递增；重复 PDO 不重复发帧。首版不跨序号回绕继续运行，耗尽时撤销会话并报告 `COUNTER_EXHAUSTED`。
- 单在途槽；繁忙或未到交换间隔时返回 `BUSY`，不覆盖、不暗中缓存新请求。主站用新的 `cycle_seq` 重试未被接受的请求；`accepted_cycle_seq` 只在成功提交 CAN 队列后更新，不代表 TX 完成或收到回复。
- 无激活时允许 `probe_tag=0` 的诊断请求，序号递增；其回复只能维护本地就绪，不能成为已激活业务反馈。诊断不得阻塞业务快路径；切换时撤销诊断在途项并隔离旧回复。
- 对端只将 `0x600` 的 8 字节原样回复到 `0x601`。接收方检查通道、ID、帧类型、DLC、tag/seq 与唯一在途请求、接收时间和截止时间；TX 完成中断或收到任意 CAN 帧都不能置业务反馈有效。
- 主站在 `RUNNING` 时每 10 ms 发起一笔新回显请求，其余周期只保活。`valid` 是当前会话最近一笔已匹配反馈的新鲜性，不表示它必然对应本周期或最新待回复请求；用 tag/seq 关联，不能强行假设一拍已收到 CAN 回答。
- 从未得到当前会话反馈或反馈失效时，`valid=0`，`feedback_age_us=0xffffffff`；保留旧数值也不能标有效。其余年龄用单调时钟差计算并饱和到 `0xfffffffe`，不能回绕变年轻。
- `publish_seq` 在每次完整 TxPDO 快照发布时递增；`can_rx_count` 统计当前会话已匹配业务回复，`can_tx_count` 统计当前会话已确认完成的业务发送。诊断、乱序或错误帧不计入这些成功数；额外错误统计后续定义。

试验时限：回复截止 5 ms，本地就绪/反馈最大年龄 50 ms，有效新 PDO 保活截止 5 ms，接受确认后等待协议条件最长 5 s。它们是待实测的初始设置，不是已经达到的延迟指标；一笔在途请求超时立即撤销就绪/会话，不能继续等到年龄上限。无请求或调度遗漏也不能无限维持旧就绪。

### 摘要与会话

`profile_digest = SHA256(ASCII(JSON({"contract":契约,"profile":规范化配置})))`。源文件先从 YAML 安全解析并校验，`nominal_bitrate_kbps` 转为内部 `nominal_bitrate` 整数 bps，时间字段将 `_ms` 或 `_s` 换成 `_us` 并转为整数微秒，再仅在内存中用键排序、无空白分隔符、`ensure_ascii=True` 的 JSON 规范化数据；不会生成另一份 JSON 配置文件。摘要不包含注释、源文件排版、键的书写顺序、测试向量、路径或运行状态。CAN ID 的十六进制/十进制写法不改变摘要；本次单位后缀调整也不改变规范化结果或摘要。先拒绝重复键、不支持的 YAML 类型及非法字段/范围，再计算摘要。哈希用于一致性判断，不是身份认证或签名。

本轮规范化配置、字段布局、完整摘要及测试向量的每个字节均与改写前核对一致；完整基线摘要保留在自动测试中，不要求手工维护。检查器默认不打印长摘要，留档时可执行 `python3 tools/protocol/check_gateway_contract.py --show-digest` 获取完整值。此调整只影响呈现，不截断内部摘要。修改有效配置或字段布局会改变摘要，不能只比较手填的 Profile ID。业务语义改变时还需显式升级契约版本/标识，不能只改本文文字而沿用旧线上含义。

激活必须匹配 `boot_id` 和 `ready_generation`；就绪失效、重新准备或配置变化时改变代际，不因每个正常反馈都增加代际。同一存活会话内，完全相同的 `request_id` 和载荷重试返回原结果；同 ID 不同载荷拒绝，失效后的旧请求拒绝，不能重新创建许可。

`boot_id`、`session_id`、`request_id`、`client_tag` 非零；会话失效时清零活动会话并清理旧命令。在受控试验内，启动/会话标识、已消费请求 ID 和 client tag 不复用。**跨复位的标识生成与防旧帧机制尚未实现，必须在固件接入前确定；不能仅靠置零计数器宣称已防重放。** 后续实板轮次需清空对端延迟回复并使用新 tag，不能沿用下面的固定样例作为实时授权。

## 状态与任务契约

状态编码：`BOOT=0`、`PREPARING=1`、`READY=2`、`RUNNING=3`、`HOLD=4`、`FAULT=5`。激活是否接受是独立事实，不增设电机式 Arm 状态；本版尚无动态重配，因此不实现草案中的 `QUIESCING`。

| 状态/事件 | 前提 | 转换与动作 | 禁止行为 |
| --- | --- | --- | --- |
| `BOOT` 初始化完成 | 本地配置合法、资源可用 | `PREPARING`，启动有界探测，管理通道响应进度 | 等主站逐个下发设备配置才准备 |
| `PREPARING` 收到有效探测回复 | 必选节点、路由及缓冲均满足 | `READY`，建立就绪代际并持续维护 | 仅凭 CAN init 或软件构造回复置 READY |
| 主站提前激活 | 尚未就绪 | 返回 `NOT_READY`，不缓存未成立的授权 | 在 SDO 回调等待 CAN、OP 或无限重试 |
| `READY` 收到激活 | 配置摘要/启动/代际匹配 | 原子接受并返回 `ACCEPTED` 和会话，仍为 `READY` | 激活时重新扫描全部设备、擦 Flash 或动态分配 |
| 已接受确认，条件齐备 | 实际映射/DC/OP 成立、当前会话首个新请求有效 | 在允许的周期边界进入 `RUNNING` | 要求第二次业务确认；只看 OP 就发业务帧 |
| `RUNNING` 新请求/回复 | 完整有效快照、预算与在途规则满足 | 收发并发布新快照；重复/错误消息拒绝 | 半帧写入活动数据区；假定排队成功就是设备已回复 |
| 无效请求或繁忙 | 原会话仍有效 | 返回/发布 `INVALID_COMMAND` 或 `BUSY`，不发送该请求；不延长无效 PDO 的保活 | 覆盖在途项或旧命令反复执行 |
| 关键条件失效 | 回复/PDO 超时、离开 OP、bus-off、映射/DC 改变 | `HOLD`，先抑制新业务发送、撤销许可、清理在途项、反馈失效 | 条件恢复就自动复用旧确认或旧 PDO |
| 等待协议超过时限 | 已确认但尚未进入 RUNNING | `HOLD`，撤销确认，报告 `PROTOCOL_MISMATCH` | 长期保存旧激活而不报告 |
| `HOLD` 可恢复 | 故障原因已处理 | 重新核验，可复用未失效资源，回 `PREPARING/READY`；需新的激活 | 无条件重启全部 MCU；或未经核验直接恢复 |
| 配置/资源不可恢复错误 | 无合法运行基础 | `FAULT`，保留可用管理与诊断 | 部分节点或半份配置悄悄上线 |

结果码和原因码的精确数值见机器契约。`NONE`、`INVALID_COMMAND`、`BUSY` 是运行/请求结果；其余错误按上表撤销许可或进入 `FAULT`。拒绝激活时 `activation_result.session_id=0`，不改变原有活动会话；仅完全相同的存活事务重试可返回原非零会话。

任务约束保持草案方向：一个所有者修改状态和 Active；共享 CAN 队列只由统一接收分发/发送调度消费；SSC 的可变状态不分散到多个设备任务。ISR 只交接事件、时间戳及必要输出抑制；事件处理、探测、管理命令都有预算。

### 首段核心

[就绪核心](../../firmware/app/gateway/gateway_readiness.c)是单任务所有的原生值接口，不依赖 RTOS、SSC、CAN 或配置读写。启动接收已校验的本地 Profile、单调时间和启动 ID；只有收到由后续适配层核验的回复事件才能进入 `READY`。事件须携带实际接收时间，拒绝超龄、未来、重复和上一次准备期间的旧时间戳。适配层仍负责 CAN 通道、ID、帧格式、在途匹配、真实回复截止及资源检查；不得用任意 RX 或 CAN init 结果替代核验。

核心用每次启动的高水位拒绝已消费请求和 tag。主站在同一次启动内，新接受的 `request_id` 和 `client_tag` 各自严格递增且不回绕；同一活跃请求的逐字段相同重试返回原会话，不顺延截止，也不再次申请 ID。进入 `HOLD` 撤销会话、改变就绪代次；恢复必须重新核验，再接受新确认。上线前须提供跨复位唯一的 `boot_id` 和会话 ID 来源；会话分配接口只能从启动时预留的 ID 中有界取值，不在确认时做 I/O 或写 Flash。测试使用替身 ID，不构成实板跨复位隔离证据。

本阶段接受确认后仍为 `READY`，没有 `RUNNING` 转换或发送入口。还需接入 YAML 预置生成、OD、PDO/DC/OP 条件和周期收发。原生类型不可直接作为线上数据；线上仍按上表固定字节布局独立编码。

## 无动作测试分层

没有外部对端不阻塞离线工作，但限制物理证据。现有 [SDK MCAN 头文件](../../third_party/hpm_sdk/drivers/inc/hpm_mcan_drv.h)和[实现](../../third_party/hpm_sdk/drivers/src/hpm_mcan_drv.c)提供 `mcan_mode_loopback_internal`；当前生产初始化并未按本文切换到该模式。

| 层次 | 所需条件 | 后续测试内容 | 能证明 / 不能证明 | 本轮状态 |
| --- | --- | --- | --- | --- |
| A. 离线契约 | 主机 Python，无板卡 | Profile 约束、字节序/长度/偏移、摘要、非法输入与固定向量 | 证明源材料自洽；不证明固件收发、调度或状态推进 | 已提供检查器与单测 |
| B. 状态机单元测试 | 纯逻辑核心、可控时钟和注入事件 | 自举、提前主站、一次确认、超时、重试与旧会话隔离 | 证明被测状态逻辑；注入事件不能证明 CAN 硬件 | 首段 8 项单测（11 个场景）及 ASan/UBSan 通过；不含周期收发和线上接口 |
| C. 控制器内部回环 | 专用无业务测试入口、重新确认实板范围 | 单路实际 TX/RX、ISR/队列、8 字节和超时路径 | 不需要外部对端；不证明收发器、线缆、端接或 ACK 来自真实节点 | [独立入口](../当前说明/独立CAN内部回环测试.md)首轮 MCAN0 实板 12 帧通过；故障注入仅在主机完成，不复用生产 transport |
| D. 物理 CAN 回显 | 可控对端，或核对后让板上另一路承担测试对端 | 请求 ID `0x600`，回显 ID `0x601`；收发和错误/丢包观测 | 覆盖实际物理收发；同 MCU 两路互测不等于独立生产设备互通 | 用户确认无外部对端；双通道互连仅是备选，未核对/接线 |
| E. EtherCAT 到 CAN 完整往返 | 新试验固件/OD/ESI、主站、物理回显路径 | 无主站预就绪 -> 状态查询 -> 一笔激活 -> 标准协议条件满足 -> 往返与故障注入 | 可验收该试验路径；不能替代生产设备或实时极限验收 | 尚未准备完整执行条件 |

内部回环返回的是原始发送 ID，不是对端在 `0x601` 发出的独立回复。层 C 必须作为独立控制器测试，不得在生产接收逻辑偷偷将 `0x600` 改写为 `0x601` 并记成层 D/E 通过。

后续测试前必须补齐：

1. 审核独立测试入口，证明不调用旧 motor 启动/发送策略，不把单纯的 LED 测试当作数据测试；默认生产固件不被替换或自动启用测试模式。
2. 如需实板，重新确认动力及所有业务节点隔离、逻辑供电、J-Link 接线和复位/烧录范围，仍走镜像冻结与保留区备份。旧确认不自动延续。
3. 物理 CAN 测试前核对原理图、实际通道、收发器供电/使能、端接和地线；现有 `board_can_transceiver_phy_set()` 为空，不能凭函数被调用判定已使能。
4. 即使只有回显载荷，也必须隔离真实执行器节点；`0x600/0x601` 不是天然无动作的安全地址。两路互连需独立确认，不在本轮操作。
5. 完整往返前分配并核对 OD/映射索引，生成一致的测试 ESI/SII，落实会话标识来源、真实帧过滤、线程/中断所有权和内存预算。64 字节激活接收完成后一次提交，不允许分片改变活动许可。

### 用例与记录

| 重复/延迟 | 重复激活、重复 PDO、旧 tag 回复、晚于截止回复 | 存活激活幂等；不重发旧命令；旧回复不进入新会话 |

[测试向量](../../tools/protocol/cfg/最小回环测试向量.yaml)是字节编码样例，含人工摘要 `00..1f`、固定会话标识及边界值，不是可直接下发的有效启动事务。实际联调须填入当前状态与摘要，序号/标识重新生成。

每轮记录冻结 ELF/契约/Profile 摘要、主站版本、连接方式、帧日志、状态转换及至少四个时间点：本地 READY、激活接受、协议条件齐备、首笔匹配 TxPDO。主从时钟未对齐时不直接相减；分别记录从站内部间隔和主站观察间隔。需要比较旧方案时保持同样物理条件，不把总耗时都归因于 SDO。
